# Gotchas

Non-obvious pitfalls and invariants. Most were discovered by hand-testing; several are encoded in load-bearing comments in the code.

## Encoding

- **`-qp 0`, never `-crf 0`, for lossless.** Hand-verified on this Homebrew libx264 build: `-crf 0` does NOT round-trip bit-exact for 10-bit (yuv420p10le) sources — only `-qp 0` does. `-crf 0` is the commonly-cited flag online but only holds for 8-bit. Documented in `encode_args`' docstring. Lossless always emits the High 4:4:4 Predictive profile and typically costs 2–3× the size of an already-lossy source.
- **Speed default parsing deliberately avoids `or`**: `raw_speed = c.get('speed'); speed = 1.0 if raw_speed is None else float(raw_speed)` in `render_timeline`. Using `c.get('speed') or 1.0` coerces a literal `0` to the default and silently skips the `(0, 1]` range check — this was a real bug caught in verification.
- **The fps filter needs a hard frame cap**: `fps=target_fps` can emit one spurious duplicate frame at EOF (concat graph runs in 1/1000000 timebase; an end timestamp landing exactly on a frame tick rounds into an extra frame). Every per-clip chain is capped with `trim=start_frame=0:end_frame=<n_norm_frames>` and audio padded/cut to the identical duration — otherwise every clip boundary drifts 1/fps out of sync.
- **`out_sec` is clamped to `video_duration`** (both in `render_timeline` and `build_timeline_filter`): the frontend's historical default outSec was the container duration, which can outlast the last video frame when audio runs longer. Without the clamp, a one-frame freeze window sampled past the last real frame selects ZERO frames — the freeze silently vanishes from video while its anullsrc silence still lands in audio, desyncing everything after it.
- **Hold sampling under reversal is flipped**: after reverse, the frame that plays FIRST is the one originally at outSec — so the lead hold samples outSec and the trail hold samples inSec. A hold must freeze the frame adjacent to it in *final playback order*.
- **The server NEVER trusts client-supplied fps/has_audio/resolution** — `render_timeline` re-probes every input itself. Only inSec/outSec/holds/speed/reversed come from the request.
- `run_ffmpeg` prepends the binary and `-y` itself — args must NOT include `ffmpeg`, and outputs are force-overwritten. render_timeline uses timeout=1800 (vs default 600) because whole-timeline `-qp 0` renders run long.
- `/api/reverse` returns HTTP **200** (not an error) with `{warning, estimated_bytes}` when the estimated RAM (W×H×3×fps×duration) exceeds 2 GiB and `confirm` is absent — client must resend with `confirm: true`. ffmpeg's reverse filter buffers the whole video in memory.
- **`under50mb` is not a CRF or single-pass-ABR mode, deliberately.** CRF has no size guarantee at all (size follows content complexity). Single-pass ABR knows a target bitrate but routinely drifts several percent off it because it can't see the whole file's complexity in advance — not acceptable against a hard "always under 50MB" promise. `render_size_capped` runs a real two-pass encode (pass 1 → `/dev/null` via `-f null`, discovers per-frame complexity; pass 2 spends the byte budget against that map) and then **measures the actual output file size** and retries with a 15%-smaller bitrate (up to `max_attempts`) if it still overshot — the guarantee is enforced by checking the real file, never just trusted from the bitrate math. Every call site (`render_timeline`, `trim`, `splice`, `hold_frame`, `reverse`) needs the render's total duration to size the bitrate budget; `trim`'s `start`/`end` can be `HH:MM:SS.ms` timecodes (see the legacy UI's own placeholder), not just plain seconds — `_parse_time_to_sec` in app.py handles both. `render_size_capped` cleans up its own `<out_path>.ffpass*` two-pass log files in a `finally` block even on failure.
- **`under50mb_hevc` (`render_size_capped(..., codec="hevc")`) uses genuinely different flags than the H.264 path, not just a swapped `-c:v`.** libx265 has no `-pass`/`-passlogfile` options at all (hand-verified) — two-pass is `-x265-params "pass=1:stats=<file>"` / `"pass=2:stats=<file>"` instead, producing stats files named `<file>` + `<file>.cutree` (vs. libx264's `<prefix>-0.log`/`-0.log.mbtree`) — `_PASSLOG_SUFFIXES` branches the `finally` cleanup on `codec` accordingly. `-maxrate`/`-bufsize` DO work identically as top-level flags for both codecs (verified via the encoded stream's own reported CPB properties) — no `vbv-maxrate=`/`vbv-bufsize=` workaround needed. 10-bit intermediate (`-profile:v main10` + `yuv420p10le`) needs its pixel-format conversion spliced into the caller's EXISTING `-vf`/`-filter_complex` value (`_inject_pixel_format`), never added as a second separate `-vf`/`-filter_complex` flag — ffmpeg silently lets a later duplicate flag on the same stream **replace** the earlier one (confirmed by hand: explicit "Multiple -filter/-af/-vf options specified for stream 0, only the last option will be used" warning), which would silently drop `reverse`'s own `-vf "reverse"` or an entire `-filter_complex` graph. The splice point for `-filter_complex` callers is the literal `[outv]` label every filter builder in this module terminates its video chain with.

## Frontend invariants

- **Hold placement invariant**: headHoldSec only on the first clip; tailHoldSec/roundHoldSec only on the last. `sanitizeHoldPlacement` (clipMath.js) zeroes violators and marks them dirty — every operation that reorders/adds/splits/deletes clips must run its result through it (all current ones do).
- **`useUndoableState` keeps `{present, past}` in ONE state object** for React StrictMode safety: double-invoked updaters produce identical results instead of double history pushes. Don't split into two useStates.
- **track2Clips (V2) is intentionally outside undo** — Cmd/Ctrl+Z only ever affects V1, via `useUndoableState`; V2 is plain `useState` in App.jsx. This is scoped to undo only — V2 is otherwise fully hand-editable (Trim/Hold/Reverse/Speed/Crop/Duplicate/Splice/Raise/reorder), so a V2 mistake is undone by re-editing or re-running Analyze/Reconstruct, not Cmd/Ctrl+Z. `handleCleared` resets V1's undo history AND clears V2's clips/selection entirely, since both reference `input/` files that just got deleted.
- **Playhead/transport/ruler are ALWAYS driven by V1**, even when V2 is displayed on top. `handlePlaybackSelectClip` only syncs V1's selection when the playing clip is actually in V1's list. `focusedTrack` (lifted to App.jsx, not local to Timeline.jsx) now does double duty: it still routes the Delete/Backspace key to the right track (Timeline.jsx), AND it's what the shared toolbar row in App.jsx (`activeClips`/`setActiveClips`/`activeSelectedClip`/`setActiveSelectedId`) reads to decide which track's clips the Trim/Hold/Reverse/Speed/Crop/Duplicate/Splice/Raise controls act on. Selecting a clip on either track sets `focusedTrack` as a side effect (`handleSelect`/`handleSelect2` in Timeline.jsx); the toolbar has no separate "which track" control of its own.
- **Playback is a rAF scrub loop** setting `videoRef.currentTime` each tick — the `<video>` never natively plays during timeline playback, so **audio does not play in preview**. `displayClips` is read via a ref so mid-playback visibility toggles apply next frame; any change to V1's clip array stops playback.
- **CLIP_PALETTE class names must stay literal strings** (comment at clipMath.js) — Tailwind v4's scanner can't generate template-interpolated classes like `` `from-${c}-700` ``.
- **Speed math has two directions**: `clipMainSec` DIVIDES by speed (timeline length stretches when slowed); TimelineClip edge-drag MULTIPLIES the pixel delta by speed (screen pixels are timeline seconds; a slowed clip covers less source time per pixel).
- **Timeline pixel constants must stay in sync**: `GUTTER_PX=48` ↔ the `w-12` gutter, `GAP=2` ↔ `gap-0.5`, Ruler adds `clips.length*2`. Changing lane spacing requires updating `playheadPx` and `clientXToTimelinePos` together.
- Deleting or reordering ANY clip marks ALL remaining clips dirty — the rendered sequence changed even though individual clips didn't.
- Keyboard shortcuts are suppressed when focus is in an INPUT/TEXTAREA; Delete removes the selected *part* (hold segment) rather than the clip when a hold is selected.
- OutputPanel auto-loads the newest output when `files.length` changes (deliberately `files.length`, not `files` — eslint-disabled).
- **"Analize" is misspelled on purpose-ish** (Timeline.jsx button + AboutDialog) — existing product copy; don't fix in only one place.
- **Chat edits only reach the timeline via `handleEditResult`'s clip-swap** (App.jsx): `/api/execute` reports which file its command actually wrote (`_output_arg_info` in app.py, parsed from the validated argv's output path — never guessed), and if a clip is selected, `App.jsx` reprobes that file and replaces the selected clip's source/dimensions in place, resetting trim/hold/reverse/speed/crop (the chat edit is now baked into new pixels, same treatment Reconstruct gives a "fresh" source). Before this, a Run only ever produced a new file in Exports with zero effect on the clip being edited — don't regress this by having `onResult` go back to a no-arg `refresh()`-only callback.

## Security / safety model

- `validate_ffmpeg_command` applies **NO character blocklist deliberately**: subprocess always gets argv lists (never `shell=True`) so `;`, `()`, `$` are inert, and filter_complex legitimately needs them. Safety = first token must be `ffmpeg` (binary path force-replaced), every `-i` path and the output must realpath-resolve inside `input/` or `output/`. Do not "harden" it with character filters.
- `safe_path` rejects absolute paths and traversal via realpath+commonpath; `GET /input/<name>` and `/output/<name>` skip it and rely on `send_from_directory`'s own protection.
- `input/` is sacrosanct — never modify or delete files there programmatically. `/api/clear_input` (user-confirmed) is the only sanctioned deletion path.

## Environment quirks

- **Hardcoded machine-specific paths**: `FFMPEG=/opt/homebrew/bin/ffmpeg`, `FFPROBE=/opt/homebrew/bin/ffprobe` (ffmpeg_utils.py), `CLAUDE_BIN=/Users/sarmieaj/.toolbox/bin/claude` (app.py). `browse_directory`/`reveal_file` are macOS-only (osascript / `open -R`).
- **Export-dir inconsistency to know before touching**: only `/api/render_timeline` writes to the user-configured export dir (`get_output_dir()`); trim/splice/hold_frame/reverse hardcode `fu.OUTPUT_DIR`, and `unique_output_name` only checks `fu.OUTPUT_DIR`. `/api/probe?dir=output` also uses `fu.OUTPUT_DIR` while render clips with `dir=='output'` resolve against `get_output_dir()`.
- `ALLOWED_EXTENSIONS` is video-only (.mp4 .mov .mkv .avi .m4v .webm) — audio/image uploads are rejected despite older docs mentioning them.
- Version spread: Python 3.9.6 venv (macOS CommandLineTools) vs bleeding-edge Vite 8 / React 19 / Tailwind 4. Lint is oxlint, not eslint.
- In shell commands, `ffmpeg`/`ffprobe`/`node` are NOT on PATH by default in this environment — run `eval "$(/opt/homebrew/bin/brew shellenv)"` first, and note the working directory resets between some invocations (cd explicitly; `npx vite build` fails with UNRESOLVED_ENTRY if run from the repo root instead of `frontend/`).
- `.export_settings.json` is **global mutable state** — a render's quality mode is whatever it holds at that moment. Parallel test renders can race each other's quality settings (bit-exact hash checks then fail mysteriously); pin it to `lossless` before hash-verification renders.
