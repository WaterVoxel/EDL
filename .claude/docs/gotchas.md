# Gotchas

Non-obvious pitfalls and invariants. Most were discovered by hand-testing; several are encoded in load-bearing comments in the code.

## Encoding

- **`-qp 0`, never `-crf 0`, for lossless.** Hand-verified on this Homebrew libx264 build: `-crf 0` does NOT round-trip bit-exact for 10-bit (yuv420p10le) sources — only `-qp 0` does. `-crf 0` is the commonly-cited flag online but only holds for 8-bit. Documented in `encode_args`' docstring. Lossless always emits the High 4:4:4 Predictive profile and typically costs 2–3× the size of an already-lossy source.
- **Speed default parsing deliberately avoids `or`**: `raw_speed = c.get('speed'); speed = 1.0 if raw_speed is None else float(raw_speed)` in `render_timeline`. Using `c.get('speed') or 1.0` coerces a literal `0` to the default and silently skips the `(0, 1]` range check — this was a real bug caught in verification.
- **The fps filter needs a hard frame cap**: `fps=target_fps` can emit one spurious duplicate frame at EOF (concat graph runs in 1/1000000 timebase; an end timestamp landing exactly on a frame tick rounds into an extra frame). Every per-clip chain is capped with `trim=start_frame=0:end_frame=<n_norm_frames>` and audio padded/cut to the identical duration — otherwise every clip boundary drifts 1/fps out of sync.
- **`out_sec` is clamped to `video_duration`** (both in `render_timeline` and `build_timeline_filter`): the frontend's historical default outSec was the container duration, which can outlast the last video frame when audio runs longer. Without the clamp, a one-frame freeze window sampled past the last real frame selects ZERO frames — the freeze silently vanishes from video while its anullsrc silence still lands in audio, desyncing everything after it.
- **Hold sampling under reversal is flipped**: after reverse, the frame that plays FIRST is the one originally at outSec — so the lead hold samples outSec and the trail hold samples inSec. A hold must freeze the frame adjacent to it in *final playback order*.
- **A hold's `anullsrc` silence must be quantized to the same frame grid the freeze is** — `lead_frames / fps`, never the raw `lead_hold_sec` off the request. That silence IS the mechanism that offsets the clip's own audio (it's concatenated ahead of `[amain{i}]` in the same order the freeze is prepended to the video), so if the two lengths disagree the whole clip's dialogue lands late against its picture. The freeze always emits a whole number of frames (`loop=round(H*fps)-1`), so any hold that isn't a frame multiple used to desync: measured at 24fps with a 0.51 s hold (which quantizes to 12 frames = 0.500 s), the audio ran **exactly 441 samples = 10.00 ms late**, and because the per-clip `apad`/`atrim` then cut back to `expected_sec` (itself computed from `lead_frames`), the same 441 samples of **real audio were silently dropped off the tail**. Both confirmed by sample-aligning the render against its source (residual 2.4e-05 = the s16le quantization step). The fix is audio-only: video frame hashes are byte-identical either way, and for frame-multiple holds the emitted graph is textually unchanged. Verify hold/audio alignment with a *non-periodic* marker — a sine tone is invisible to a shift that's a whole number of its periods (441 samples is exactly 10 cycles of 1 kHz at 44.1 kHz, which is how this nearly went unnoticed).
- **Delay the A1 bed with `adelay`, not a PTS shift** — the bed is offset to V1's picture start by `adelay=delays=<ms>:all=1`, and the *prepends-silence* semantics are what make it safe: the downstream `apad=whole_dur=N`/`atrim=end=N` still measure from 0, so a 1 s head hold yields 1 s of leading silence and 1 s **less bed heard**, never a render 1 s longer. An `asetpts`-style shift would push the bed's end past `N` and either stretch the output or get truncated unpredictably. `all=1` is mandatory: without it `adelay` only shifts the channels it was given explicit delays for, so a stereo bed comes out with one channel early. The offset is frame-quantized (`lead_frames / fps`) so it lands on the same grid as the freeze. Verified by the difference identity `(with-bed)[i] - (no-bed)[i] == BED_GAIN * bed[i - off]` across hold ∈ {0, 0.5, 1.0, 0.51, 2.0} (max err 4.3e-05 = the s16le step), with **zero** bed contribution during the hold (0.00e+00) and output length always exactly `hold + sequence`. A zero head hold emits no `adelay` node at all, so the no-hold graph is provably unchanged.
- **`concat` negotiates its output format from its FIRST input, so every audio piece must be `aformat`-ed as it is created** — not just once after the concat. The per-clip audio pieces are gap/main/gap in playback order, so *which* piece lands first depends on which holds exist. With a **trail-only** gap the first input is the raw source pad `[i:a]`, and a mono/48 kHz source made concat negotiate mono: the stereo noise fill that followed was silently **downmixed, measured -4.4 dB** (rms 0.007089 vs the asset's own 0.011854), and the post-concat `aformat` then upmixed the already-collapsed signal back to stereo. The same clip *with a lead hold* was full level, because that put an already-`aformat`-ed gap first — the bug's presence depended on hold layout, not on the gap being filled. **Pure silence hid this indefinitely: a downmixed silence is still silence**, which is why it only surfaced with noise fill — and note that detector is now GONE: gaps are always `anullsrc` regardless of the toggle (room tone is a separate summed track, never a concat piece), so nothing in the concat pieces would reveal a re-broken negotiation. The `aformat` on `[amain{i}]` has to be kept on the strength of this entry, not re-derived from a symptom. Fix is one `aformat` on the `[amain{i}]` chain, making negotiation independent of piece ORDER. Cost is bounded and is the *better* resample (convert once before concat, rather than after a downmix): for a source needing conversion, **28 samples (0.3 ms) differ at the concat seam, max 5/32768 ≈ -76 dBFS**; for a source already stereo/44.1 kHz the render is **byte-identical**, and a clip with no gap at all (one audio piece, no concat) is byte-identical either way. Video frame hashes unaffected in all cases.
- **Room tone fills the MEASURED silence and nothing else — and BOTH designs it replaced are worth remembering as classes of bug.** `noise_fill_plan()` walks the same per-clip audio pieces `build_timeline_filter` emits (`clip_audio_pieces()`: lead gap, body, trail gap, and the sub-frame slack piece), marks each `(has_sound, duration)`, then carves out the span the A1 track's own audio actually covers (`bed_span()`, from the new `audio_duration` probe field). `noise_track()` renders the complement as ONE bounded full-length stream — per-clip segments concatenated — summed as one ordinary `amix` input. Gaps themselves stay plain `anullsrc`. **Bug class 1 (the original):** eligibility was a set of gap POSITIONS — `noise_gaps = {"head_hold"} if audio_beds else {"head_hold", "trail_hold", "body"}` — so **a timeline with an A1 bed and no head hold, the ordinary case, had no eligible gap at all** and the toggle emitted zero chains. Every saved project in `projects/` is exactly that shape (beds loaded, `headHoldSec: 0` everywhere), so the render was byte-identical on and off while the per-gap chain was provably correct in isolation. Reported twice as "Room Tone does nothing". **Bug class 2 (the overcorrection):** replacing it with one endless layer summed under *everything* did fill every hole, and was reported immediately as "it's playing over the entire audio track" — the bed covers a real project end to end, so tone under the bed is tone everywhere. The rule that survives both: **decide by measured coverage, never by position and never by giving up on measuring.** Existing audio is bit-identical with the toggle on (max |on−off| = **0.000e+00**); only silence changes.
  - **The asset's own tail is 856 frames of pure digital silence, so looping the file whole puts a 17.8 ms DROPOUT in the "continuous" layer every 3.003 s.** Hand-measured on `Audio_NOISE.wav` (144144 frames @48 kHz = 3.003000 s exactly): frames 143174–144143 are a fade through a −100 dBFS window into 856 all-zero frames; leading zeros are 0. Looped and gained, that is a 0.333 Hz pulse in the noise floor — **39 zero-runs of ~754 frames (17.1 ms) in a 120 s render, 90 all-zero 5 ms RMS windows** — which reads as pumping and defeats the point of the layer. **A 50 ms window scan cannot see it** (min −29.0 dBFS, no −∞ windows); it takes a 5 ms scan, so use one. Fix is the leading `atrim=end_sample=NOISE_LOOP_END_SAMPLE` (`= 143174`) **before** `aloop`, cutting where the material is still at full level (5 ms windows there run −36.9 to −42.0 dBFS and it re-enters the loop at −39.5, so the seam is a step inside the noise's own variation). Verified after: **0 all-zero frames of any length across 5,292,000 frames (120 s)**, min 5 ms window −32.72 dBFS, level unchanged (−12.827 dBFS peak / −26.96 dB RMS). The index counts the ASSET's 48 kHz frames, so the trim must stay ahead of the `aformat` resample — and it must be re-measured if the asset is ever replaced.
  - **The fill is bounded PER CLIP, and the last clip gets a 50 ms margin so `amix=duration=first` — not arithmetic — lands the end.** Each clip's runs are padded/trimmed to that clip's own `expected_sec` (`apad=whole_dur` → `atrim=end`), exactly as `[aseq]`'s pieces are, because one `anullsrc`/`atrim` of `total_sec` does NOT quantize the same way: at 24 fps a frame is 44100/24 = **1837.5** samples, so a 10.0 s three-clip timeline measures **441001** samples of picture audio against **441000** for a single trim of 10.0. Merging adjacent same-kind runs (which the plan does, to emit fewer nodes) then shifts the last boundary by a further half-sample — and `amix` treats an input that **ENDS EARLY as silence**, which put a literal `(0, 0)` at sample-frame 441000 of 441001 with the toggle on: the one thing the feature exists to prevent, and invisible to any RMS scan. Fix is structural, not a rounding chase: `NOISE_TAIL_MARGIN_SEC = 0.05` is added to the last clip's final run **and** to its `apad`/`atrim` target, so the fill is deliberately longer than the sequence and the mix cuts it. Re-verified **0 zero sample-frames** in both render and stem. Two rules follow: the tone label must never be `amix`'s FIRST input (it would then set the length and make the render 50 ms long-ended), and never map it straight to an output.
  - **`build_a1_filter`'s per-clip skeleton is a LENGTH authority, not content — do not collapse it into one `anullsrc` of `total_sec`.** The stem is documented as sample-for-sample the A1 contribution to the equivalent V1 render, and it earns that by building the same pieces per clip in the same order with the same `apad=whole_dur/atrim=end=expected_sec`, so it quantizes exactly the way `[aseq]` does. (It reads each clip's `has_audio` even though it renders no clip audio: that is what tells `noise_fill_plan` where the V1 render's own sound would be, and therefore where tone must stay out. Drop it and the stem gets tone the render doesn't have, which is the same as not being a stem.) Raw gap durations do NOT agree between `anullsrc` and a tone chain for fractional lengths (`D=0.4171` → 18394 vs 18395 frames; `D=0.033367` → 1471 vs 1472); it is that per-clip normalization that collapses both to the same count, so don't remove or reorder it.
  - **The asset is quiet enough that a working layer reads as a broken one** — `Audio_NOISE.wav` measures **−39.0 dB RMS / −24.9 dB peak**, and the render reproduces it at exactly that level with no attenuation anywhere. Against pure digital silence on laptop speakers that is easy to miss completely, which is how "room tone does nothing" survived two rounds of investigation while the tone was provably in the file. `NOISE_GAIN_DB = 12.0` (module top) is the fix, applied in `noise_layer` alone so the V1 render and the A1 stem can never disagree about level: **keep it in one place**, since a stem louder or quieter than the render's own tone is not that render's A1 contribution any more. Measured result **−26.96 dB RMS / −12.83 dB peak** (the 48 k→44.1 k `aformat` adds +0.09 dB of interpolation overshoot over the arithmetic −12.92, so headroom sums written from `NOISE_GAIN_DB` and the asset's peak alone run slightly optimistic). Gain is a per-sample scale and the layer changes no length, so no video frame or dialogue sample moves.
  - **Tone costs no headroom now — but the bed still can, so don't attribute the margin to the tone.** `amix normalize=0` is an exact sum, so headroom is the caller's problem: clip audio at full scale plus a 0.35 bed reaches **+2.61 dBFS** on its own, and AAC does not clamp it (a deliberately hot test measured **+3.44 dB peak** surviving the encode). Room tone no longer adds to that at all, because it plays only where nothing else does: the render peak is `max(existing peak, −12.83 dBFS)`. Measured — the `Batch02_v2` render peaks **−9.06 dBFS with the toggle both off and on**, identical. The earlier continuous design took the worst case to +3.96 dBFS; that exposure is gone, and any doc still quoting it is stale.
  - **Verified by measurement, not inspection.** Filtergraph-level (never on the encoded file — the `under50mb_hevc` two-pass path is not deterministic run-to-run, which cost a wrong-looking frame hash once already). On `Batch02_v2`: video **240 frames, identical `framemd5` with the toggle off and on**, audio sample count identical (441001), **0 of 441001 zero sample-frames with tone on** (0 in the stem too) against a **25,725-frame run of true silence with it off**, and the bed's whole 9.4167 s reach differing by exactly **0.000e+00** — the only samples that changed are the 0.583 s round-up (all-zero 5 ms windows 116 → 0). The containment claim is the important one and needs a per-sample check, not a length check: on a synthetic 3-clip timeline (clip audio + holds + a silent source + slow-mo) the sound region `[0.5, 3.5)` is **bit-identical over 132,300 sample-frames**, and across a 10-shape matrix (`/tmp/rt/matrix.py`: no-audio source, holds, slow-mo, reversed, unaligned trim, bed shorter/longer/exactly covering) **not one sample-frame of tone landed over existing sound** and `filled == noise_fill_seconds(plan)` to <2 ms every time. Three-input `amix normalize=0` is still an exact unity sum (**3.73e-09** across 286,650 sample-frames). Stem equivalence by subtraction, `((V1+A1+tone) − V1plain) − A1stem`: **3.73e-09** with all three passes at exactly 286,650 sample-frames. The stem can still land a sample or two SHORT of the render where per-clip frame counts are odd (536549 vs 536551 on a 12.1667 s timeline) — **pre-existing, present identically with the toggle off**, so don't read it as a tone bug; the tail margin fixed the tone's own end, not this. The structural claim is checkable without rendering: generate the graph both ways and diff the chain list; with nothing to fill it is **byte-identical** to the toggle-off graph.
  - **Bed reach comes from the audio STREAM's duration, not the container's** — `get_video_info` now returns `audio_duration` alongside `video_duration` for this. A container's duration reflects its LONGEST stream, so a file whose video outruns its audio would be credited with sound it does not have and the tail would render silent with the toggle on. Falls back to the container duration when the stream reports none (and to `0.0` when there is no audio stream at all), so a file ffprobe is vague about degrades to the old behaviour rather than to "no coverage". Exercised against files where the two agree; **not yet measured against a file whose audio is genuinely shorter than its container**, which is the case to construct if this is ever suspect.
  - **Room tone is render-only — the preview cannot play it.** `AudioBedPlayer` emulates `BED_GAIN` and nothing else, and the asset is not even served to the browser (there is no `/assets` route). So the toggle is inaudible until Render, which is itself part of why it was reported as broken. If the A1 lane's amber "noise" labels ever need to be trusted, this is the caveat to state.
- **The server NEVER trusts client-supplied fps/has_audio/resolution** — `render_timeline` re-probes every input itself. Only inSec/outSec/holds/speed/reversed come from the request.
- `run_ffmpeg` prepends the binary and `-y` itself — args must NOT include `ffmpeg`, and outputs are force-overwritten. render_timeline uses timeout=1800 (vs default 600) because whole-timeline `-qp 0` renders run long.
- `/api/reverse` returns HTTP **200** (not an error) with `{warning, estimated_bytes}` when the estimated RAM (W×H×3×fps×duration) exceeds 2 GiB and `confirm` is absent — client must resend with `confirm: true`. ffmpeg's reverse filter buffers the whole video in memory.
- **`under50mb` is not a CRF or single-pass-ABR mode, deliberately.** CRF has no size guarantee at all (size follows content complexity). Single-pass ABR knows a target bitrate but routinely drifts several percent off it because it can't see the whole file's complexity in advance — not acceptable against a hard "always under 50MB" promise. `render_size_capped` runs a real two-pass encode (pass 1 → `/dev/null` via `-f null`, discovers per-frame complexity; pass 2 spends the byte budget against that map) and then **measures the actual output file size** and retries with a 15%-smaller bitrate (up to `max_attempts`) if it still overshot — the guarantee is enforced by checking the real file, never just trusted from the bitrate math. Every call site (`render_timeline`, `trim`, `splice`, `hold_frame`, `reverse`) needs the render's total duration to size the bitrate budget; `trim`'s `start`/`end` can be `HH:MM:SS.ms` timecodes (see the legacy UI's own placeholder), not just plain seconds — `_parse_time_to_sec` in app.py handles both. `render_size_capped` cleans up its own `<out_path>.ffpass*` two-pass log files in a `finally` block even on failure.
- **A filter-produced label consumed by more than one chain needs an explicit `split=N`.** ffmpeg auto-splits a raw *input* pad (`[0:v]` can feed several filters), but a *filter output* label (`[vsrc0]`, `[vov0]`) can only be consumed **once**. `build_timeline_filter` feeds its per-clip video source to up to three chains (lead hold, main body, trail hold), so it now emits `split=<n_consumers>` whenever that source is a filter label rather than `[i:v]`. **This was a latent pre-existing bug: crop + hold on the same clip had never rendered at all** — it died with `Input link in0:v0 parameters (size 1920x1080, SAR 1:1) do not match the corresponding output link in0:v0 parameters (512x512, SAR 1:1)`, exit 234 (confirmed against git HEAD). The overlay path inherited the same flaw but failed *silently* (30/135 frames composited, exit 0) because an overlay doesn't change frame size, so concat happily accepted the uncomposited frames. Verified after the fix: crop-only output is **byte-identical to the pre-fix version** across static crop / animated crop / single keyframe / no crop / reversed+speed+holds / multi-clip with `no_audio` both ways — the `split` only affects the two combinations that were already broken.
- **`overlay` silently CLIPS an out-of-range x/y; `crop` silently CLAMPS.** Opposite failure modes for the same class of bug, both exit 0 with no warning. A crop ramp running past the edge freezes against it (the pan just stops); an overlay ramp running past the edge loses the overflowing pixels entirely. Both mean keyframe bounds must be validated server-side before rendering — `render_timeline` checks every overlay keyframe's `x+w`/`y+h` against the *probed* source resolution, and its `t` against the clip's main-body window. Also relevant: `overlay`'s `eval` defaults to **frame** (per-frame expressions work without opting in) and `eof_action` defaults to **repeat** (which freezes the last overlay frame for the rest of the clip and extends the background to the foreground's length — a frame-COUNT change that reads as "not lossless" in a framemd5 diff). `eof_action=pass:repeatlast=0` is what stops compositing at the overlay's end without freezing or truncating.
- **`under50mb_hevc` (`render_size_capped(..., codec="hevc")`) uses genuinely different flags than the H.264 path, not just a swapped `-c:v`.** libx265 has no `-pass`/`-passlogfile` options at all (hand-verified) — two-pass is `-x265-params "pass=1:stats=<file>"` / `"pass=2:stats=<file>"` instead, producing stats files named `<file>` + `<file>.cutree` (vs. libx264's `<prefix>-0.log`/`-0.log.mbtree`) — `_PASSLOG_SUFFIXES` branches the `finally` cleanup on `codec` accordingly. `-maxrate`/`-bufsize` DO work identically as top-level flags for both codecs (verified via the encoded stream's own reported CPB properties) — no `vbv-maxrate=`/`vbv-bufsize=` workaround needed. 10-bit intermediate (`-profile:v main10` + `yuv420p10le`) needs its pixel-format conversion spliced into the caller's EXISTING `-vf`/`-filter_complex` value (`_inject_pixel_format`), never added as a second separate `-vf`/`-filter_complex` flag — ffmpeg silently lets a later duplicate flag on the same stream **replace** the earlier one (confirmed by hand: explicit "Multiple -filter/-af/-vf options specified for stream 0, only the last option will be used" warning), which would silently drop `reverse`'s own `-vf "reverse"` or an entire `-filter_complex` graph. The splice point for `-filter_complex` callers is the literal `[outv]` label every filter builder in this module terminates its video chain with.
- **The `custom` mode's two-pass render is a deliberate near-copy of `render_size_capped`, not a generalization of it.** `render_custom_two_pass` repeats the retry loop, the audio-bitrate floor and the passlog cleanup rather than parameterizing the original, because both `under50mb*` modes are hand-verified against frame hashes and measured output sizes — refactoring them to serve a configurable third mode would put that verification at risk for no user-visible gain. Only read-only pieces are shared (`_PASSLOG_SUFFIXES`, `_inject_pixel_format`). If a bug is found in one, check the other; they are meant to drift only where the spec says they should.
- **Three things about the custom mode's flags, all measured rather than assumed.** (1) `p010le` is NOT in `libx265 -h`'s or `libx264 -h`'s supported pixel-format list, but *requesting* it works — ffmpeg inserts the conversion and the encoded stream comes out `yuv420p10le`. It stays offered because it's the pixel format an Apple-ecosystem user is most likely to type. (2) Both codecs' `-profile:v` is a **free-form string**, not an enum ffmpeg validates against a list, so `EXPORT_PROFILES` is our allowlist and nothing else — an unlisted value would reach the encoder verbatim. (3) Output-only flags (`-movflags`, `-tag:v`) are **silently ignored by the null muxer**, which is why the user's extra args can be passed to pass 1 as well as pass 2; keeping the two passes' flags identical matters more than pruning the ones pass 1 can't use.
- **The custom mode's bitrate formula gives the WHOLE byte budget to video** — `(target_bytes × 8 × safety) ÷ duration ÷ 1000`, per spec, unlike `target_bitrate_for_size` which subtracts the audio bitrate first. So `safety` (default 0.90) is what has to cover both container overhead and the entire AAC track: a long render with high-bitrate source audio can overshoot the cap and go through the shrink-and-retry loop, and **each retry re-encodes both passes**. In the other direction, `maxrate` defaults to 0.95× the average, which makes VBV clamp the achieved rate near maxrate rather than the target — measured output with the defaults lands at **≈0.84–0.86 of the cap**, not 0.90. Both are worth knowing before "the file is smaller than I asked for" or "it encoded four times" reads as a bug.
- **Extra encode args are rejected structurally, not by character blocklist.** `validate_extra_encode_args` `shlex.split`s the text, then requires it to start with a flag, refuses a whole `ffmpeg` command, refuses anything in `_EXTRA_ARG_CONFLICTS` (the flags the dialog itself computes — `-c:v`, `-b:v`, `-pass`, `-vf`, `-preset`, …), and runs any path-looking token through `_media_path_ok` (the containment check extracted out of `validate_ffmpeg_command`, which now calls it too). There is deliberately no shell-metacharacter filter: `subprocess.run` is always given an argv list, so there is no shell to inject into, and a blocklist would only reject legitimate filter syntax.

## Frontend invariants

- **Hold placement invariant**: headHoldSec only on the first clip; tailHoldSec/roundHoldSec only on the last. `sanitizeHoldPlacement` (clipMath.js) zeroes violators and marks them dirty — every operation that reorders/adds/splits/deletes clips must run its result through it (all current ones do).
- **A stale mid-sequence hold is REACHABLE, and only the render's own first/last rule hides it.** `sanitizeHoldPlacement` runs on reorder/split/duplicate/delete but *not* on append — Raise the last clip, then add another clip, and the now-middle clip still carries `roundHoldSec > 0` until something else sanitizes. Nothing shows because `render_timeline` applies the same rule server-side (`lead_hold` only `if is_first`, `trail_hold` only `if is_last`), so the joined render ignores it. **That safety net inverts in a 1+ shot render**, where each clip is rendered as its own one-clip timeline and is therefore both first and last: the stale hold would suddenly render and that shot would come out longer than the stretch of the joined render it stands for. `App.renderShots` zeroes head holds off every shot but the first and tail/round holds off every shot but the last for exactly this reason — measured: a stale 0.5s round hold on clip 2 gave a 1.5s shot against the joined render's 1.0s stretch before the guard. Don't "simplify" it away as redundant with `sanitizeHoldPlacement`. **`analyzeMath.sequencePieces` (V2 Batch Analyzer) is the third place this rule has to be applied by hand**, and there for the mirror-image reason: it derives where the cuts landed in a file the render already wrote, so a stale hold it trusted would both invent a cut in the middle of real footage and push every later cut point past the frame it belongs on. Any new code that reasons about a clip's *rendered* length owes the same first/last treatment.
- **`useUndoableTracks` keeps `{present, past, tag}` in ONE state object** for React StrictMode safety: double-invoked updaters produce identical results instead of double history pushes. Don't split into two useStates. The three tracks are named slices of `present` for the same reason plus one more — a history entry has to snapshot V1, V2 and A1 *together*, or interleaved edits produce an entry that half-applies.
- **There is exactly ONE undo history, shared by V1, V2 and A1 — do not add per-track stacks.** Undo is a single button and a single Cmd/Ctrl+Z, so it must mean "step back my last edit, wherever it was"; per-track stacks make the same keystroke do different things depending on which lane was last focused. ANIM has no slice of its own — crop keyframes live on clips, so they ride whichever list `CropOverlay` writes to (undoable on V1 *and* V2). V2 was deliberately outside the history for a long time (rationale: it's rebuilt from a rule by Analyze/Reconstruct, not hand-edited). **That reasoning was wrong in practice** and is worth remembering as a bug class: the shared toolbar makes V2 hand-editable with the same nine tools as V1, so a track that accepts edits but silently ignores Cmd/Ctrl+Z is worse than one with no tools. If you add a fourth editable lane, give it a slice — don't reintroduce plain `useState`.
- **A pointer drag must push ONE history entry, not one per pointermove.** Edge-drag trims (`TimelineClip.handleEdgeDrag`) and crop-box drags (`CropOverlay`) update state per mouse sample; unguarded, one drag pushed dozens of entries and shoved everything else off the 50-entry stack, so undo cost one press per mouse sample *and* the edit before the drag was gone. Each gesture mints a token with `nextGesture(label)` at pointer-down and passes `{coalesce: token}` on every update; a token matching the entry already on top folds into it. Tokens must be unique per gesture (hence the module counter, not a per-clip id) or two successive drags of the same edge would merge. `undo` clears `tag` so a resumed token can't fold into a just-popped entry. **Any new drag handler that mutates clips needs this** — verified as of this change that the only other pointermove handlers are `Playhead.jsx` (seeks, no clip mutation) and App.jsx's panel resize.
- **A single user action must not write two lanes non-silently** — with one shared history that costs two entries, so Cmd/Ctrl+Z leaves the action half-undone. Audited as of this change: the only handler touching two slices is `handleRenderConfirm`, and all four of its writes are the `{silent: true}` dirty-flag clears, so it costs nothing. If you ever need a genuine two-lane edit, coalesce both writes under one `nextGesture` token.
- **Bookkeeping the user didn't perform must be written with `{silent: true}`.** The three post-render `dirty`-flag clears in App.jsx are the case that matters: without `silent`, the first Cmd/Ctrl+Z after every render just re-dirtied the clips instead of undoing the last real edit. Same rule for anything else the app changes on its own behalf.
- **Project-open and `handleCleared` `reset()` the history rather than pushing to it** — undoing across either would restore clips pointing at media that is gone or belongs to another project. `handleCleared` clears V1, V2 **and** A1 (A1's beds used to survive it, which left the timeline referencing `input/` files that had just been deleted).
- **Playhead/transport/ruler are ALWAYS driven by V1**, even when V2 is displayed on top. `handlePlaybackSelectClip` only syncs V1's selection when the playing clip is actually in V1's list. `focusedTrack` (lifted to App.jsx, not local to Timeline.jsx) now does double duty: it still routes the Delete/Backspace key to the right track (Timeline.jsx), AND it's what the shared toolbar row in App.jsx (`activeClips`/`setActiveClips`/`activeSelectedClip`/`setActiveSelectedId`) reads to decide which track's clips the Trim/Hold/Reverse/Speed/Crop/Duplicate/Splice/Raise controls act on. Selecting a clip on either track sets `focusedTrack` as a side effect (`handleSelect`/`handleSelect2` in Timeline.jsx); the toolbar has no separate "which track" control of its own.
- **Playback is a rAF scrub loop** setting `videoRef.currentTime` each tick — the `<video>` never natively plays during timeline playback, so **the clips' own audio does not play in preview**. The one exception is the **A1 bed**, which is a separate `<audio>` element that really does play, slaved to `transport.getTimelinePos()` (`AudioBedPlayer`) — that's why it's timeline-locked and survives mid-sequence holds/reverse/slow-mo. The one offset it honors is V1's picture start: source time is `timelinePos - startSec`, and while that's negative (inside the first clip's head hold) the element parks paused at 0, matching the render's leading silence. It mounts inside the Timeline subtree, so it goes silent on the AGENT/Reformat/Actions tabs. `displayClips` is read via a ref so mid-playback visibility toggles apply next frame; any change to V1's clip array stops playback.
- **Never animate from `MediaContext.currentTime`** — it comes from `timeupdate`, which fires at ~4 Hz. Anything that has to track the playhead smoothly (overlay preview, the A1 bed player) needs its own rAF loop reading the transport directly.
- **A frame grab must crop to `activePreview.info`'s size, not to `videoWidth`/`videoHeight`** — the same trap `PreviewPlayer`'s clip-path exists for. Some encoders pad the coded picture out to the next 16px macroblock boundary without signaling a crop, and the browser reports those padded dimensions, so a naive `drawImage(video, 0, 0)` bakes the fringe the preview hides into the PNG. `FrameGrabButtons.grabCanvas` therefore draws the source rect `(0, 0, trueW, trueH)`, capped at the coded size. Verified live in headless Chrome against the dev server (`002_0120.mp4`, coded 2206×946): the offset draw produced the expected 2198×938 canvas, `getImageData` read back fine (**never tainted** — every source is same-origin through the Vite proxy), and `toBlob` yielded a 1.1 MB `image/png`. Two other measured details: the clipboard path must hand `ClipboardItem` the **`toBlob` promise, not an awaited blob** (WebKit only honors `clipboard.write` inside the click's own turn, and both engines accept `Promise<Blob>`), and the download's object URL must be revoked on a timeout rather than synchronously or WebKit can cancel the download mid-read. What the capture does NOT include: V2 overlay layers and the crop box, which are sibling DOM elements over the `<video>`, not pixels in it.
- **CLIP_PALETTE class names must stay literal strings** (comment at clipMath.js) — Tailwind v4's scanner can't generate template-interpolated classes like `` `from-${c}-700` ``.
- **Speed math has two directions**: `clipMainSec` DIVIDES by speed (timeline length stretches when slowed); TimelineClip edge-drag MULTIPLIES the pixel delta by speed (screen pixels are timeline seconds; a slowed clip covers less source time per pixel).
- **Timeline pixel constants must stay in sync**: `GUTTER_PX=48` ↔ the `w-12` gutter, `GAP=2` ↔ `gap-0.5`, Ruler adds `clips.length*2`. Changing lane spacing requires updating `playheadPx` and `clientXToTimelinePos` together.
- **`sequenceSec * pps` is NOT the width of the V1 lane** — anything that must sit under V1 has to be measured with `sequencePosToPx`/`sequenceClipBounds` (clipMath.js) instead. V1's clips are a `gap-0.5` flex row, so the lane is wider than `duration * pps` by 2px per clip boundary, and `TimelineClip` additionally floors each clip's box at `MIN_CLIP_PX = 24` so a sub-0.4s clip is drawn wider than its duration. A single continuous span therefore drifts left of the picture, accumulating per clip — which is exactly how the A1 bed came to not sit under the frame it plays with. Head/tail holds need no special case in that math (they're already inside `clipTotalSec`), but a floored clip's *interior* must be scaled by its rendered width, not by `pps`. Kept deliberately separate from `timelinePosToPx`, which drives the playhead and ignores the floor — don't merge them without re-verifying the playhead against the clips.
- Deleting or reordering ANY clip marks ALL remaining clips dirty — the rendered sequence changed even though individual clips didn't.
- Keyboard shortcuts are suppressed when focus is in an INPUT/TEXTAREA; Delete removes the selected *part* (hold segment) rather than the clip when a hold is selected.
- OutputPanel auto-loads the newest output when `files.length` changes (deliberately `files.length`, not `files` — eslint-disabled).
- **The V2 action buttons are labeled "V2 Analyzer" and "V2 Reconstruct"** (Timeline.jsx `actionsBar` + AboutDialog's numbered list) — renamed from the old "Analize" (sic) / "Reconstruct". The prop and handler names did NOT change (`onAnalyze`/`handleAnalyze`, `onReconstruct`/`handleReconstruct`), and neither did the feature's name in prose ("Analyze & Reconstruct"), so grep for the label text, not the identifiers, and change both copy sites together.
- **Never animate anything from `MediaContext.currentTime`.** It's fed by the `<video>`'s `timeupdate` event, which is throttled to **~4Hz** — hand-measured at 3.76Hz (Chromium 151, a near-perfect 265.6ms metronome), 3.99Hz (WebKit 26.5), 3.82Hz (Firefox 153, max gap 290ms). A crop box panning 400px over 4s therefore teleports in **~26.6px jumps** and can only ever occupy 15 of the 400 columns it crosses — this was the actual cause of juddery crop-keyframe motion. `CropOverlay`'s animated box now reposition itself from a **rAF loop reading `video.currentTime`** (measured 60.00Hz on a 60Hz display, 120Hz on ProMotion → 1.67px steps, ~16× smoother), writing `style.left/top` imperatively like `Timeline.positionPlayhead` does. Two non-obvious requirements: the loop must write **unconditionally every frame** (React still re-renders at timeupdate's 4Hz and puts the stale `displayX` back into `style.left`, so memoizing "unchanged" samples reintroduces the judder), and it must suspend while a pointer drag owns the box (`draggingRef`) or the loop and the cursor fight over position. `requestVideoFrameCallback` is the wrong tool here (capped at the source frame rate — 30Hz, 3.33px steps, and only 23.6Hz in Firefox); the box is CSS-composited, so it should move at display rate, not decode rate.
- **Crop keyframe `t` is relative to `inSec`, so every trim must rebase it** via `cropAnimation.retimeKeyframesForTrim` (wired into `Timeline.handleTrim`/`handleTrim2` and `TrimForm.apply`/`reset`). Without it a trim silently slides the pan onto different frames, and — worse — leaves keyframes past the shortened body, which `app.py` bounds-checks and **rejects the whole render** for (the edit looks fine until Render fails). Keyframes falling outside the new window are replaced by a single one at the boundary carrying the curve's own interpolated value there, so the retained span of the pan survives exactly. It returns the same array identity when nothing moves, so callers don't set a needless dirty flag.
- **A crop resize must clamp against the FURTHEST keyframe, not the visible one.** One box size is shared by every keyframe (by design), so growing the box while parked on a keyframe near x=0 can push a later keyframe past the frame edge — same render-rejection failure as above. `CropOverlay.handleResizeDown` caps the drag using `cropAnimation.maxKeyframeOrigin`.
- **ffmpeg's `crop` filter silently clamps an out-of-range `x`/`y` — exit 0, no warning at any loglevel** (verified to `-v debug`). A ramp that runs past `in_w - out_w` just freezes hard at the edge. So keyframe range must be validated *before* render; no ffmpeg diagnostic will ever tell you. Contrast the *other* failure mode: an unbalanced-paren expression is a HARD failure (exit 234, `[Eval] Missing ')'`, zero output) — since these ladders are generated programmatically, a value bug fails silently while a syntax bug fails loudly. Also verified: `crop` re-evaluates `x`/`y` per frame (not stepped), nested `if(lt(t,...))` ladders parse correctly to at least 64 levels / ~2.5KB, and **yuv420p floors `x`/`y` to even** (`lrint(expr) & ~1`) so odd offsets are unreachable — `exact=1` restores 1px granularity, at a quality cost, and the project does not currently pass it.
- **V2-as-overlay REPLACES the composite decision, so `displayClips` must not swap tracks.** Normally `Timeline.displayClips` makes a visible V2 *replace* V1 in the shared `<video>`. When `overlayMatch` resolves any pair to an overlay, that's wrong twice over: the shared element must keep decoding V1 (there'd be nothing to composite onto otherwise), and the V2 picture is drawn over it by `OverlayPreview`'s own second `<video>` element instead. One `<video>` decodes one file, so a true composite needs two elements — the overlay follows the main one's clock (`play()`/`pause()` mirrored, `currentTime` nudged only when it drifts >0.12s during playback so it isn't the choppy per-frame-seek scrub path), and hides outside its own range to mirror `eof_action=pass`. `v1Visible`/`v2Visible` are lifted to App.jsx (like `focusedTrack`) so the overlay layer honors the same eye toggles as the lane.
- **The overlay preview and the render must share the sampling math, not merely agree.** `OverlayPreview` positions its PiP with `cropAnimation.sampleCropOrigin` and `box.width / sourceWidth` — deliberately the same function and the same scale factor `CropOverlay` uses for the crop box, since the overlay has to land exactly where that box was drawn. Verified against real renders: preview samples matched the positions ffmpeg actually produced at every checked time (100/450/800/1150/1480 px), within the sub-pixel difference from yuv420p's even-value floor.
- **A/B mode renders from a DIFFERENT match than the preview shows, and that's intentional.** App.jsx derives two sets from the same clips: `overlays = matchOverlays(v1, v2)` drives the live preview, and `abOverlays = matchOverlays(v1, v2, { fullFrameSameSize: true })` is used only by an A/B render. They differ in exactly one case — a V2 clip whose resolution *equals* V1's. The preview keeps its long-standing full-frame-replacement behavior there (swap tracks, no compositing), while A/B treats it as an overlay at 0,0 covering the frame, because that's what "render V2 over V1" means for two same-size clips. So a same-size A/B render is not previewed as a composite; it doesn't need to be, since the result is pixel-identical to the V2 clip alone (verified bit-exact, 72/72 frames). Don't "fix" this by pointing the preview at `abOverlays` — that would make a visible same-size V2 stop replacing V1 in the preview, breaking Analyze/Reconstruct round-trips, which are the common case.
- **A 1+ shot series equals the joined render frame for frame — but only because the shots share a size.** Verified: 4 shots (head hold, reverse, 0.5× slow-down, tail+round hold) laid end to end matched the single joined render on **180/180 framemd5 hashes**, audio durations summing exactly (1.5+1.0+2.0+1.5 = 6.0s). The equality holds because `render_timeline` derives `target_w/h/fps` **per render**, so a track whose clips differ in size deliberately renders differently split than joined: measured, a 160×120 cropped clip renders 160×120 as its own shot and 320×240 (padded) when joined to a 320×240 clip. That's the intended reading of "unique shots" and it's stated in the render dialog — don't try to make the split match the joined render's frame by forcing a target size onto each pass, and don't claim byte-equality for a mixed-size track. Two more per-file consequences: a size-capped quality mode budgets **each shot** under the cap (N files, N budgets), and each shot's audio gets its own AAC frame boundaries (packet counts sum to 261 vs the joined 259 — encoder padding at each split, not drift).
- **Renaming a file is REFUSED while the timeline points at it, on purpose — in BOTH bins.** A clip resolves its media by filename (`sourceName` + `sourceDir`), so renaming a file any V1/V2 clip — or the A1 bed — references would orphan it, and the only symptom would be an ffmpeg failure at Render. That includes **Export Bin** files: a chat edit or Reformat re-points the selected clip at the render it just produced (`sourceDir: 'output'`). `App.jsx` derives both sets from one `inUseNamesFor(dir)` helper — `inUseSourceNames` for `MediaLibrary`, `inUseOutputNames` for `OutputPanel` — kept separate because a same-named file in the other folder is not the same file. Each panel's `handleRename` blocks on its own set rather than rewriting `sourceName` across the clip list: a silent relink would leave every undo step behind it pointing at the old, now-nonexistent name. Two per-file states are keyed by filename and therefore have to be carried over by hand on a successful rename — the ★ (`fileList.renameFavorite`, called by whichever panel owns that `favorites` state) and, input side only, the sticky V1/V2/A1 track tag (`fileList.renameTrackTag`, owned by App via `MediaLibrary`'s `onRenamed`). Still unavoidably broken by a rename: a **saved `.nara` project** that used the old name; nothing in the client knows which projects reference which files.
- **Chat edits only reach the timeline via `handleEditResult`'s clip-swap** (App.jsx): `/api/execute` reports which file its command actually wrote (`_output_arg_info` in app.py, parsed from the validated argv's output path — never guessed), and if a clip is selected, `App.jsx` reprobes that file and replaces the selected clip's source/dimensions in place, resetting trim/hold/reverse/speed/crop (the chat edit is now baked into new pixels, same treatment Reconstruct gives a "fresh" source). Before this, a Run only ever produced a new file in Exports with zero effect on the clip being edited — don't regress this by having `onResult` go back to a no-arg `refresh()`-only callback.

## Security / safety model

- `validate_ffmpeg_command` applies **NO character blocklist deliberately**: subprocess always gets argv lists (never `shell=True`) so `;`, `()`, `$` are inert, and filter_complex legitimately needs them. Safety = first token must be `ffmpeg` (binary path force-replaced), every `-i` path and the output must realpath-resolve inside `input/` or `output/`. Do not "harden" it with character filters.
- `safe_path` rejects absolute paths and traversal via realpath+commonpath; `GET /input/<name>` and `/output/<name>` skip it and rely on `send_from_directory`'s own protection.
- `input/` is sacrosanct — never modify or delete a file's *contents* there programmatically. `/api/clear_input` and `DELETE /api/files/<name>` (both user-confirmed) are the only sanctioned deletion paths, and `/api/rename_file` with `dir="input"` (the Media Bin's right-click Rename) the only sanctioned write: it renames, so the bytes are still untouched. Everything else reads.

## Environment quirks

- **Binary paths resolve at import time, with Apple Silicon winning.** `ffmpeg_utils._tool()` returns `/opt/homebrew/bin/<name>` when it exists and otherwise `shutil.which(name)`; `CLAUDE_BIN` (app.py) is `shutil.which("claude")` with `~/.toolbox/bin/claude` as fallback. Consequence: on a non-`/opt/homebrew` machine the app inherits the PATH of the shell that launched Flask, so a backend started without `brew shellenv` can fail to find ffmpeg while your own shell finds it fine. Don't reintroduce bare `"ffmpeg"` strings — the explicit brew path is what keeps a stray conda/system build from winning here. `browse_directory`/`reveal_file` are macOS-only (osascript / `open -R`).
- **Export-dir inconsistency to know before touching**: only `/api/render_timeline` writes to the user-configured export dir (`get_output_dir()`); trim/splice/hold_frame/reverse hardcode `fu.OUTPUT_DIR`, and `unique_output_name` only checks `fu.OUTPUT_DIR`. `/api/probe?dir=output` also uses `fu.OUTPUT_DIR` while render clips with `dir=='output'` resolve against `get_output_dir()`.
- **Two extension tuples, and the difference matters.** `ALLOWED_EXTENSIONS` is still video-only (.mp4 .mov .mkv .avi .m4v .webm) and gates anywhere a *video* is required (timeline clip, overlay source). `MEDIA_EXTENSIONS = ALLOWED_EXTENSIONS + AUDIO_EXTENSIONS` (+ .wav .mp3 .m4a .aac .flac .aiff) gates the seven file-management sites in `app.py` — `_list_dir` (serving both `/api/files` and `/api/outputs`), `upload`, `clear_input`, `delete_input_file`, `rename_file`, `clear_output`, `delete_output_file` — so an audio bed can be uploaded, listed, and deleted through the normal UI. Image uploads are still rejected. Note `/api/probe` has **no** extension gate at all. **`clear_input` and `delete_input_file` are destructive and now sweep audio files too** — intended (an audio file in `input/` must be deletable the same way), but don't widen either further without saying so out loud.
- Version spread: Python 3.9.6 venv (macOS CommandLineTools) vs bleeding-edge Vite 8 / React 19 / Tailwind 4. Lint is oxlint, not eslint.
- In shell commands, `ffmpeg`/`ffprobe`/`node` are NOT on PATH by default in this environment — run `eval "$(/opt/homebrew/bin/brew shellenv)"` first, and note the working directory resets between some invocations (cd explicitly; `npx vite build` fails with UNRESOLVED_ENTRY if run from the repo root instead of `frontend/`).
- `.export_settings.json` is **global mutable state** — a render's quality mode is whatever it holds at that moment. Parallel test renders can race each other's quality settings (bit-exact hash checks then fail mysteriously); pin it to `lossless` before hash-verification renders. It is also **the user's live configuration**, not scratch space: back it up (`cp` to `/tmp`) before writing test values into it, and restore it when done. `POST /api/export_settings` is a partial update precisely so one writer can't clobber another's keys — keep it that way if you add a field.
