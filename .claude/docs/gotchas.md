# Gotchas

Non-obvious pitfalls and invariants. Most were discovered by hand-testing; several are encoded in load-bearing comments in the code.

## Encoding

- **`-qp 0`, never `-crf 0`, for lossless.** Hand-verified on this Homebrew libx264 build: `-crf 0` does NOT round-trip bit-exact for 10-bit (yuv420p10le) sources — only `-qp 0` does. `-crf 0` is the commonly-cited flag online but only holds for 8-bit. Documented in `encode_args`' docstring. Lossless always emits the High 4:4:4 Predictive profile and typically costs 2–3× the size of an already-lossy source.
- **Speed default parsing deliberately avoids `or`**: `raw_speed = c.get('speed'); speed = 1.0 if raw_speed is None else float(raw_speed)` in `render_timeline`. Using `c.get('speed') or 1.0` coerces a literal `0` to the default and silently skips the `(0, MAX_SPEED]` range check — this was a real bug caught in verification.
- **`speed > 1` is legal and exact.** Both render routes accept `(0, MAX_SPEED]` where `MAX_SPEED = 10.0` (was `(0, 1]` before 0.27.0). Two producers: **V2 Reconstruct**, which emits the reciprocal of a V1 slow-down so a shot stretched from 24 frames to 48 comes back at 24, and — since 0.61.0 — the **Speed control**, which offers the first two of those reciprocals as ordinary presets (`SLOW_SPEEDS.slice(0, 2).map(s => 1/s)` in `SpeedForm.jsx`: 133% and 200%). Reciprocals rather than round numbers is the load-bearing choice: it makes 50%-then-200% an exact round trip and keeps `1 / 0.75` in the preset list identical to the double Reconstruct computes. **2.5×/4×/5× are deliberately NOT on the menu** (offered in 0.61.0 development, removed by request before release) — the routes still accept them and Reconstruct still emits them for a 0.4×/0.25×/0.2× V1 slow-down, so `SpeedForm`'s not-a-preset branch is the normal path for a reconstructed clip, not an edge case. Don't "tidy" that branch away, and don't infer the render's ceiling from the menu. Four facts worth not re-deriving:
  - **It is exact, not an approximation.** Speed is a pure PTS change (`setpts=(1/speed)*PTS`); below 1 the fps normalization *repeats* frames, above 1 it *drops* them. A stretch only ever duplicates, so the compression only ever drops duplicates. Verified out-and-back at every preset — `0.75→32f→1.333×`, `0.5→48f→2×`, `0.4→60f→2.5×`, `0.25→96f→4×`, `0.2→120f→5×` — all **24/24 frames byte-identical**, non-integer reciprocals included. And end to end through the real pipeline: a mixed-speed 3-shot V1 render (24 + 48 + 24 frames) reconstructed and re-rendered came back **72/72 frames byte-identical to the original source**, with 24 distinct frames in the middle shot.
  - **The ceiling is derived, not picked.** The 12 fps effective-rate floor bounds how slow a clip may be (`speed >= 12/clip_fps`), so the fastest un-stretch anyone can need is `clip_fps/12` — 10× at 120 fps, less for anything slower. `MAX_RESTORE_SPEED` in `analyzeMath.js` mirrors it so Reconstruct never emits a clip the render would 400 on at press time, long after the user could connect cause to effect.
  - **A speed-up's sampling phase is offset by up to half a step, and that is not a bug.** Measured lossless on a 24 fps source, a 48-frame window: `2×` gives 24 frames that are source frames 1, 3, 5, … (byte-identical to every 2nd frame of the same window at `1×`), but `4×` gives 12 frames that are source frames **2, 6, 10, …** — an even stride of 4 starting one frame in, because `fps=` picks the frame nearest each output tick and at 4× the first tick's nearest neighbour isn't frame 1. Even stride, every frame distinct, every frame present in the source, nothing invented. Don't "correct" the phase; it would break the `0.5×`/`2×` byte-identity above, which is the property that actually matters.
  - **The 12 fps floor must stay on the slow side only.** It is a picture-quality rule about frames held too long; a speed-up raises the effective rate, so applying the floor to it would reject the only thing speed > 1 is for.
  - **A retime renders SILENT in both directions**, so un-stretching cannot restore audio a slow-down dropped — there was none in the file. Don't "fix" that by unmuting the compressed body.
  - **`clipMath`'s frame mirror already agrees above 1×** — no arithmetic change was needed. Checked against real `clip_timing` + `n_norm_frames` over 1500 sequences / 5216 clips (4525 of them above 1×): **0 frame-count mismatches, 0 `targetFps` disagreements.**
- **A render shorter than ~0.4s fails outright in the 2-pass size-capped quality mode** — pre-existing, hand-reproduced on 2026-08-24, NOT fixed. `target_bitrate_for_size` divides the whole byte budget by the output duration, so a very short render asks for an enormous bitrate and `-bufsize` (`video_rate * 2`) overflows the encoder's int32: `Value 3086815744.000000 for parameter 'bufsize' out of range`, then `Error opening output file /dev/null` on the analysis pass. Reproduced through the live route with a 24 fps source: a **0.25s** output fails, a **0.5s** output succeeds, at `speed: 1` either way — so this is about output LENGTH, not retiming. Worth knowing here because Reconstruct's un-stretch *shortens* a render (a 0.5s shot slowed to 0.5× and then restored is 0.25s again), so it reaches this ceiling more easily than a slow-down ever did. The fix is a clamp on `-maxrate`/`-bufsize`, but it changes encode args, so it needs the **verify-render** procedure rather than a drive-by edit.
- **The fps filter needs a hard frame cap**: `fps=target_fps` can emit one spurious duplicate frame at EOF (concat graph runs in 1/1000000 timebase; an end timestamp landing exactly on a frame tick rounds into an extra frame). Every per-clip chain is capped with `trim=start_frame=0:end_frame=<n_norm_frames>` and audio padded/cut to the identical duration — otherwise every clip boundary drifts 1/fps out of sync.
  - **"The identical duration" means `n_norm_frames / target_fps`, and the ambiguity there hid a real drift bug until 0.30.0.** `clip_timing` counts frames on the SOURCE clip's fps; the render re-quantizes to `target_fps` (`max` of the clips' rates) and caps at `n_norm_frames`. Those two lengths differ whenever a clip's fps isn't `target_fps`, or a speed lands the stretched body between output frames — and the audio used to be padded to `clip_timing`'s seconds while the video was capped at the frame count. Because **`concat` advances its per-segment offset by the LONGEST stream**, an audio overhang of a fraction of a frame pushed every later cut further out of position and made the output VFR. Measured on 20 clips alternating 24/30 fps at `target_fps=30`: `avg_frame_rate=1525/51` instead of `30/1`, duration `20.400` against the video's own `610/30 = 20.333`, last cut **2 frames** past where `analyzeMath.sequenceCutOffsets` predicts it (so V2 Batch Analyze and Reconstruct cut on the wrong frame); 12 clips at 0.75× on 24 fps footage ran `16.667` against `396/24 = 16.500`, **4 frames** out. Across 144 fps/trim/speed/target combinations the audio was too LONG in 50 and too SHORT in 45 (a silent hole of up to 20.8 ms at each clip's tail) — only 49 were already aligned, which is why single-source-fps 1× timelines never showed it. `quantized_timing()` is now the one place that arithmetic lives, and everything measuring itself against the picture reads it: the per-clip audio pad, the A1 bed, room tone's plan, and `build_a1_filter` (which is why that function takes `target_fps` — a stem quantized on a different grid than its render is the same bug wearing a different hat; it was up to 100 ms off). Video frame hashes are unaffected in every case: no `no_audio` graph changed by one character.
- **Not every container records its own duration, and a missing one used to read as a confident `0.0`.** `format.duration` is simply absent from anything the muxer couldn't seek back into — `ffmpeg -i x.mp4 -c copy -f matroska pipe:1 > y.mkv` reproduces it exactly — and a truncated file can report `0`. `get_video_info` therefore returns **`duration_known`** alongside `duration` (which still reports `0.0`, because most callers only display it). Only the three routes that do *arithmetic* with it gate on the flag: `render_timeline`, `render_a1` and `hold_frame` 400 with "cannot read the duration of X". **`trim` and `reverse` deliberately do not** — they hand `-ss`/`-to` or `reverse` to ffmpeg, which reads the stream itself, and both are measured working on such a file (frame-for-frame identical before and after the flag was added). So don't "finish the job" by raising from `get_video_info`: that removes two working operations to improve a message. Note the Media Bin still shows these files as `0:00` — `/api/probe` returns the flag but no frontend reads it yet.
- **`out_sec` is clamped to `video_duration`** (both in `render_timeline` and `build_timeline_filter`): the frontend's historical default outSec was the container duration, which can outlast the last video frame when audio runs longer. Without the clamp, a one-frame freeze window sampled past the last real frame selects ZERO frames — the freeze silently vanishes from video while its anullsrc silence still lands in audio, desyncing everything after it.
- **Hold sampling under reversal is flipped**: after reverse, the frame that plays FIRST is the one originally at outSec — so the lead hold samples outSec and the trail hold samples inSec. A hold must freeze the frame adjacent to it in *final playback order*.
- **A hold's `anullsrc` silence must be quantized to the same frame grid the freeze is** — `lead_frames / fps`, never the raw `lead_hold_sec` off the request. That silence IS the mechanism that offsets the clip's own audio (it's concatenated ahead of `[amain{i}]` in the same order the freeze is prepended to the video), so if the two lengths disagree the whole clip's dialogue lands late against its picture. The freeze always emits a whole number of frames (`loop=round(H*fps)-1`), so any hold that isn't a frame multiple used to desync: measured at 24fps with a 0.51 s hold (which quantizes to 12 frames = 0.500 s), the audio ran **exactly 441 samples = 10.00 ms late**, and because the per-clip `apad`/`atrim` then cut back to `expected_sec` (itself computed from `lead_frames`), the same 441 samples of **real audio were silently dropped off the tail**. Both confirmed by sample-aligning the render against its source (residual 2.4e-05 = the s16le quantization step). The fix is audio-only: video frame hashes are byte-identical either way, and for frame-multiple holds the emitted graph is textually unchanged. Verify hold/audio alignment with a *non-periodic* marker — a sine tone is invisible to a shift that's a whole number of its periods (441 samples is exactly 10 cycles of 1 kHz at 44.1 kHz, which is how this nearly went unnoticed).
- **Referencing `[0:a]` on a source with no audio stream kills the WHOLE filtergraph, picture included** — not just the audio half, and not with a warning. ffmpeg answers `Stream specifier ':a' in filtergraph description ... matches no streams` / `Error binding filtergraph inputs/outputs: Invalid argument` and encodes nothing, so a graph that reaches for absent audio is a total failure rather than a degraded one. This is what made `/api/hold_frame` fail on **27 of this machine's 30 videos** until 0.38.0 (finding #17), in all 5 quality modes, and the reported reason was ffmpeg's own **version banner** because the route surfaces `stderr[-4000:]`. Two rules follow. (1) Any builder that touches input audio takes the probed `has_audio` as a **required** argument — `build_holdframe_filter(t, dur, fps, has_audio)`, like `build_concat_filter`'s `has_audio_flags` — so the next caller cannot inherit a wrong default; verified that a 3-arg call raises `TypeError`. (2) Three things must agree or the render fails anyway: the graph's terminal labels, the route's `-map` list, and the `has_audio` handed to `encode_args` (which emits `-an` via `audio_args` when false). **Single-source routes preserve the source's stream layout** (`trim`, `reverse`, and now `hold_frame`: a silent input gives a silent output); **`splice` is the deliberate exception** because `concat` requires every input to present the same streams, which is why `build_concat_filter` synthesizes a per-input `anullsrc`. Note the hold's *own* `anullsrc` silence is a different thing and stays — it only exists when there is real audio to interrupt. Verified at argv level: for an audio-bearing source the command is byte-identical across all 5 quality modes before and after the fix.
- **A hold drops the one source frame on its `t_end` boundary** — a 2 s / 25 fps source with a 0.5 s hold yields **61** frames where the arithmetic says 62, because the frame at `t_end` satisfies neither `trim=end=t` nor `trim=start=t_end`. Pre-existing and deliberately untouched by 0.38.0 (the video half of that graph is byte-identical before and after), but know it before treating a hold's output being one frame short of `source + duration` as a new defect.
- **Delay the A1 bed with `adelay`, not a PTS shift** — the bed is offset to V1's picture start by `adelay=delays=<ms>:all=1`, and the *prepends-silence* semantics are what make it safe: the downstream `apad=whole_dur=N`/`atrim=end=N` still measure from 0, so a 1 s head hold yields 1 s of leading silence and 1 s **less bed heard**, never a render 1 s longer. An `asetpts`-style shift would push the bed's end past `N` and either stretch the output or get truncated unpredictably. `all=1` is mandatory: without it `adelay` only shifts the channels it was given explicit delays for, so a stereo bed comes out with one channel early. The offset is frame-quantized (`lead_frames / fps`) so it lands on the same grid as the freeze. Verified by the difference identity `(with-bed)[i] - (no-bed)[i] == BED_GAIN * bed[i - off]` across hold ∈ {0, 0.5, 1.0, 0.51, 2.0} (max err 4.3e-05 = the s16le step), with **zero** bed contribution during the hold (0.00e+00) and output length always exactly `hold + sequence`. A zero head hold emits no `adelay` node at all, so the no-hold graph is provably unchanged.
- **`concat` negotiates its output format from its FIRST input, so every audio piece must be `aformat`-ed as it is created** — not just once after the concat. The per-clip audio pieces are gap/main/gap in playback order, so *which* piece lands first depends on which holds exist. With a **trail-only** gap the first input is the raw source pad `[i:a]`, and a mono/48 kHz source made concat negotiate mono: the stereo noise fill that followed was silently **downmixed, measured -4.4 dB** (rms 0.007089 vs the asset's own 0.011854), and the post-concat `aformat` then upmixed the already-collapsed signal back to stereo. The same clip *with a lead hold* was full level, because that put an already-`aformat`-ed gap first — the bug's presence depended on hold layout, not on the gap being filled. **Pure silence hid this indefinitely: a downmixed silence is still silence**, which is why it only surfaced with noise fill — and note that detector is now GONE: gaps are always `anullsrc` regardless of the toggle (room tone is a separate summed track, never a concat piece), so nothing in the concat pieces would reveal a re-broken negotiation. The `aformat` on `[amain{i}]` has to be kept on the strength of this entry, not re-derived from a symptom. Fix is one `aformat` on the `[amain{i}]` chain, making negotiation independent of piece ORDER. Cost is bounded and is the *better* resample (convert once before concat, rather than after a downmix): for a source needing conversion, **28 samples (0.3 ms) differ at the concat seam, max 5/32768 ≈ -76 dBFS**; for a source already stereo/44.1 kHz the render is **byte-identical**, and a clip with no gap at all (one audio piece, no concat) is byte-identical either way. Video frame hashes unaffected in all cases.
- **Room tone fills the MEASURED silence and nothing else — and BOTH designs it replaced are worth remembering as classes of bug.** `noise_fill_plan()` walks the same per-clip audio pieces `build_timeline_filter` emits (`clip_audio_pieces()`: lead gap, body, trail gap, and the sub-frame slack piece), marks each `(has_sound, duration)`, then carves out the spans the A1 track's own audio actually covers (`bed_spans()`, one per bed, each from the `audio_duration` probe field). `noise_track()` renders the complement as ONE bounded full-length stream — per-clip segments concatenated — summed as one ordinary `amix` input. Gaps themselves stay plain `anullsrc`. **Bug class 1 (the original):** eligibility was a set of gap POSITIONS — `noise_gaps = {"head_hold"} if audio_beds else {"head_hold", "trail_hold", "body"}` — so **a timeline with an A1 bed and no head hold, the ordinary case, had no eligible gap at all** and the toggle emitted zero chains. Every saved project in `projects/` is exactly that shape (beds loaded, `headHoldSec: 0` everywhere), so the render was byte-identical on and off while the per-gap chain was provably correct in isolation. Reported twice as "Room Tone does nothing". **Bug class 2 (the overcorrection):** replacing it with one endless layer summed under *everything* did fill every hole, and was reported immediately as "it's playing over the entire audio track" — the bed covers a real project end to end, so tone under the bed is tone everywhere. The rule that survives both: **decide by measured coverage, never by position and never by giving up on measuring.** Existing audio is bit-identical with the toggle on (max |on−off| = **0.000e+00**); only silence changes.
  - **The asset's own tail is 856 frames of pure digital silence, so looping the file whole puts a 17.8 ms DROPOUT in the "continuous" layer every 3.003 s.** Hand-measured on `Audio_NOISE.wav` (144144 frames @48 kHz = 3.003000 s exactly): frames 143174–144143 are a fade through a −100 dBFS window into 856 all-zero frames; leading zeros are 0. Looped and gained, that is a 0.333 Hz pulse in the noise floor — **39 zero-runs of ~754 frames (17.1 ms) in a 120 s render, 90 all-zero 5 ms RMS windows** — which reads as pumping and defeats the point of the layer. **A 50 ms window scan cannot see it** (min −29.0 dBFS, no −∞ windows); it takes a 5 ms scan, so use one. Fix is the leading `atrim=end_sample=NOISE_LOOP_END_SAMPLE` (`= 143174`) **before** `aloop`, cutting where the material is still at full level (5 ms windows there run −36.9 to −42.0 dBFS and it re-enters the loop at −39.5, so the seam is a step inside the noise's own variation). Verified after: **0 all-zero frames of any length across 5,292,000 frames (120 s)**, min 5 ms window −32.72 dBFS, level unchanged (−12.827 dBFS peak / −26.96 dB RMS). The index counts the ASSET's 48 kHz frames, so the trim must stay ahead of the `aformat` resample — and it must be re-measured if the asset is ever replaced.
  - **The fill is bounded PER CLIP, and the last clip gets a 50 ms margin so `amix=duration=first` — not arithmetic — lands the end.** Each clip's runs are padded/trimmed to that clip's own `expected_sec` (`apad=whole_dur` → `atrim=end`), exactly as `[aseq]`'s pieces are, because one `anullsrc`/`atrim` of `total_sec` does NOT quantize the same way: at 24 fps a frame is 44100/24 = **1837.5** samples, so a 10.0 s three-clip timeline measures **441001** samples of picture audio against **441000** for a single trim of 10.0. Merging adjacent same-kind runs (which the plan does, to emit fewer nodes) then shifts the last boundary by a further half-sample — and `amix` treats an input that **ENDS EARLY as silence**, which put a literal `(0, 0)` at sample-frame 441000 of 441001 with the toggle on: the one thing the feature exists to prevent, and invisible to any RMS scan. Fix is structural, not a rounding chase: `NOISE_TAIL_MARGIN_SEC = 0.05` is added to the last clip's final run **and** to its `apad`/`atrim` target, so the fill is deliberately longer than the sequence and the mix cuts it. Re-verified **0 zero sample-frames** in both render and stem. Two rules follow: the tone label must never be `amix`'s FIRST input (it would then set the length and make the render 50 ms long-ended), and never map it straight to an output.
  - **`build_a1_filter`'s per-clip skeleton is a LENGTH authority, not content — do not collapse it into one `anullsrc` of `total_sec`.** The stem is documented as sample-for-sample the A1 contribution to the equivalent V1 render, and it earns that by building the same pieces per clip in the same order with the same `apad=whole_dur/atrim=end=expected_sec`, so it quantizes exactly the way `[aseq]` does. (It reads each clip's `has_audio` even though it renders no clip audio: that is what tells `noise_fill_plan` where the V1 render's own sound would be, and therefore where tone must stay out. Drop it and the stem gets tone the render doesn't have, which is the same as not being a stem.) Raw gap durations do NOT agree between `anullsrc` and a tone chain for fractional lengths (`D=0.4171` → 18394 vs 18395 frames; `D=0.033367` → 1471 vs 1472); it is that per-clip normalization that collapses both to the same count, so don't remove or reorder it.
  - **The asset is quiet enough that a working layer reads as a broken one** — `Audio_NOISE.wav` measures **−39.0 dB RMS / −24.9 dB peak**, and the render reproduces it at exactly that level with no attenuation anywhere. Against pure digital silence on laptop speakers that is easy to miss completely, which is how "room tone does nothing" survived two rounds of investigation while the tone was provably in the file. `NOISE_GAIN_DB = 12.0` (module top) is the fix, applied in `noise_slice` alone so the V1 render and the A1 stem can never disagree about level: **keep it in one place**, since a stem louder or quieter than the render's own tone is not that render's A1 contribution any more. Measured result at +12 **−26.96 dB RMS / −12.83 dB peak** (the 48 k→44.1 k `aformat` adds +0.09 dB of interpolation overshoot over the arithmetic −12.92, so headroom sums written from a gain and the asset's peak alone run slightly optimistic). Gain is a per-sample scale and the layer changes no length, so no video frame or dialogue sample moves.
  - **The level is now a REQUEST parameter, and the "one place" invariant moved rather than disappearing.** `NOISE_GAIN_DB` is the default and the fallback for a request that omits `noiseGainDb`; `NOISE_GAIN_DB_MIN = -12.0` / `_MAX = 24.0` bound it. It threads `build_{timeline,a1}_filter(noise_gain_db=…)` → `noise_track` → `noise_slice`, all keyword-defaulted, so the two builders no longer agree *by construction*. What holds the equivalence now is that **both routes read the level through the one shared parser `app.py::_a1_noise_gain_db`** — the same reason `_a1_request_beds` exists. Add a third caller and it must go through that function too, or `/api/render_a1`'s stem stops matching the joined render. Two details are load-bearing: the parser must **not** be `data.get(...) or NOISE_GAIN_DB` (0 dB is a legal level, and `or` would silently make it 12 — the `speed or 1.0` bug class), and the bound test is written `not (MIN <= x <= MAX)` so NaN is rejected rather than passed through as a filtergraph token. It rounds to 1 decimal so a given user-visible level always produces the same graph string, which is what makes framemd5 comparisons repeatable. `clampNoiseGainDb` in `clipMath.js` mirrors it client-side, and the field is held as raw TEXT in App state (a half-typed `-` must survive) clamped once at payload time. Verified: the graph at any level differs from the default's only in the `volume=NdB` token; every tone sample scales by the requested factor to within 1e-4; **`max|24dB − 12dB|` over the 187,426 samples carrying clip audio or bed is exactly 0** — the gain cannot leak off the tone layer; framemd5 identical across off/−12/+12/+24; sample count identical at every level; the fill plan is untouched (gain cannot move a boundary, which is why the plan functions deliberately take no gain argument).
  - **+24 dB is a MEASURED ceiling, not a taste call** — the asset peaks at −24.92 dBFS, so +24 is the loudest the tone can be while still, alone, not clipping; rendered it lands at **−0.83 dBFS** (the resample overshoot again). Anything above that needs a limiter, not a bigger `max`. Don't widen the bounds without re-measuring, and remember `SpeedForm.jsx` mirrors all three constants — the frontend and backend numbers must move together or a legal-looking stepper value 400s.
  - **`NumericStepper`'s `min` defaults to 0** — the room-tone dB stepper has to pass `min={NOISE_GAIN_DB_MIN}` explicitly or the whole quieter-than-the-asset half of the range is unreachable by ▼ while still being typeable, which reads as an arrow that stops working.
  - **Tone costs no headroom now — but the bed still can, so don't attribute the margin to the tone.** `amix normalize=0` is an exact sum, so headroom is the caller's problem: clip audio at full scale plus a 0.35 bed reaches **+2.61 dBFS** on its own, and AAC does not clamp it (a deliberately hot test measured **+3.44 dB peak** surviving the encode). Room tone no longer adds to that at all, because it plays only where nothing else does: the render peak is `max(existing peak, tone peak at the chosen level)` — −12.83 dBFS at the default +12, −0.83 at the +24 ceiling. Measured — the `Batch02_v2` render peaks **−9.06 dBFS with the toggle both off and on**, identical. The earlier continuous design took the worst case to +3.96 dBFS; that exposure is gone, and any doc still quoting it is stale.
  - **Verified by measurement, not inspection.** Filtergraph-level (never on the encoded file — the `under50mb_hevc` two-pass path is not deterministic run-to-run, which cost a wrong-looking frame hash once already). On `Batch02_v2`: video **240 frames, identical `framemd5` with the toggle off and on**, audio sample count identical (441001), **0 of 441001 zero sample-frames with tone on** (0 in the stem too) against a **25,725-frame run of true silence with it off**, and the bed's whole 9.4167 s reach differing by exactly **0.000e+00** — the only samples that changed are the 0.583 s round-up (all-zero 5 ms windows 116 → 0). The containment claim is the important one and needs a per-sample check, not a length check: on a synthetic 3-clip timeline (clip audio + holds + a silent source + slow-mo) the sound region `[0.5, 3.5)` is **bit-identical over 132,300 sample-frames**, and across a 10-shape matrix (`/tmp/rt/matrix.py`: no-audio source, holds, slow-mo, reversed, unaligned trim, bed shorter/longer/exactly covering) **not one sample-frame of tone landed over existing sound** and `filled == noise_fill_seconds(plan)` to <2 ms every time. Three-input `amix normalize=0` is still an exact unity sum (**3.73e-09** across 286,650 sample-frames). Stem equivalence by subtraction, `((V1+A1+tone) − V1plain) − A1stem`: **3.73e-09** with all three passes at exactly 286,650 sample-frames. The stem can still land a sample or two SHORT of the render where per-clip frame counts are odd (536549 vs 536551 on a 12.1667 s timeline) — **pre-existing, present identically with the toggle off**, so don't read it as a tone bug; the tail margin fixed the tone's own end, not this. The structural claim is checkable without rendering: generate the graph both ways and diff the chain list; with nothing to fill it is **byte-identical** to the toggle-off graph.
  - **Bed reach comes from the audio STREAM's duration, not the container's** — `get_video_info` now returns `audio_duration` alongside `video_duration` for this. A container's duration reflects its LONGEST stream, so a file whose video outruns its audio would be credited with sound it does not have and the tail would render silent with the toggle on. Falls back to the container duration when the stream reports none (and to `0.0` when there is no audio stream at all), so a file ffprobe is vague about degrades to the old behaviour rather than to "no coverage". Exercised against files where the two agree; **not yet measured against a file whose audio is genuinely shorter than its container**, which is the case to construct if this is ever suspect.
  - **Removing an A1 clip leaves a HOLE; nothing after it moves.** Each bed carries an explicit `startSec` in LANE seconds (0 = V1's picture start, *excluding* the head hold, so a bed's position is immune to head-hold edits and the lane-wide `adelay` keeps meaning exactly "V1's head hold" — do not fold a leading hole into that `adelay`). `a1_bed_source` interleaves `anullsrc` silence pieces into the **same single `concat`** it already used, so `amix` stays at a **fixed three inputs** (clip layer, bed layer, tone layer) whatever the bed count — the reason its docstring rejects per-bed `adelay`, and still the reason. Four details are load-bearing: (1) **`anullsrc:duration=D` FLOORS to `int(D*sr)` samples while a following `atrim=end_sample=N` yields exactly N**, so gap pieces ask for `(n+2)/sr` seconds and are cut by sample count — measured, not assumed; (2) the piece's `aformat` must precede its `atrim`, because removing bed 0 makes a silence piece `concat`'s FIRST input for the first time and `concat` negotiates format from that input (see the entry above); (3) the one-bed fast path had to become **"one bed AND no leading gap"** or removing bed 0 of a two-bed lane silently drops the head hole; (4) coverage is still measured per bed from `audio_duration`, never from the client's `durationSec` (a container duration used only for drawing) — `startSec` is a client edit decision, reach is a server-owned media fact.
  - **The removal guarantee is ≤2 samples, and it measures 1 — but the moved bed is BIT-IDENTICAL at that offset.** Bed *j*'s onset is reached through *decoded* samples in a contiguous lane and through a *computed* `anullsrc` gap once a bed before it is removed, so probe-vs-decode disagreement of a fraction of a sample remains by construction; exact equality at a fixed index is the wrong assertion and will fail. Measured on three A1 stems over one 10 s timeline (contiguous / middle bed removed keeping `startSec` / the same with `startSec` stripped as a control): the surviving clip after the hole is **bit-identical at a lag of exactly −1 frame** (`max|d| == 0` over 130,459 frames; the next-nearest lags differ by 0.159 and 0.299), the hole itself is **all-zero frames** with the toggle off, and the stripped control moves that clip **86,362 frames = the removed clip's whole 1.958333 s** — which is what proves the test can see a shift at all. With tone on, the hole fills with **zero all-zero frames** left in it and every bed-covered range is bit-identical to the toggle-off stem (only the single boundary frame at the nominal cut differs, the same ≤2-sample residual). Harness: `/tmp/rt2/verify_holes_render.py`.
  - **Splitting an A1 clip is a CUT, and that is a measured claim, not a design intention.** A split is `clipMath.splitBed`: the same file twice, the left half gaining `outSec`, the right half `inSec` *and* a `startSec` advanced by the left half's played length — so the two halves butt-join with **no hole** and no other clip moves. Both fields are optional and absent means "the whole file", which is why there is no `.nara` migration and why an untrimmed lane's graph is **byte-identical** to the pre-feature one (150-case dump unchanged, `/tmp/a1split/graphs.py`, md5 `64ade8e3fffc6bc4935972eecca2b0d4`). In the graph a trimmed clip becomes `aformat,atrim=start_sample=A:end_sample=B,asetpts=PTS-STARTPTS` inside the **same single `concat`** the lane already used. Four details are load-bearing: (1) **`aformat` comes FIRST, before the `atrim`** — that puts the cut in the graph's own rate domain, so both halves are cuts of the *same* resampled stream and `[A,t) ++ [t,B) == [A,B)` sample for sample; trimming first would restart swr's state at the seam and make "split then render" differ from the unsplit render exactly where a seam must be invisible; (2) sample counts, never seconds, for the same reason the gap pieces are pinned that way; (3) the one-bed fast path needed a **third** condition (`not trims[0]`) or splitting a single clip and deleting one half returns the raw `[N:a]` and silently drops the trim; (4) `bed_spans`/`noise_fill_plan` are **blind to a split** — two adjacent spans merge back into the unsplit one — so room-tone coverage is provably unchanged by a cut, and that is a property to preserve rather than a coincidence.
  - **The split is bit-exact at the graph's rate, and the ONE frame that differs at other rates is the fast path, not the cut.** Measured through `/api/render_a1` (deterministic `pcm_s16le`; `/tmp/a1split/render_check.py`, 13 checks): a 44.1 kHz clip split at a deliberately unaligned 1.317 s renders **bit-identically** to unsplit (356,474 samples, `max|a−b| == 0`), as does splitting a half again into three parts; V1's `framemd5` is identical across the split (97 frames) and so is the joined render's audio md5 — an audio-only edit cannot touch a frame. With a **48 kHz** source, split-vs-unsplit differs in exactly **one frame**: the bed's last resampled frame (137812 = `int(3.125 × 44100)`), `(−6,−6)` vs `(0,0)`, −74 dBFS. That is **not the cut** — the same lane trimmed to the whole file (concat path, cutting nothing) is bit-identical to the split, so the delta is the pre-existing difference between the one-bed fast path (which hands raw `[N:a]` to the bed chain's `aformat`, resampling one filter later) and the concat path, which moves swr's end-of-stream flush by a frame. ffmpeg is deterministic here — the same payload rendered twice is identical — so don't chase this as nondeterminism, and don't "fix" it by dropping the fast path, which would change every existing project's graph for one inaudible frame.
  - **`bed_span` → `bed_spans` was renamed, not re-signatured, on purpose.** Every old call site spread the result as two positional scalars (`*bed_span(...)`), so returning a LIST under the old name would have been unpacked into two garbage cut points with no error anywhere. The rename turns each stale site into a `NameError` instead — which is exactly what it did to `/tmp/rt2/verify_gain.py` on the first re-run. `bed_reach_sec` was removed rather than aliased for the same reason. A contiguous lane's spans merge to the single span the old function returned, so `noise_fill_plan` is **bit-identical for every lane without a hole** (48 graphs and 48 plans byte-identical to the pre-change baseline, `/tmp/rt2/verify_holes.py`), and overlap is clamped forward in exactly two idempotent places — `fu.normalize_bed_placements` and `clipMath.normalizeBeds` — so a gap can never be negative.
  - **Room tone is render-only — the preview cannot play it.** `AudioBedPlayer` emulates `BED_GAIN` and nothing else, and the asset is not even served to the browser (there is no `/assets` route). So the toggle is inaudible until Render, which is itself part of why it was reported as broken. If the A1 lane's amber "noise" labels ever need to be trusted, this is the caveat to state. A HOLE left by a removed A1 clip is therefore silent in the preview even with the toggle on — correctly so for the toggle off, and by the same limitation as every other filled stretch when it is on.
- **The server NEVER trusts client-supplied fps/has_audio/resolution** — `render_timeline` re-probes every input itself. Only inSec/outSec/holds/speed/reversed come from the request.
- `run_ffmpeg` prepends the binary, `-nostdin` and `-y` itself — args must NOT include `ffmpeg`, and outputs are force-overwritten. render_timeline uses timeout=1800 (vs default 600) because whole-timeline `-qp 0` renders run long.
  - **`-nostdin` plus `stdin=subprocess.DEVNULL` are not hygiene — dropping either one hangs every render on a Terminal-launched server, and the default agent shell cannot reproduce it.** ffmpeg links `tcsetattr` (`nm -u /opt/homebrew/bin/ffmpeg` shows it; ffprobe shows neither `tcsetattr` nor `tcgetattr`, which is why `probe` needs nothing) and calls it on fd 0 at startup for the `[q] to stop` keypress reader. From a process group that is not the tty's foreground group that raises **SIGTTOU**, and since `subprocess.run` keeps the child in our own group the signal stops *the whole group*: measured 5 processes in `STAT T` at once — ffmpeg, `app.py`, the reloader child and both `resource_tracker` helpers — so the **server** is bricked for every later request, not just the render. The `timeout=` cannot rescue it either: the block is indefinite, not bounded (a `timeout=10` call was still stopped at 245s when the observer gave up, because the Python that would raise `TimeoutExpired` is stopped too; `SIGCONT` doesn't help, the interrupted `tcsetattr` restarts and re-raises). Proven by signal, not inferred: ignoring SIGTTOU in a `preexec_fn` completes the encode in 0.3s, ignoring SIGTTIN leaves it stopped at 8.1s. **Why it can look fine:** `nohup` redirects stdout/stderr but never stdin, so a hand-typed `nohup python3 app.py > log 2>&1 &` leaves fd 0 on the tty (the docs add `< /dev/null` as of 0.31.1 — see AUDIT #15 — but the short form is what people type) — yet an agent shell has no controlling terminal by default (`tty` → `not a tty`, `ps` shows `TTY ??`/`TPGID 0`), so an agent-launched server never reproduces this and every render passes. **To reproduce it you must allocate a pty yourself** — `script -q /dev/null`, or `pty.fork()` + an interactive shell — and then put Flask in a background process group on that tty; a plain agent-shell `nohup ... &` is not the failing shape. Output bytes are unaffected, measured across 5 render cases (plain trim; multi-clip concat with holds + reverse + 0.75x; `under50mb` two-pass h264; `under50mb_hevc` two-pass x265; `/api/render_a1`) rendered on a patched and an unpatched instance: identical file md5 **and** identical `framemd5` on all 5, with the flag confirmed present in the patched arm's real argv (15/15 invocations) and absent in the other. `-nostdin` does not disable stdin as a *data* source either (`cat x | ffmpeg -nostdin -i -` is byte-identical). Two caveats for anyone re-verifying: in **Matroska** the file md5 differs run-to-run with identical flags (SegmentUID is random) so compare `framemd5` there, not file bytes; and the `Press [q] to stop` line disappears from stderr, which nothing parses but which shifts every `detail` string by 32 characters.
  - **Killing an orphaned encoder on server exit needs a main-thread registry, because the render thread cannot clean up after itself (AUDIT #8, 0.39.0).** Flask serves renders on **daemon** threads, and at interpreter exit daemon threads are dropped *without unwinding* — so the `finally` in `run_ffmpeg_staged`/`multipass_export_render` never runs and the only `Popen` handle vanishes with the thread. Before 0.39.0 a debug-reloader restart (`touch VERSION`), Ctrl-C, `kill`, or a closed Terminal therefore left ffmpeg reparented to **PID 1**, encoding at ~1100% CPU with nowhere to deliver, and two-pass scratch files (`.ffpass`/`.ffpass.cutree` for x265, `-0.log`/`.mbtree` for x264) orphaned under `.partials`. Fix: `run_tracked` records every child in a module-level `_LIVE_CHILDREN` set and `stage_output`/`discard_output` maintain `_LIVE_STAGES`; `install_shutdown_handlers()` (called once from `__main__`) registers an `atexit` callback plus SIGTERM/SIGHUP handlers that SIGTERM-then-SIGKILL the children and discard their staging dirs. **Three facts that were measured, not reasoned:** (1) the werkzeug reloader restarts via `sys.exit(3)` from the main thread (`_reloader.py:trigger_reload`), which is an *ordinary* exit, so `atexit` runs — don't assume a reload skips it. (2) `app.run()` installs its **own** `signal(SIGTERM, lambda *a: sys.exit(0))` *after* `install_shutdown_handlers()`, so under the debug server the SIGTERM that fires is werkzeug's — harmless, because its `sys.exit()` still triggers `atexit`; our SIGTERM handler only matters when the app is run without the reloader, and our SIGHUP handler always matters (werkzeug never touches SIGHUP). (3) SIGINT is left on Python's default on purpose — the encoder shares the server's process group (see the `-nostdin` bullet: no `start_new_session`), so the tty delivers Ctrl-C to it directly *and* the `KeyboardInterrupt` reaches `atexit`; adding a SIGINT handler only wedges werkzeug's own shutdown. **Out of scope by decision at the time:** a client disconnect while the server stays up (`curl -m 1`) still ran the render to completion — that half shipped separately in 0.45.0, see the next bullet. Successful renders are byte-identical to pre-fix (9/11 modes IDENTICAL by md5; `trim match`/`trim high` differ run-to-run on the pre-fix server too — x264 ABR/CRF non-determinism, same argv, matching frame hashes).
  - **Cancelling a render when its client goes away needs a watcher thread and a per-request scope OBJECT — a thread id will cancel the wrong render (AUDIT #8, 0.45.0).** The request thread is blocked in `Popen.communicate()` for the whole encode, so there is no loop to check a flag in; `cancel_on_disconnect` (app.py) starts a daemon thread that polls `request.environ["werkzeug.socket"]` once a second (`CLIENT_POLL_SECONDS`) and calls `fu.cancel_scope(scope)`. **Detection is `select.select([sock],[],[],0)` then `sock.recv(1, socket.MSG_PEEK)`:** readable + `b""` = the peer sent FIN; readable + real data = a **pipelined keep-alive request**, deliberately *not* treated as a disconnect; `OSError` = ECONNRESET and friends. `werkzeug.socket` exists on werkzeug 3.1.8 (`WSGIRequestHandler.make_environ`) and is the only handle on the connection a Flask view gets — there is no framework-level "is the client still there". The scope is a `CancelScope` **object** held in a `threading.local`, never a thread ident, because werkzeug hands the same thread to the next keep-alive request and thread ids are recycled: a watcher that fired late would otherwise SIGTERM a *different* render (verified: two renders down one keep-alive connection both return 200). `run_tracked` also **refuses to spawn** inside an already-cancelled scope, which is what stops a two-pass mode from launching pass 2 after pass 1 was killed. Cancellation surfaces as `RenderCancelled(RuntimeError)` so it unwinds through paths that already exist — every route maps `RuntimeError` to a JSON error and every staging dir is discarded in a `finally`, not an `except` — and the decorator answers **499** ("client closed request") so deliberate cancellations don't inflate the log's 500 count. Measured on a 90s fixture against a copy differing by exactly this change: encoder gone **0.7s** after the hang-up (1.7s in pass 1, 2.3s in pass 2) with no output, no partials and no passlogs, vs. 11.9–13.2s of further encoding and a committed file on the pre-change copy; uninterrupted renders byte-identical (`lossless`/`high`/`under50mb_hevc` md5s all match). **Two deliberate exclusions:** `/preview` is *not* cancelled (an aborted preview conversion completes and lands in the cache, so the next open of that clip is instant — measured 25.000000s / 17.5 MB), and `/api/execute` is cancelled but writes straight to the export dir with no staging, so it leaves the truncated file it had written (measured 28 MB, `duration=8.566667`, 257 frames, playable) — the same leftover any failed chat command leaves. `_stop_procs` is shared with the shutdown half on purpose: two kill loops would drift on which signal comes first or whether the child is reaped.
- `/api/reverse` returns HTTP **200** (not an error) with `{warning, estimated_bytes}` when the estimated RAM (W×H×3×fps×duration) exceeds 2 GiB and `confirm` is absent — client must resend with `confirm: true`. ffmpeg's reverse filter buffers the whole video in memory.
- **`under50mb` is not a CRF or single-pass-ABR mode, deliberately.** CRF has no size guarantee at all (size follows content complexity). Single-pass ABR knows a target bitrate but routinely drifts several percent off it because it can't see the whole file's complexity in advance — not acceptable against a hard "always under 50MB" promise. `render_size_capped` runs a real two-pass encode (pass 1 → `/dev/null` via `-f null`, discovers per-frame complexity; pass 2 spends the byte budget against that map) and then **measures the actual output file size** and retries with a 15%-smaller bitrate (up to `max_attempts`) if it still overshot — the guarantee is enforced by checking the real file, never just trusted from the bitrate math. Every call site (`render_timeline`, `trim`, `splice`, `hold_frame`, `reverse`) needs the render's total duration to size the bitrate budget; `trim`'s `start`/`end` can be `HH:MM:SS.ms` timecodes (see the legacy UI's own placeholder), not just plain seconds — `_parse_time_to_sec` in app.py handles both. `render_size_capped` cleans up its own `<out_path>.ffpass*` two-pass log files in a `finally` block even on failure.
- **A filter-produced label consumed by more than one chain needs an explicit `split=N`.** ffmpeg auto-splits a raw *input* pad (`[0:v]` can feed several filters), but a *filter output* label (`[vsrc0]`, `[vov0]`) can only be consumed **once**. `build_timeline_filter` feeds its per-clip video source to up to three chains (lead hold, main body, trail hold), so it now emits `split=<n_consumers>` whenever that source is a filter label rather than `[i:v]`. **This was a latent pre-existing bug: crop + hold on the same clip had never rendered at all** — it died with `Input link in0:v0 parameters (size 1920x1080, SAR 1:1) do not match the corresponding output link in0:v0 parameters (512x512, SAR 1:1)`, exit 234 (confirmed against git HEAD). The overlay path inherited the same flaw but failed *silently* (30/135 frames composited, exit 0) because an overlay doesn't change frame size, so concat happily accepted the uncomposited frames. Verified after the fix: crop-only output is **byte-identical to the pre-fix version** across static crop / animated crop / single keyframe / no crop / reversed+speed+holds / multi-clip with `no_audio` both ways — the `split` only affects the two combinations that were already broken.
- **`overlay` silently CLIPS an out-of-range x/y; `crop` silently CLAMPS.** Opposite failure modes for the same class of bug, both exit 0 with no warning. A crop ramp running past the edge freezes against it (the pan just stops); an overlay ramp running past the edge loses the overflowing pixels entirely. Both mean keyframe bounds must be validated server-side before rendering — `render_timeline` checks every overlay keyframe's `x+w`/`y+h` against the *probed* source resolution, and its `t` against the clip's main-body window. Also relevant: `overlay`'s `eval` defaults to **frame** (per-frame expressions work without opting in) and `eof_action` defaults to **repeat** (which freezes the last overlay frame for the rest of the clip and extends the background to the foreground's length — a frame-COUNT change that reads as "not lossless" in a framemd5 diff). `eof_action=pass:repeatlast=0` is what stops compositing at the overlay's end without freezing or truncating.
- **`under50mb_hevc` (`render_size_capped(..., codec="hevc")`) uses genuinely different flags than the H.264 path, not just a swapped `-c:v`.** libx265 has no `-pass`/`-passlogfile` options at all (hand-verified) — two-pass is `-x265-params "pass=1:stats=<file>"` / `"pass=2:stats=<file>"` instead, producing stats files named `<file>` + `<file>.cutree` (vs. libx264's `<prefix>-0.log`/`-0.log.mbtree`) — `_PASSLOG_SUFFIXES` branches the `finally` cleanup on `codec` accordingly. `-maxrate`/`-bufsize` DO work identically as top-level flags for both codecs (verified via the encoded stream's own reported CPB properties) — no `vbv-maxrate=`/`vbv-bufsize=` workaround needed. 10-bit intermediate (`-profile:v main10` + `yuv420p10le`) needs its pixel-format conversion spliced into the caller's EXISTING `-vf`/`-filter_complex` value (`_inject_pixel_format`), never added as a second separate `-vf`/`-filter_complex` flag — ffmpeg silently lets a later duplicate flag on the same stream **replace** the earlier one (confirmed by hand: explicit "Multiple -filter/-af/-vf options specified for stream 0, only the last option will be used" warning), which would silently drop `reverse`'s own `-vf "reverse"` or an entire `-filter_complex` graph. The splice point for `-filter_complex` callers is the literal `[outv]` label every filter builder in this module terminates its video chain with.
- **The `custom` mode's two-pass render is a deliberate near-copy of `render_size_capped`, not a generalization of it.** `render_custom_two_pass` repeats the retry loop, the audio-bitrate floor and the passlog cleanup rather than parameterizing the original, because both `under50mb*` modes are hand-verified against frame hashes and measured output sizes — refactoring them to serve a configurable third mode would put that verification at risk for no user-visible gain. Only read-only pieces are shared (`_PASSLOG_SUFFIXES`, `_inject_pixel_format`). If a bug is found in one, check the other; they are meant to drift only where the spec says they should.
- **Three things about the custom mode's flags, all measured rather than assumed.** (1) `p010le` is NOT in `libx265 -h`'s or `libx264 -h`'s supported pixel-format list, but *requesting* it works — ffmpeg inserts the conversion and the encoded stream comes out `yuv420p10le`. It stays offered because it's the pixel format an Apple-ecosystem user is most likely to type. (2) Both codecs' `-profile:v` is a **free-form string**, not an enum ffmpeg validates against a list, so `EXPORT_PROFILES` is our allowlist and nothing else — an unlisted value would reach the encoder verbatim. (3) Output-only flags (`-movflags`, `-tag:v`) are **silently ignored by the null muxer**, which is why the user's extra args can be passed to pass 1 as well as pass 2; keeping the two passes' flags identical matters more than pruning the ones pass 1 can't use.
- **The custom mode's bitrate formula gives the WHOLE byte budget to video** — `(target_bytes × 8 × safety) ÷ duration ÷ 1000`, per spec, unlike `target_bitrate_for_size` which subtracts the audio bitrate first. So `safety` (default 0.90) is what has to cover both container overhead and the entire AAC track: a long render with high-bitrate source audio can overshoot the cap and go through the shrink-and-retry loop, and **each retry re-encodes both passes**. In the other direction, `maxrate` defaults to 0.95× the average, which makes VBV clamp the achieved rate near maxrate rather than the target — measured output with the defaults lands at **≈0.84–0.86 of the cap**, not 0.90. Both are worth knowing before "the file is smaller than I asked for" or "it encoded four times" reads as a bug.
- **Every render is written to `<export dir>/.partials/<pid>.<tid>/<final basename>` and moved into place only on success** (`stage_output` / `commit_output` / `discard_output` / `run_ffmpeg_staged`, 0.34.0), so an interrupted render leaves nothing in the export dir. Three measured facts hold that design in place, and a future temp-file change must respect all three. (1) **ffmpeg picks the muxer from the output extension**, so a temp path must keep the real extension last — a name ending `.part` makes ffmpeg refuse the job outright ("Unable to find a suitable output format … use a standard extension"), which is how the same pattern first broke every *preview* in 0.33.0. (2) A flat sibling temp file is not an option even with a valid extension: `_list_dir` filters only on media extensions and **does not skip dotfiles**, so `.foo.mp4.1234.part.mp4` shows up in the Export Bin, where `OutputPanel.jsx` auto-selects the newest file by mtime and mounts a `<video>` on it. A subdirectory is invisible to it; a suffix is not. (3) Forcing the format instead would corrupt `.m4v`: `-f mp4` rewrites the ftyp major brand from `M4V ` to `isom`, and `-f m4v` is the *raw* MPEG-4 video muxer, which refuses H.264 ("m4v muxer supports only codec mpeg4") and writes 0 bytes. Keeping the exact final basename one directory down needs no `-f` and is byte-identical to rendering in place (`cmp`-verified for mp4/mov/avi/m4v; matroska and webm can't be compared this way — SegmentUID/DateUTC make their output differ between two identical runs). `commit_output` also walks to the next free `_1`/`_2` name rather than replacing an existing file, which is what preserves the pre-existing behavior of two same-name renders producing two files — and it **claims each candidate name with `os.open(..., O_CREAT|O_EXCL)` rather than testing it with `os.path.exists`** (0.35.0, finding #2). A test is not a claim: 0.34.0's `while os.path.exists(final)` loop left microseconds between the check and the `os.replace`, and two commits landing in that gap both saw the name free and one render's output was destroyed while both requests reported the same filename. Measured with the gap widened to 0.3s: 8 concurrent commits left **1** file. `O_EXCL` is filesystem-level, so it also holds against a second `app.py` process, which a `threading.Lock` would not. The placeholder it creates must be unlinked if the `os.replace` then fails, or a failed commit leaves exactly the 0-byte export finding #9 removed. Side effect worth knowing: the two-pass stats files derive their prefix from the output path, so they are now born in the staging dir and die with it — including libx264's `-0.log.temp`/`.mbtree.temp`, which `_PASSLOG_SUFFIXES` never listed.
- **Extra encode args are rejected structurally, not by character blocklist.** `validate_extra_encode_args` `shlex.split`s the text, then requires it to start with a flag, refuses a whole `ffmpeg` command, refuses anything in `_EXTRA_ARG_CONFLICTS` (the flags the dialog itself computes — `-c:v`, `-b:v`, `-pass`, `-vf`, `-preset`, …), and runs any path-looking token through `_media_path_ok` (the containment check extracted out of `validate_ffmpeg_command`, which now calls it too). There is deliberately no shell-metacharacter filter: `subprocess.run` is always given an argv list, so there is no shell to inject into, and a blocklist would only reject legitimate filter syntax.

## Frontend invariants

- **Hold placement invariant**: headHoldSec only on the first clip; tailHoldSec/roundHoldSec only on the last. `sanitizeHoldPlacement` (clipMath.js) zeroes violators and marks them dirty — every operation that reorders/adds/splits/deletes clips must run its result through it (all current ones do).
- **A unit-toggled input has to convert its OWN value when the toggle flips (0.64.0).** `HoldFrameForm`'s duration field follows the transport's TC/FR toggle like `TrimForm`'s boxes, but it is the user's standing entry rather than a value derived from a clip — so nothing re-renders it from state the way `TrimForm`'s effect re-derives In/Out from `selectedClip` on a `displayMode` change. Left alone, `1` second silently becomes `1` frame and the next Head press applies a 42 ms hold instead of a 1 s one. It converts in place on the flip (a `useRef` holds the previous mode; the effect deliberately no-ops when only fps changed, because a frame count keeps its meaning when the sequence's rate changes). Two rules for any new unit-toggled field: the value written to a clip stays **seconds** (`headHoldSec`/`tailHoldSec` — the toggle is display only, and the render's unit must not depend on what the UI is showing), and the frame conversion goes through `holdFrames` + `sequenceTargetFps` — the render's own half-to-even rounding on the render's grid, so N frames typed is N frames of the *output* (verified for mixed fps too: 12 frames asked of a 24 fps first clip in a 30 fps sequence renders as exactly 12 head frames) — never a bare `Math.round`, and never the first/last clip's own fps, which is not the number any other readout in the app counts in.
- **The V1 lane now arbitrates THREE drag kinds, and the bin drag has to be tested first (0.65.0).** A clip reorder, an OS file drop and a Media Bin drag all land on the same lane, and the first two are told apart by `dataTransfer`: `'Files'` in `types` means the OS, its absence means a reorder. A bin drag carries no files either, so `v1FileDragProps.onDrop`'s pre-existing `if (!e.dataTransfer.files.length)` branch claims it as a reorder, finds `dragFromRef.current == null` and `return`s — the drop silently does nothing. `readBinDragPayload` is therefore checked **before** that branch, and `isBinDrag` (which reads `types`, the only thing readable during `dragover`) is what lights the lane. Two more things this drag needs that are easy to lose: `useBinFolders.handleFileDragStart` must keep `effectAllowed: 'copyMove'` — narrowing it back to `'move'` makes the browser refuse the lane's `dropEffect = 'copy'` outright and the drop just won't fire — and only the Media Bin (`scope === 'input'`) writes the payload at all, so the Export Bin and Project Library never light a lane they'd have to refuse (every clip builder hardcodes `sourceDir: 'input'`). Adding a fourth drag kind means extending the same ordered chain, not adding a parallel handler.
- **A stale mid-sequence hold is REACHABLE, and only the render's own first/last rule hides it.** `sanitizeHoldPlacement` runs on reorder/split/duplicate/delete but *not* on append — Raise the last clip, then add another clip, and the now-middle clip still carries `roundHoldSec > 0` until something else sanitizes. Nothing shows because `render_timeline` applies the same rule server-side (`lead_hold` only `if is_first`, `trail_hold` only `if is_last`), so the joined render ignores it. **That safety net inverts in a 1+ shot render**, where each clip is rendered as its own one-clip timeline and is therefore both first and last: the stale hold would suddenly render and that shot would come out longer than the stretch of the joined render it stands for. `App.renderShots` zeroes head holds off every shot but the first and tail/round holds off every shot but the last for exactly this reason — measured: a stale 0.5s round hold on clip 2 gave a 1.5s shot against the joined render's 1.0s stretch before the guard. Don't "simplify" it away as redundant with `sanitizeHoldPlacement`. **`analyzeMath.sequencePieces` is the third place this rule has to be applied by hand** — and it now feeds TWO consumers, **V2 Batch Analyzer and V2 Reconstruct** — there for the mirror-image reason: it derives where the cuts landed in a file the render already wrote, so a stale hold it trusted would both invent a cut in the middle of real footage and push every later cut point past the frame it belongs on. (For Reconstruct the damage is worse than a misplaced cut: it drops hold pieces and reorders the rest, so a phantom hold would delete real footage and shift every shot's range.) Any new code that reasons about a clip's *rendered* length owes the same first/last treatment.
- **`sequencePieces` must measure in FRAMES, and the frame grid is the RENDER's, not the clip's.** It predicts where a render put its cuts, so raw seconds are the wrong unit even though they are the right unit for drawing the same clips on screen (`clipMainSec` stays raw — don't "unify" the two). Three separate quantizations have to be mirrored from the backend, and all three are load-bearing: (1) the body is `ceil(outSec*fps) − ceil(inSec*fps)` whole source frames with `outSec` clamped to the video stream's last frame and a floor of one frame (`ffmpeg_utils.clip_timing`); (2) each hold is `round(H*fps)` frames, and the tail hold and the Raise round-up are **summed before** rounding (`app.py` builds one `trail_hold`), so rounding them separately can miss the render's single rounding — they are split back apart on a frame boundary here only because Batch Analyze names segments by piece kind; (3) the whole sequence is normalized to ONE output rate, `target_fps = max(input fps)`, and **each clip is hard-capped to `round(expected_sec * target_fps)` frames** (`n_norm_frames`), so a boundary is a running sum of per-clip integer frame counts — rounding the *cumulative* total instead (which `pieceOffsetsOnV2`'s `snap` alone used to do) is off by up to half a frame per clip at any speed whose stretch is not a whole number of frames, i.e. at the 0.75× and 0.4× presets. Measured across 3000 randomized sequences (2–19 clips, mixed fps/speeds/holds): raw seconds drifted up to **27 frames** — 0.45 s at 60 fps — against **0** for the frame arithmetic. Confirmed end to end against real ffmpeg output rather than only in the abstract: a 3-clip 24 fps render with unaligned trims plus 0.75×/0.5× shots and head/tail/Raise holds came out **92 frames**, exactly the predicted total, with every boundary on a whole frame (8/27/50/84/90/92), where the old arithmetic predicted 8/27/**48**/**83**/**89**/**91** — a 2-frame early cut on shot 2, which for Reconstruct means splicing 2 frames of shot 3 onto the end of shot 2 and losing 2 frames of shot 2. The error is worst exactly where the user changed time, because the per-clip body error is multiplied by `1/speed`. This is a **second copy of Python arithmetic**, which `clip_timing`'s own docstring warns against; it is unavoidable (the browser decides these cuts with no render in flight to ask) so `clipMath.clipRenderFrames`/`clipMainFrames`/`holdFrames`/`clipRenderedMainSec` and `clip_timing`/`n_norm_frames` must be changed together. All of it now goes through one `clipRenderFrames(clip, {isFirst, isLast, targetFps})`, which both `sequencePieces` and `sequenceRenderFrames` (and therefore Raise) build on — a third hand-written copy is how these drift.
- **`Math.round` is the WRONG rounding for the frame mirror — the render rounds half to EVEN.** Python's `round()` is banker's rounding, so `round(72.5)` is **72**; JS `Math.round(72.5)` is **73**. This is not a pedantic edge case: `expected_sec * target_fps` lands exactly on `.5` constantly, because an odd source-frame count at 0.4× (`×2.5`) or 0.2× (`×5`) produces one every time and both are presets. Measured: a 30 fps clip trimmed to 29 frames at 0.4× is `72.5` output frames — `clip_timing` + `n_norm_frames` give **72**, `Math.round` gives 73, and a real render of that 3-clip sequence is **135 frames** where half-up predicted 136. In a randomized 2500-sequence set against real Python, **632 of 10119 clips (in 561 sequences) hit an exact tie**, so half-up is a one-frame error on roughly a fifth of realistic timelines, and it accumulates. Everything in the mirror rounds through `clipMath.roundFrames`; never reintroduce a bare `Math.round` on a frame count.
- **Raise measures the RENDER's length, and it cannot always hit the second exactly.** `RaiseButton` used a raw-seconds sum (`sequenceBaseSec`, now deleted so it can't be reached again) and was therefore wrong in **both** directions: it offered a round-up on a sequence the render already lands whole — and applying it pushed the render a frame *past* the whole second — and it reported "whole" on a render that wasn't. Both verified against real ffmpeg: a 30 fps 3-clip sequence renders to exactly 4.500 s, the old code offered `+0.4833s → 5s`, and that hold really renders to **149 frames = 4.9667 s**, a frame short of the 5 s it advertised; `clipMath.sequenceRaise` offers `+0.50s` and renders to **exactly 150 frames = 5.000000 s**. The residual limitation is real and inherent, not a bug to fix: the hold is quantized on the **last clip's** fps and the sequence on the output rate, so the reachable lengths step by more than one output frame when the last clip is slower than the output (and the tie-rounding above can skip lengths even at matched fps) — e.g. reachable totals `…1283, 1285, 1286, 1287, 1289…`, with the target simply absent. `sequenceRaise` walks the hold up one last-clip frame at a time and takes the first render that **reaches** the second (so it is never short, and always the smallest such hold), returning `exact: false` when it overshoots — 180 of 2411 raises, by at most 3 frames. The UI shows `≈` and explains it in the tooltip rather than promising a length the render won't produce. **`RaiseButton` has NO status readout beside it, and re-adding one means reproducing a bug (0.63.1).** It used to print `baseSec` as the current length, and `sequenceRaise().baseSec` is measured with any existing `roundHoldSec` **stripped** — that is what makes a second Round Up replace its own previous answer instead of stacking a second hold on it — so the caption read "whole (13.9s)" beside a transport already reading `00:00:14:00`: one sequence, two numbers, and the one on the button said the button hadn't worked. The caption was removed rather than corrected, because the transport bar now states the rendered length on the render's own grid and a second measurement of the same fact can only drift from it. All that's left is the enabled state plus the tooltip. If a readout is ever wanted back, the number to quote is `sequenceRenderFrames / sequenceTargetFps` (the render as it stands, hold included) and *whole* must be checked **before** *has an offer*. **`amountSec > 0` is the WRONG enabled test, for the same stripped-base reason** — it stays true after a successful Round Up, so the button stayed lit on an already-whole sequence and a second press rewrote the identical hold: no visible change, one undo entry, and a project marked unsaved. Measured on this repo's `projects/`: **22 of 25** saved projects render to an exact whole second and every one of them lit the button. It is `amountSec > 0 && roundUpAmount(rendered) > 0` — lit only when a round-up would change something. Consequence to keep either way: `amountSec <= 0` does **not** mean the render is whole — a stale `roundHoldSec` left on the last clip while a later edit lengthened the rest of the sequence lands a whole base plus that hold, so Raise has nothing to add while the render runs long. Round Up cannot fix that (it only ever writes a hold); the fix is to clear the stale ROUND segment (select it, Delete). `App.logMessages`' round-up warning is gated on the same rendered length and is now the one place a not-whole render is called out in words — **one** message about the sequence rather than one per clip, which used to warn four times about a sequence that renders to an exact 14 s and told the user to Raise a single clip, which Raise cannot do.
- **Known raw-seconds readouts that still predict a render — audited 2026-08-24, deliberately NOT fixed at 0.26.1.** The three entries above fixed every consumer that *cuts* footage (Reconstruct, Batch Analyze, Raise, the round-up warnings). A sweep for the same root cause elsewhere found these, and the decision was to record them rather than widen that change; each one now has a ready fix in `clipRenderFrames`/`sequenceTargetFps`, so don't re-derive the arithmetic when picking one up. Verification labels are honest — "read" means the code was read and the defect is certain, "cited" means the mechanism is consistent but nothing was measured.
  - `App.handleExportEdl` (**read**) — the `.edl` handed to another NLE is wrong three ways at once: `dur` is `(outSec − inSec) + holds` with **no `/speed`**, so every REC timecode after a slowed shot lands early; the holds are added for every clip with no first/last rule; and the program rate is `timelineClips[0].fps` rather than the render's `max`. It also contradicts the app's own on-screen EDL panel, which divides by speed — the same sequence shows two different record timelines.
  - `App.handleExportEdl`'s hand-rolled `tc()` (**read**) — `totalFrames % fps` with a **float** fps (ffprobe gives NTSC as `30000/1001` = 29.97002997…) prints a fractional frame field, e.g. `00:00:02:0.0599…`, so the whole export is unparseable rather than merely imprecise. `timecode.js:5` already does this correctly with `% Math.round(fps)`; the export should call `formatTimecode`, not its own copy.
  - `TransportBar`'s total — **FIXED at 0.63.1, listed here so it isn't "fixed" a second time.** It was the raw `clipTotalSec` sum × `selectedClip?.fps`, so it ignored quantization *and* the advertised total changed when the user clicked a different clip in a mixed-fps sequence — which is what made a Round Up that landed the render on exactly 14.000s read `00:00:13:23`. `Timeline.jsx` now hands the bar `fps={sequenceTargetFps(clips)}` and `totalFrames={sequenceRenderFrames(clips, fps)}`, and the bar derives the total *and* the position from that one frame number. What deliberately did **not** change: `transport.totalDuration` is still the raw sum and is still what every seek is clamped to, because the lane, the Ruler, the playhead and `buildSegments` are all drawn in raw seconds — quantizing the playback domain would put the transport's end past the end of the segments, where `handleAfter` can't reach it and playback spins instead of stopping. The visible consequence of keeping the two domains apart, and the intended reading: at the last frame the position says `00:00:13:23` against a total of `00:00:14:00` (a position is a frame, a total is a length), and the position is clamped to `totalFrames − 1` so the raw domain can't name a frame past the end of the file.
  - `EdlTable`'s REC IN / REC OUT (**cited**) — cumulative raw seconds formatted at each row's own fps, so boundaries drift down the list and consecutive rows disagree about the same instant.
  - `AudioBedBar`'s short/exact/"cut" state (**cited**) — measures A1 against the raw sequence sum, so it can report "exact" while the render trims the bed's tail, and tells the user how many seconds "is never heard" from the wrong number. Display-only, but acting on it (trimming the bed) discards audio the render was keeping.
  - `TrimForm`'s frames boxes (**read**) — `toDisplay` uses `Math.round` where a trim edge is quantized with `ceil(sec*fps − eps)`, so the number doesn't name the frame the render cuts on; and because `apply()` writes **both** boxes back through `fromDisplay`, pressing Apply after editing one field can move the *other* edge by a frame. Note the right mirror for a trim edge is `ceil`, **not** `roundFrames`. Timecode mode has the same lossy round-trip via `toFixed(2)`; the durable fix is to leave a field the user never edited alone.
  - `ffmpeg_utils.noise_fill_plan` (**partly refuted — read the code before believing the claim**) — an audit agent reported up to 83 ms of accumulating room-tone drift laying tone over dialogue. `clip_audio_pieces` already compensates the common case with an explicit SLACK piece, so the exposure is confined to clips whose whole-frame body falls *short* of the raw trim window (negative slack, which gets no piece) plus the residual output-grid rounding, and the drift runs **late**, not early. Real but far smaller than reported.
  - **A1 Split's two gates disagree, and it can block every render** (**cited; the 400 was not reproduced**) — the UI gates Split on `durationSec`, the probed *container* duration (`clipMath.bedOutSec`), while the render bounds its own reach by the probed *audio-stream* duration (`app.py::_a1_bed_lane`). Both sources are deliberate and documented in place. On a file whose audio stream ends before its container, the UI therefore allows a Split the backend rejects, and from then on `/api/render_timeline` **and** `/api/render_a1` return 400 for the whole project — not just for A1 — until the user works out that the split has to be undone. Reproducing it needs a file with a short audio stream; that's the first step if you pick this up.
- **`useUndoableTracks` keeps `{present, past, tag}` in ONE state object** for React StrictMode safety: double-invoked updaters produce identical results instead of double history pushes. Don't split into two useStates. The three tracks are named slices of `present` for the same reason plus one more — a history entry has to snapshot V1, V2 and A1 *together*, or interleaved edits produce an entry that half-applies.
- **There is exactly ONE undo history, shared by V1, V2 and A1 — do not add per-track stacks.** Undo is a single button and a single Cmd/Ctrl+Z, so it must mean "step back my last edit, wherever it was"; per-track stacks make the same keystroke do different things depending on which lane was last focused. ANIM has no slice of its own — crop keyframes live on clips, so they ride whichever list `CropOverlay` writes to (undoable on V1 *and* V2). V2 was deliberately outside the history for a long time (rationale: it's rebuilt from a rule by Analyze/Reconstruct, not hand-edited). **That reasoning was wrong in practice** and is worth remembering as a bug class: the shared toolbar makes V2 hand-editable with the same nine tools as V1, so a track that accepts edits but silently ignores Cmd/Ctrl+Z is worse than one with no tools. If you add a fourth editable lane, give it a slice — don't reintroduce plain `useState`.
- **A pointer drag must push ONE history entry, not one per pointermove.** Edge-drag trims (`TimelineClip.handleEdgeDrag`) and crop-box drags (`CropOverlay`) update state per mouse sample; unguarded, one drag pushed dozens of entries and shoved everything else off the 50-entry stack, so undo cost one press per mouse sample *and* the edit before the drag was gone. Each gesture mints a token with `nextGesture(label)` at pointer-down and passes `{coalesce: token}` on every update; a token matching the entry already on top folds into it. Tokens must be unique per gesture (hence the module counter, not a per-clip id) or two successive drags of the same edge would merge. `undo` clears `tag` so a resumed token can't fold into a just-popped entry. **Any new drag handler that mutates clips needs this** — `AudioBedBar.handleMoveDrag` (moving an A1 clip) is the third one and mints `nextGesture('bedmove')`; the only pointermove handlers that mutate nothing are `Playhead.jsx` (seeks) and App.jsx's panel resize.
- **A trim has no commit-on-release signal, so anything user-facing triggered by one must defer to `pointerup` itself.** `TimelineClip.handleEdgeDrag`'s `onUp` only removes its listeners — it fires no final `onTrim` — and `coalesce` gives no end-of-gesture callback either (`reduceEdit` only learns a gesture ended when a *different* token arrives). So `Timeline.handleTrim` is called on every pointermove and *cannot tell* whether the drag is still in progress. Rendering a modal, toast or confirm straight from it drops UI into the middle of the user's drag. The V1 footage-loss warning is the working pattern: `App.handleFootageLoss` accumulates **signed** deltas keyed by the gesture token, arms one `document.addEventListener('pointerup', settle, {once: true})` on the gesture's first report, and decides only there. Signed is what makes it correct as well as well-timed — a drag pulled inward then back out past its start sums to ~0 and stays silent, with no snapshot of the pre-drag window. The threshold matters too (`MIN_LOSS_SEC`): pixels-to-seconds means one stray pointermove can shave a fraction of a frame, and warning about that teaches the user to dismiss without reading.
- **Dialogs do not block Timeline's Delete/Backspace key by themselves.** Timeline's keydown is bound to `document` and only skips `INPUT`/`TEXTAREA` (`Timeline.jsx`), so a modal whose focused element is a *button* leaves Delete falling through to delete a clip behind it. `RenderDialog` is accidentally safe because it autofocuses a text input; `FootageLossDialog` autofocuses OK, so it swallows Delete/Backspace in a **capture-phase** `document` listener (a capture listener on the document runs before that same document's bubble listeners, so `stopPropagation` there keeps Timeline's from ever seeing it). Any new dialog without a focused text field needs the same guard, and `App.jsx`'s Cmd+S guard list needs its open-state added.
- **A single user action must not write two lanes non-silently** — with one shared history that costs two entries, so Cmd/Ctrl+Z leaves the action half-undone. Audited as of this change: the only handler touching two slices is `handleRenderConfirm`, and all four of its writes are the `{silent: true}` dirty-flag clears, so it costs nothing. If you ever need a genuine two-lane edit, coalesce both writes under one `nextGesture` token.
- **Bookkeeping the user didn't perform must be written with `{silent: true}`.** The three post-render `dirty`-flag clears in App.jsx are the case that matters: without `silent`, the first Cmd/Ctrl+Z after every render just re-dirtied the clips instead of undoing the last real edit. Same rule for anything else the app changes on its own behalf.
- **Project-open and `handleCleared` `reset()` the history rather than pushing to it** — undoing across either would restore clips pointing at media that is gone or belongs to another project. `handleCleared` clears V1, V2 **and** A1 (A1's beds used to survive it, which left the timeline referencing `input/` files that had just been deleted).
- **Playhead/transport/ruler are ALWAYS driven by V1**, even when V2 is displayed on top. `handlePlaybackSelectClip` only syncs V1's selection when the playing clip is actually in V1's list. `focusedTrack` (lifted to App.jsx, not local to Timeline.jsx) now does double duty: it still routes the Delete/Backspace key to the right track (Timeline.jsx), AND it's what the shared toolbar row in App.jsx (`activeClips`/`setActiveClips`/`activeSelectedClip`/`setActiveSelectedId`) reads to decide which track's clips the Trim/Hold/Reverse/Speed/Crop/Duplicate/Splice/Raise controls act on. Selecting a clip on either track sets `focusedTrack` as a side effect (`handleSelect`/`handleSelect2` in Timeline.jsx); the toolbar has no separate "which track" control of its own.
- **A1 has a selection but is NOT a `focusedTrack` value, and that was a deliberate choice.** `App.selectedBedIndex` is read by **`SpliceButton` and `MoveClipButtons`** — the two tools that mean something on an audio clip — and every other toolbar control, plus the Delete/Backspace key, keeps acting on the focused V1/V2 clip. Teaching those two to read the bed selection directly is much cheaper than teaching every control a third track; removal is still the × on the bar, not Delete. **The selection is exclusive in BOTH directions:** `App.selectItem`/`selectItem2` clear the bed selection on a real pick (`id != null`), and `App.selectBed` clears `selectedId`/`selectedId2`, so exactly one clip is ever ringed and the tools that don't understand A1 read "select a clip" rather than silently acting on a clip with no ring. It only became exclusive when Move joined Split; before that two rings could show at once, which is why A1's is **sky** (matching the Split button) against `TimelineClip`'s white. Two more things to know: playback's follow-the-playhead selection goes through `setSelectedId` directly, so it deliberately does *not* clear the bed selection (**that is the one path that can still put two rings up** — a bed selected while playback rings the clip under the playhead; Move and Split still follow the bed); and nothing acts on the index without checking a clip is there — `selectedBed` for Split, `beds[selectedBedIndex]` in `MoveClipButtons` — so an index left pointing past the end of a shorter lane (undo, project open) degrades to "nothing selected" instead of to the wrong clip.
- **The A1 array's ORDER is load-bearing, so moving a clip has to re-sort the lane and hand back the moved clip's new index.** Both normalizers — `clipMath.normalizeBeds` and `ffmpeg_utils.normalize_bed_placements` — clamp each bed forward to the *previous* bed's end **in array order**, not in time order, because the render concatenates A1 into one stream (`a1_bed_source`) and so cannot represent overlap at all. An out-of-order array therefore doesn't just look wrong, it silently shoves clips later. That rules out both alternatives you'd reach for first: a drag can't overlap, and it can't ripple neighbours aside either (removal moves nothing, so a move shouldn't). `clipMath.moveBed` instead snaps to the nearest start where the clip *fits* — hence dragging left until it stops closes a hole exactly — then returns `{beds, index}` re-sorted by start. Two things fall out of that: **identity on A1 is position** (the same file can sit on the lane twice), so the caller must move the selection to the returned index or the ring jumps to a different clip; and the drag recomputes `moveBed(snapshotTakenAtPointerdown, ...)` from scratch on every pointermove rather than accumulating, because a hop past a neighbour changes the index mid-gesture and any remembered index would be stale by the next sample. Dragging home is then a real no-op — `moveBed` returns the same array reference and `reduceEdit` bails, costing no undo step. The one edit on this lane that *does* move a clip other than the selected one is the toolbar's swap (`clipMath.swapBeds`, behind Move ◀ ▶ and `⌥←`/`⌥→`): the selected clip and its neighbour exchange places, and it is safe with no `fits` test at all precisely because the pair keeps the span it already occupied — both outer edges, and the gap between them stays between them — so the two clips cover the same stretch of lane as before and the normalizers have nothing to clamp, whatever the durations are. Don't "simplify" it into a start-anchored move: letting the far edge fall where the durations put it brings the collision case back and needs the legality test with it.
- **Split's A1 branch reads the playhead through a REF, never through state.** `SpliceButton`'s own comment records that a playhead readout was removed from this toolbar because it re-laid the row out every frame — so lifting the ~15 Hz `timelinePos` into App to feed the A1 split point would reintroduce exactly that. Instead `Timeline` assigns `laneClockRef.current = () => transport.getTimelinePos() - sequenceVideoStartSec(clips)` during render (the pattern `AudioBedPlayer` already uses for its own refs), handing out **lane seconds** — the frame `bed.startSec` lives in — and `apply()` re-reads it at click time so the cut lands where the playhead *is*, not where it was at the last tick. The 150 ms interval in that component exists only to refresh the *enabled* state while a bed is selected (a seek landing on the same source frame, e.g. inside a hold, fires no `timeupdate`), and it is gated on `selectedBed` so it never runs otherwise.
- **Playback is a rAF scrub loop** setting `videoRef.currentTime` each tick — the `<video>` never natively plays during timeline playback, so **the clips' own audio does not play in preview**. The one exception is the **A1 bed**, which is a separate `<audio>` element that really does play, slaved to `transport.getTimelinePos()` (`AudioBedPlayer`) — that's why it's timeline-locked and survives mid-sequence holds/reverse/slow-mo. The one offset it honors is V1's picture start: source time is `timelinePos - startSec + inSec` (the clip's own `inSec`, so a half of a split clip plays the part of the file it kept), and outside its own stretch — before its turn, inside the first clip's head hold, or past its played length — the element parks paused at its `inSec`, matching the render's leading silence and keeping it out of the `ended` state, where a `play()` would loop the file under the rest of the sequence. It mounts inside the Timeline subtree, so it goes silent on the AGENT/Reformat/Actions tabs. `displayClips` is read via a ref so mid-playback visibility toggles apply next frame; any change to V1's clip array stops playback.
- **Never animate from `MediaContext.currentTime`** — it comes from `timeupdate`, which fires at ~4 Hz. Anything that has to track the playhead smoothly (overlay preview, the A1 bed player) needs its own rAF loop reading the transport directly.
- **A frame grab must crop to `activePreview.info`'s size, not to `videoWidth`/`videoHeight`** — the same trap `PreviewPlayer`'s clip-path exists for. Some encoders pad the coded picture out to the next 16px macroblock boundary without signaling a crop, and the browser reports those padded dimensions, so a naive `drawImage(video, 0, 0)` bakes the fringe the preview hides into the PNG. `FrameGrabButtons.grabCanvas` therefore draws the source rect `(0, 0, trueW, trueH)`, capped at the coded size. Verified live in headless Chrome against the dev server (`002_0120.mp4`, coded 2206×946): the offset draw produced the expected 2198×938 canvas, `getImageData` read back fine (**never tainted** — every source is same-origin through the Vite proxy), and `toBlob` yielded a 1.1 MB `image/png`. Two other measured details: the clipboard path must hand `ClipboardItem` the **`toBlob` promise, not an awaited blob** (WebKit only honors `clipboard.write` inside the click's own turn, and both engines accept `Promise<Blob>`), and the download's object URL must be revoked on a timeout rather than synchronously or WebKit can cancel the download mid-read. What the capture does NOT include: V2 overlay layers and the crop box, which are sibling DOM elements over the `<video>`, not pixels in it.
- **`displayName` is a LABEL, everywhere — never an identity.** Media resolves by `sourceName` + `sourceDir`, and `analyzeMath.keyForClip` detects duplicates structurally (`sourceName|inSec|outSec`), so Duplicate is free to rename the pair `_a`/`_b` without touching what renders or what Analyze/Reconstruct decide. The only readers are cosmetic: `EdlTable`'s REEL column, the warning strings in `analyzeMath`/`overlayMatch`, and the `.edl` export — which **truncates the reel to 8 characters** (`App.jsx`), so a long name loses the suffix there. `clip.isDuplicate` is the same kind of field: it draws the ⧉ marker and nothing else, it never reaches ffmpeg (the server reads clip specs key by key with `.get()`, ignoring extras), and it needs no `.nara` version bump because `buildProject` serializes clips wholesale — an older project simply has no flag and draws no marker. Don't promote either one into a decision the render or the V2 tools read.
- **Duplicate's `_a`/`_b` suffix regex is single-letter ON PURPOSE.** `duplicateNames` (clipMath.js) strips `/_([a-z])$/` to find a name's family; the tempting `/_([a-z]+)$/` would read the `_video` in `my_video` as a suffix and rename that clip to `my_a`, silently destroying a name the user chose. The cost is a 26-member ceiling, past which the copy falls back to the numeric split scheme keyed off the family root (`v01`, not `v_a01`) — which cannot collide with any letter name. It also fills the first free letter rather than counting members, so deleting `_b` and duplicating again reuses `_b` instead of drifting to `_d`. Both properties are pinned by node tests.
- **CLIP_PALETTE class names must stay literal strings** (comment at clipMath.js) — Tailwind v4's scanner can't generate template-interpolated classes like `` `from-${c}-700` ``.
- **Speed math has two directions**: `clipMainSec` DIVIDES by speed (timeline length stretches when slowed); TimelineClip edge-drag MULTIPLIES the pixel delta by speed (screen pixels are timeline seconds; a slowed clip covers less source time per pixel).
- **Timeline pixel constants must stay in sync**: `GUTTER_PX=48` ↔ the `w-12` gutter, `TRACK_PAD=8` ↔ the lanes' *and the Ruler wrapper's* `px-2`. **`GAP` is 0 and must stay 0** (`Timeline.jsx:18`, mirrored by `clipMath.GAP_PX`): a flex gap eats width but carries no time, so any non-zero value scales a lane by its own clip count and V1, V2 and the Ruler stop agreeing — at 2px a 6-clip V1 drew 10px (4 frames) long while a 1-clip V2 drew true, which is how a V2 file one frame *longer* than V1 ended 7.5px *short* of it and its end read frame 356 (AUDIT #18). Changing lane spacing requires updating `playheadPx` and `clientXToTimelinePos` together.
- **`sequenceSec * pps` is NOT the width of the V1 lane** — anything that must sit under V1 has to be measured with `sequencePosToPx`/`sequenceClipBounds` (clipMath.js) instead. `TimelineClip` floors each clip's box at `MIN_CLIP_PX = 24`, so a sub-0.4s clip is drawn wider than its duration. A single continuous span therefore drifts left of the picture, accumulating per clip — which is exactly how the A1 bed came to not sit under the frame it plays with. Head/tail holds need no special case in that math (they're already inside `clipTotalSec`), but a floored clip's *interior* must be scaled by its rendered width, not by `pps`. Kept deliberately separate from `timelinePosToPx`, which drives the playhead and ignores the floor — don't merge them without re-verifying the playhead against the clips.
- Deleting or reordering ANY clip marks ALL remaining clips dirty — the rendered sequence changed even though individual clips didn't.
- **"Move a clip" means REORDER, and array order is the entire representation of it.** V1/V2 clips carry no position field; `build_timeline_filter` concatenates them in payload-array order, so moving a clip is `moveClip(clips, from, to)` (clipMath.js) and nothing else — no positions, no gaps, no black/silence filler, no `.nara` version change, **no backend change at all**. Shown, not assumed: dumping the filtergraph for order [A,B,C] vs [C,A,B] gives the *same multiset of 13 chains*, only re-slotted, with a byte-identical `concat=n=3` node. All four surfaces route through that one helper so they can't disagree — toolbar `MoveClipButtons`, `⌥←`/`⌥→` (Timeline's keydown, matched *before* the plain-arrow frame steps and gated on `!e.metaKey && !e.ctrlKey`), the lane drag, and `EdlTable`'s ▲▼. `moveClip` returns **the same array reference** for a no-op or clamped move, which is load-bearing: `reduceEdit` bails on `next === present[key]`, so ⌥← on the first clip costs no undo entry and sets no dirty flags. Two consequences to keep in mind: `applyMove` must read the *rendered* `clips` array (so the keydown effect's deps list `clips`/`track2Clips`, not `clips.length` — a stale array would freeze into the handler), and a reorder **strips** a head/tail/round hold stranded off an outer slot rather than transferring it (`sanitizeHoldPlacement` zeroes violators — pre-existing behavior of every reorder/add/split/delete, easy to mis-remember as a transfer).
- **The drop index is not the hovered index.** `dropTargetIndex(from, overIndex, side)` = `side === 'after' ? overIndex + 1 : overIndex`, **then `if (from < to) to -= 1`** to account for the hole the dragged clip leaves behind. The old `handleDrop` spliced at the hovered index with no correction, so dragging rightwards landed one slot short — the classic off-by-one that reads as "it didn't go where I put it". `side` comes from the **cursor against the clip's own rect** (`e.clientX < rect.left + rect.width/2`), not from the index, which is what lets a 24px-floored clip still be dropped on either of its edges. The insertion line is drawn at the boundary this formula resolves to, so what you see is where it lands — pinned by an exhaustive node test over every `(from, overIndex, side)` triple of a 5-clip array against a naive remove-then-insert reference.
- **Edge auto-scroll during a drag must be a rAF loop, not a `dragover` handler.** Native HTML5 `dragover` **stops firing while the cursor holds still** — which is exactly when the user has parked at the lane's edge waiting for it to scroll. So `dragover` only records cursor X into a ref and a `requestAnimationFrame` loop (started on drag start, stopped on drop/`dragend`/unmount) nudges `scrollerRef.current.scrollLeft` while that X sits within `EDGE_SCROLL_PX` of an edge. The listener is one handler on the scroller div, not per lane: `dragover` bubbles, so it covers ruler + V1 + V2 + A1, and it avoids fighting the `v1FileDragProps` spread whose own `onDragOver` early-returns for non-file drags.
- **Three different overlays can appear over the same lane, so the reorder line has its own color.** Playhead = 1px `bg-red-500`; a file drag washes the lane `bg-indigo-950/40`; V1 selection is a white ring and A1's a sky ring — the insertion line is 2px **`bg-teal-300`**, matching the teal Move buttons and EDL arrows. It straddles the seam between clips (`left/right: -1`, half of its 2px width on each side) so it reads as a boundary rather than as part of either clip. It used to sit *inside* a 2px inter-clip gap at `-2`; that gap is gone (see `GAP` above). Don't recolor it red or indigo.
- **`data-clip` on `TimelineClip`'s root is how the lane tells "over a clip" from "past the last clip".** `dragover` bubbles from the clip to the lane to the scroller, so the lane handler can't otherwise know whether a clip already claimed the event; `isOverAClip(e)` (`e.target.closest('[data-clip]')`) gates the drop-at-the-end path (`dropAt = '1:end'`). Ordering matters: a drop on a clip clears `dragFromRef` first, and the lane's handler is gated on that ref being non-null, so the bubbling lane drop can't apply the move a second time. The lane's `dragLeave` also clears `dropAt`, or dragging out of the lane leaves a stale line behind. Both `handleDragOver`/`handleDragOver2` are gated on *their own* track's `dragFromRef`, so a file drag or a cross-track drag never lights a misleading line.
- **A reorder does not retroactively re-cut V2.** `analyzeAgainstV1`, `batchCutAgainstV1` and `reconstructFromV1` all read the live V1 array **at click time**, so a reorder is honored by the *next* run of any of them with no extra wiring — verified: reordering V1 turned Analyze's segments from `0-2,3-4,5-8` into `5-8,0-2,3-4` and `sequenceCutOffsets` from `2,3` into `3,5`. But the V2 clips already on the lane are the output of an earlier run and don't move themselves, so **re-run V2 Analyzer after reordering V1**. This is why the EDL rows got ▲▼ at all: that list is the order those three tools read.
- **Reconstruct now reads V1's ORDER as data, and a post-render reorder scrambles it undetectably.** V2's round-tripped file was written by a render of V1 *as V1 stood then*; `reconstructFromV1` cuts and un-moves it against V1 *as V1 stands now*. Reorder V1 after that render and every boundary lands on the wrong frame — and **no length check can catch it**, because a permutation preserves the sequence's total duration, so `overflow` and `leftoverSec` are both 0 and the output looks perfectly plausible. The old flat Reconstruct was accidentally immune (it only ever read holds, all symmetric over the array); reversing moves is what trades that immunity away. The only proxy available today is V1's own `dirty` flags — a reorder marks clips dirty, a render clears them — so `handleReconstruct` warns when `hasDirty`, and the tooltip/About copy states the precondition. The real fix is to stamp V1's piece-length vector onto the V2 clip at render time and compare; that is a new clip field plus a `.nara` version bump, deliberately not done here.
- **A V2 clip does not know its V1 clip unless the analyzer stamped it.** `v1Id`/`v1Name` (`analyzeMath.v1Provenance`) is the ONLY link, and it must be written by every path that emits V2 segments — `analyzeAgainstV1`, `batchCutAgainstV1`, `reconstructAgainstV1`. Add a fourth emitter and forget it and the 1+ render's **V1 name** silently falls back to the V2 file's own name, which is the bug the stamp was added to fix (0.59.0): the box was named *V1 name* but in A mode named files after V2's clips, so a whole batch came out `Video01-analyzed_01`, `_02`… instead of the shot codes under them. Do NOT re-derive the link by index — `analyzeAgainstV1` drops clips past V2's end, `batchCutAgainstV1` merges colliding cuts and appends untouched extra V2 clips, and Reconstruct welds several V1 clips into one range, so segment i is not V1 clip i in any of the three. The stamp is spread LAST in each emitter, after `...v2c`, or a re-analyze inherits the previous run's provenance.
- **A fused V2 clip is ONE clip drawn over N lane entries, and `fuseId` is provenance — never the source of truth.** Reconstruct's output has to be one seamless clip (the user's requirement, and no render pass is allowed at that point), but the ranges it emits are *by construction* non-adjacent in V2's file and a clip object holds one IN/OUT pair. So the entries are stamped with a shared `fuseId` and **coherence is re-derived on every read** by `clipMath.fuseGroups`: adjacency in the array plus agreement on `reversed`/`speed`/`crop`, and a run of one is not fused at all. That direction matters — a stored-and-maintained group would need a sanitize pass, which would break `moveClip`'s same-reference no-op contract, and would go stale the moment a `{...clip}` spread copied the id (`batchCutAgainstV1` spreads V2's clip, so it sets `fuseId: null` explicitly). Consequences to keep straight:
  - **Count groups, not entries, everywhere a V2 clip count is shown or acted on**: `App.renderShots` (one group ⇒ one file, and its hold-zeroing rule applies to the group's ends, not each member's), the RenderDialog `shotCount` (whose number also sets `shotOutputNames`' zero-pad width) and the `shotStems` beside it (`App.shotStemsFor` names each file after its group's FIRST clip, the one whose name the fused box shows — the dialog cross-checks `shotStems.length === shotCount` and hides the **V1 name** box if a caller ever disagrees, so a per-entry list would silently cost the feature rather than misname a file), the `1 / 1+` toggle label, and the "V2 held N clips" warnings. `fuseGroups` is safe to call on V1 too — no V1 clip carries a `fuseId`, so it returns one group per clip.
  - **The three V2 tools refuse a fused clip outright** rather than operating on `track2Clips[0]`, which is only its first range — otherwise one box comes back with half of itself re-cut. `App.fusedV2Blocks` points the user at V2 Render mode `1` to flatten it into a real file first.
  - **Delete is atomic, drag/move is not.** A box that draws as one clip must delete as one clip in one undo step (`Timeline.handleDelete2` via `fuseGroupIds`); dragging a member out is the deliberate way to break a run, and it self-heals because the adjacency check simply stops matching.
  - **Closing a seam is free now, but was not.** The lane's flex gap is 0 (see `GAP` above), so a group wrapper no longer changes lane width at all. While the gap was 2px, wrapping a run cost 2px of lane width per boundary it closed, and that was safe **only** because nothing aligns under V2 — `Ruler`, `Playhead` and `AudioBedBar` all measure V1. The wrapper survives for the other reason: a group has exactly one name, duration, badge set, delete × and selection ring. Do not reintroduce a lane gap to space groups apart — re-read the `GAP` entry above first.
  - **A run splits where members disagree on `reversed`/`speed`/`crop`**, which is correct rather than a bug to fix: one box carries one ◀ badge and one duration, so fusing a reversed range to a forward one would make the label lie. A mixed-`reversed` Reconstruct therefore lands as more than one box — and since 0.27.0 so does a **mixed-speed** one, because un-stretching gives slowed shots a different `speed` from un-slowed ones. `handleReconstruct` must therefore ask `fuseGroups` how many boxes it produced instead of telling the user "ONE clip": the earlier requirement that a reconstruction present as one clip holds for a uniform-speed V1, which is the common case, not for every V1.
  - `FUSE_BOX`/`FUSE_FILL` in `TimelineClip.jsx` must stay **literal** Tailwind strings (`rounded-l`, not `rounded-${side}`) — v4 scans source text, so an interpolated class is purged and the seam reopens **in a production build only**.
- Keyboard shortcuts are suppressed when focus is in an INPUT/TEXTAREA; Delete removes the selected *part* (hold segment) rather than the clip when a hold is selected.
- OutputPanel auto-loads the newest output when `files.length` changes (deliberately `files.length`, not `files` — eslint-disabled).
- **The V2 action buttons are labeled "V2 Analyzer" and "V2 Reconstruct"** (Timeline.jsx `actionsBar` + AboutDialog's numbered list) — renamed from the old "Analize" (sic) / "Reconstruct". The prop and handler names did NOT change (`onAnalyze`/`handleAnalyze`, `onReconstruct`/`handleReconstruct`), and neither did the feature's name in prose ("Analyze & Reconstruct"), so grep for the label text, not the identifiers, and change both copy sites together.
- **Never animate anything from `MediaContext.currentTime`.** It's fed by the `<video>`'s `timeupdate` event, which is throttled to **~4Hz** — hand-measured at 3.76Hz (Chromium 151, a near-perfect 265.6ms metronome), 3.99Hz (WebKit 26.5), 3.82Hz (Firefox 153, max gap 290ms). A crop box panning 400px over 4s therefore teleports in **~26.6px jumps** and can only ever occupy 15 of the 400 columns it crosses — this was the actual cause of juddery crop-keyframe motion. `CropOverlay`'s animated box now reposition itself from a **rAF loop reading `video.currentTime`** (measured 60.00Hz on a 60Hz display, 120Hz on ProMotion → 1.67px steps, ~16× smoother), writing `style.left/top` imperatively like `Timeline.positionPlayhead` does. Two non-obvious requirements: the loop must write **unconditionally every frame** (React still re-renders at timeupdate's 4Hz and puts the stale `displayX` back into `style.left`, so memoizing "unchanged" samples reintroduces the judder), and it must suspend while a pointer drag owns the box (`draggingRef`) or the loop and the cursor fight over position. `requestVideoFrameCallback` is the wrong tool here (capped at the source frame rate — 30Hz, 3.33px steps, and only 23.6Hz in Firefox); the box is CSS-composited, so it should move at display rate, not decode rate.
- **Crop keyframe `t` is relative to `inSec`, so every trim must rebase it** via `cropAnimation.retimeKeyframesForTrim` (wired into `Timeline.handleTrim`/`handleTrim2` and `TrimForm.apply`/`reset`). Without it a trim silently slides the pan onto different frames, and — worse — leaves keyframes past the shortened body, which `app.py` bounds-checks and **rejects the whole render** for (the edit looks fine until Render fails). Keyframes falling outside the new window are replaced by a single one at the boundary carrying the curve's own interpolated value there, so the retained span of the pan survives exactly. It returns the same array identity when nothing moves, so callers don't set a needless dirty flag.
- **A crop resize must clamp against the FURTHEST keyframe, not the visible one.** One box size is shared by every keyframe (by design), so growing the box while parked on a keyframe near x=0 can push a later keyframe past the frame edge — same render-rejection failure as above. `CropOverlay.handleResizeDown` caps the drag using `cropAnimation.maxKeyframeOrigin`.
- **ffmpeg's `crop` filter silently clamps an out-of-range `x`/`y` — exit 0, no warning at any loglevel** (verified to `-v debug`). A ramp that runs past `in_w - out_w` just freezes hard at the edge. So keyframe range must be validated *before* render; no ffmpeg diagnostic will ever tell you. Contrast the *other* failure mode: an unbalanced-paren expression is a HARD failure (exit 234, `[Eval] Missing ')'`, zero output) — since these ladders are generated programmatically, a value bug fails silently while a syntax bug fails loudly. Also verified: `crop` re-evaluates `x`/`y` per frame (not stepped), nested `if(lt(t,...))` ladders parse correctly to at least 64 levels / ~2.5KB, and **yuv420p floors `x`/`y` to even** (`lrint(expr) & ~1`) so odd offsets are unreachable — `exact=1` restores 1px granularity, at a quality cost, and the project does not currently pass it.
- **V2-as-overlay REPLACES the composite decision, so `displayClips` must not swap tracks.** Normally `Timeline.displayClips` makes a visible V2 *replace* V1 in the shared `<video>`. When `overlayMatch` resolves any pair to an overlay, that's wrong twice over: the shared element must keep decoding V1 (there'd be nothing to composite onto otherwise), and the V2 picture is drawn over it by `OverlayPreview`'s own second `<video>` element instead. One `<video>` decodes one file, so a true composite needs two elements — the overlay follows the main one's clock (`play()`/`pause()` mirrored, `currentTime` nudged only when it drifts >0.12s during playback so it isn't the choppy per-frame-seek scrub path), and hides outside its own range to mirror `eof_action=pass`. `v1Visible`/`v2Visible` are lifted to App.jsx (like `focusedTrack`) so the overlay layer honors the same eye toggles as the lane.
- **The overlay preview and the render must share the sampling math, not merely agree.** `OverlayPreview` positions its PiP with `cropAnimation.sampleCropOrigin` and `box.width / sourceWidth` — deliberately the same function and the same scale factor `CropOverlay` uses for the crop box, since the overlay has to land exactly where that box was drawn. Verified against real renders: preview samples matched the positions ffmpeg actually produced at every checked time (100/450/800/1150/1480 px), within the sub-pixel difference from yuv420p's even-value floor.
- **A/B mode renders from a DIFFERENT match than the preview shows, and that's intentional.** App.jsx derives two sets from the same clips: `overlays = matchOverlays(v1, v2)` drives the live preview, and `abOverlays = matchOverlays(v1, v2, { fullFrameSameSize: true })` is used only by an A/B render. They differ in exactly one case — a V2 clip whose resolution *equals* V1's. The preview keeps its long-standing full-frame-replacement behavior there (swap tracks, no compositing), while A/B treats it as an overlay at 0,0 covering the frame, because that's what "render V2 over V1" means for two same-size clips. So a same-size A/B render is not previewed as a composite; it doesn't need to be, since the result is pixel-identical to the V2 clip alone (verified bit-exact, 72/72 frames). Don't "fix" this by pointing the preview at `abOverlays` — that would make a visible same-size V2 stop replacing V1 in the preview, breaking Analyze/Reconstruct round-trips, which are the common case.
- **A 1+ shot series equals the joined render frame for frame — but only because the shots share a size.** Verified: 4 shots (head hold, reverse, 0.5× slow-down, tail+round hold) laid end to end matched the single joined render on **180/180 framemd5 hashes**, audio durations summing exactly (1.5+1.0+2.0+1.5 = 6.0s). The equality holds because `render_timeline` derives `target_w/h/fps` **per render**, so a track whose clips differ in size deliberately renders differently split than joined: measured, a 160×120 cropped clip renders 160×120 as its own shot and 320×240 (padded) when joined to a 320×240 clip. That's the intended reading of "unique shots" and it's stated in the render dialog — don't try to make the split match the joined render's frame by forcing a target size onto each pass, and don't claim byte-equality for a mixed-size track. Two more per-file consequences: a size-capped quality mode budgets **each shot** under the cap (N files, N budgets), and each shot's audio gets its own AAC frame boundaries (packet counts sum to 261 vs the joined 259 — encoder padding at each split, not drift).
- **Renaming a file is REFUSED while the timeline points at it, on purpose — in BOTH bins.** A clip resolves its media by filename (`sourceName` + `sourceDir`), so renaming a file any V1/V2 clip — or the A1 bed — references would orphan it, and the only symptom would be an ffmpeg failure at Render. That includes **Export Bin** files: a chat edit or Reformat re-points the selected clip at the render it just produced (`sourceDir: 'output'`). `App.jsx` derives both sets from one `inUseNamesFor(dir)` helper — `inUseSourceNames` for `MediaLibrary`, `inUseOutputNames` for `OutputPanel` — kept separate because a same-named file in the other folder is not the same file. Each panel's `handleRename` blocks on its own set rather than rewriting `sourceName` across the clip list: a silent relink would leave every undo step behind it pointing at the old, now-nonexistent name. Still unavoidably broken by a rename: a **saved `.nara` project** that used the old name; nothing in the client knows which projects reference which files. **Three** per-file states are keyed by filename and so must be carried over by hand on a successful rename — the ★ (`fileList.renameFavorite`, called by whichever panel owns that `favorites` state), the sticky V1/V2/A1 track tag (`fileList.renameTrackTag`, owned by App via `MediaLibrary`'s `onRenamed`), and the bin folder assignment (`fileList.renameBinFolderFile`, via `useBinFolders`' `carryRenamedFile` — in **both** bins as of 0.57.0, each against its own scope). Anything new that keys off a filename joins that list. The **Project Library**'s own Rename has the same obligation for the same reason, against `scope: 'projects'` (0.63.0): a renamed project would otherwise drop out of its folder back to the top level — and unlike a media rename, that one is never refused, since a `.nara` is not a clip source.
- **Bin folders are virtual for exactly the reason above, and must stay that way — in both bins.** They group files in the UI; `input/`/`output/` stay flat and no file ever moves. The Export Bin's are no different: a clip whose source is a render resolves it by bare filename too (`sourceDir: 'output'`), so filing a render must not touch its path either. Making them real subdirectories would turn `cam.mp4` into `B-Roll/cam.mp4`, which *is* a rename as far as `sourceName` is concerned — so the drag would have to be refused for any file on the timeline, i.e. precisely the files worth organising, and it would silently break saved `.nara` projects the same way a rename does. It would also need `_list_dir` to recurse (it skips directories today), a `<path:>` converter on `/api/probe/<name>` (the only media route without one), a move endpoint, and path-safe encoding in `useTimelinePlayback.js` and `OverlayPreview.jsx`, which both do `encodeURIComponent(clip.sourceName)` and would turn the separator into `%2F`. The virtual model needs none of it and costs only Finder visibility. If real folders are ever genuinely wanted, the prerequisite is a stable per-file id that clips reference instead of a filename — not a bigger rename guard.
- **An `<input>` inside a list that owns a `keydown` handler will bubble into it.** The bin's folder-rename input sits inside the `<ul>` whose `handleKeyDown` maps Delete/Backspace to "delete the selected file from disk" — so typing a folder name would delete files. `handleKeyDown` bails on `e.target.tagName === 'INPUT'` and the input also `stopPropagation`s. The guard is deliberately on the tag, not on `e.target !== e.currentTarget`: the ★ button doesn't focus the list, so arrow keys legitimately arrive from a child. Related: **Escape-to-cancel an inline rename can't be read from state**, because removing the focused input is itself what fires the blur that commits — hence `cancelEditRef`, a ref so the blur handler in the same tick sees it.
- **A superseded request is dropped with a sequence ref, NOT an `AbortController` — and that is deliberate.** `probe()` replies land in whatever order the backend finishes them, so a slow reply for an earlier click used to overwrite a newer one and describe the wrong file under the right name (finding #10, measured in **both** bins; `OutputPanel.loadOutput`'s copy was worse because its `setSelectedName` sits inside the `.then`, so the stale reply dragged the highlighted row back too). Both `MediaLibrary.selectFile` and `OutputPanel.loadOutput` now take a ticket (`const seq = ++probeSeqRef.current`) and their replies return early unless they still hold the newest one. Aborting instead would *regress* the UI: `api.js`'s `apiFetch` takes no `AbortSignal` and turns any fetch rejection into `ApiError('cannot reach the backend — is the server on 127.0.0.1:5001 running?', 0)`, which `main.jsx`'s global `unhandledrejection` handler alerts — so every superseded click would raise a false "server is down" alarm. Teaching `apiFetch` to tell `AbortError` from a dead server is a change to the transport every call in the app shares. Cost of the guard, knowingly accepted: the in-flight request still runs to completion, it is only its answer that is discarded. **Every place a panel empties itself has to bump that ticket too (0.44.0, AUDIT #14)** — `OutputPanel`'s `handleDelete`, `handleClear` and its `files.length === 0` branch cleared `selectedName`/`info` without it, so a probe already on the wire repopulated the panel (highlighted row, Media Info Out, Download target and the `<video>`) for a file that had just been deleted. #10 added the ref for the click race only. The rule to keep: *the newest ticket wins*, so anything that invalidates what the panel shows takes a ticket, not just anything that asks a question.
- **A `loadeddata` wait needs a paired `error` listener, or playback wedges forever.** `useTimelinePlayback` cannot start a segment until the element has the frame, but a `<video>` whose file is missing/renamed/unreadable fires `error` and *never* `loadeddata` — so the engine sat in `playing` with the position frozen and nothing reported (finding #10). Both start paths (`startNativeAt`, `freezeStart`) go through one `whenLoaded(v, gen, clip, onReady)` that registers both events and removes both. Two non-obvious requirements in its failure branch: it must **clear `loadedUrlRef`** (that ref caches which URL the element holds so a contiguous clip skips the reload; left set after a failed load, a later Play treats the element as already pointed at that file and never re-attempts it, so restoring the file still wouldn't play it), and it must `stop()` *before* reporting so the transport is consistent when the message appears. The report is a `⚠` line in the Actions log naming the file — deliberately not an alert, since a dialog mid-playback has to be dismissed before anything else can happen and the failure is diagnostic, not a decision.
- **`ended` is the hand-off signal at the end of a file; `EPS_SRC` cannot be, at any value.** `runNative`'s frame loop only advances while frames keep arriving, and a clip trimmed to the very end of its file runs out of frames *before* the `outSec - EPS_SRC` hand-off is satisfied: a 2.000 s @24 fps file presents its last frame at **1.9583 s** against a threshold of 1.96, so `step` took the "still inside" branch, asked for one more `requestVideoFrameCallback`, and got `ended` instead — element `paused=true`, engine still `playing=true`, playhead frozen mid-timeline, nothing reported (AUDIT #14; identical on pre-#10 code). `EPS_SRC = 0.04` is deliberately left alone: it is one frame at 30 fps, widening it to cover 24 would cut a frame off every 30 fps clip, and no fixed tolerance covers every frame rate (25 fps lands on 1.96 exactly). So each native driver arms an `ended` listener that calls `step()`, and `step` treats an ended element as *not* inside the body — an element that has run out will never present another frame, so scheduling another rVFC is the stall itself. Two requirements: the listener needs **its own cleanup slot** (`endedCleanupRef`), because `listenerCleanupRef` holds short-lived listeners that are cleared the moment they fire while this one must stay armed for the whole driver, and `cancelLoops` must disarm it or drivers accumulate listeners. Measured with the real hook under node against an A/B copy differing only by this change: 24 fps went from `STALLED, playing=true, pos=1.9167` to running to the end of the timeline, while 30 fps, 25 fps and a clip trimmed short of its file's end are frame-for-frame unchanged, `ended` listeners left = 0, never more than 1 attached.
- **The Actions log only exists in the DOM while the Actions tab is open** — the centre dock swaps its children rather than hiding them. So `setAnalyzeLog` lines are retained but invisible to a user sitting on another tab, and any *automated* read of the log has to switch tab first (which also means nothing in it can be read during playback). Anything that must be seen at the moment it happens cannot be a log line.
- **"Unsaved work" is one fingerprint, not a boolean flag** — `projectWork.workFingerprint` (sorted-key JSON of V1 + V2 + A1 + room tone's switch and level, i.e. exactly what a `.nara` stores). `App.savedWorkRef` is re-baselined on save, save-as, project-open and `handleCleared`, always **from the payload/normalized values that were written or read**, never from state a render later touches — which is what keeps a clean re-open from prompting. Three deliberate exclusions: `dirty` is normalized out of every clip (it means "not yet rendered", so a Render would otherwise read as unsaved work the user never did), the selection is not work, and export presets are not work (opening a project *merges* them, so they survive). Anything new that a save writes has to join the fingerprint or opening a project will silently discard it.
- **A multi-file drop must cost only the files that fail.** `Timeline.addFilesInOrder` (shared by `handleV1Files`/`handleA1Files`) keeps the sequential `await` — order is load-bearing, since each `add` appends, so parallelising with `Promise.allSettled` would land clips in completion order — and collects failures instead of throwing out of the loop, then reports once naming each file. Swallowing each error there is also what keeps `main.jsx`'s global handler quiet, so the user sees the one message that names the files rather than a transport error that names none. Before this, a mid-drop failure abandoned every file after it as well.
- **Chat edits only reach the timeline via `handleEditResult`'s clip-swap** (App.jsx): `/api/execute` reports which file its command actually wrote (`_output_arg_info` in app.py, parsed from the validated argv's output path — never guessed), and if a clip is selected, `App.jsx` reprobes that file and replaces the selected clip's source/dimensions in place, resetting trim/hold/reverse/speed/crop (the chat edit is now baked into new pixels, same treatment Reconstruct gives a "fresh" source). Before this, a Run only ever produced a new file in Exports with zero effect on the clip being edited — don't regress this by having `onResult` go back to a no-arg `refresh()`-only callback.
- **Merge's collapse is frame-exact, and the seam frame is not doubled or dropped.** `clipMath.mergeClips` replaces two adjoining clips with one spanning clip; the worry is `trim=end=3` and `trim=start=3` both claiming the frame at pts 3. Measured lossless against the live server on 24 fps footage: clips `0–3` + `3–7` and one clip `0–7` produce **identical framemd5 lists, 168 frames** (= 7 s × 24), and the same held for the reversed pair. So `end` is exclusive and `start` inclusive, and the collapse is a true no-op on the pixels — which is what lets Merge silently rewrite two clips into one.
- **A merge that CAN'T collapse is not a failure, and must not be made one.** Different source files, a gap between the ranges, or a retime/reverse/crop on only some members means the data can't become one clip — so `mergeClips` falls back to a shared `fuseId` and the run draws and renders as one anyway. Refusing instead would break the commonest reason to merge (gluing two different shots into one deliverable). Consequence to keep in mind: **V1 can now carry `fuseId`** (`.nara` version 9), so nothing may assume `fuseGroups` is a no-op on V1 — `Timeline.handleDelete` deletes the whole run, the A/B `1+` shot count reads `fuseGroups(clips)`, and both lanes draw through the shared `ClipGroups`.
- **`fuseGroups`' agreement rule applies to RECONSTRUCTED runs only, and relaxing it for merges was the point.** Members of a run sharing a `fuseId` must agree on `reversed`/`speed`/`crop` — unless the run carries `fuseMerged: true`, which only `mergeClips` sets. That check was never a render constraint: `renderShots` posts a group as a **multi-clip payload**, so the server honours each member's own speed and direction (measured: `0–2s @50%` + `2–5s @100%` in one payload → 7.000 s / 168 frames = 96 + 72, exactly the per-member arithmetic). It existed purely so one box couldn't print one ◀ badge and one speed over members that disagree — which `ClipGroups` now handles by printing `⇄` and `· mixed` instead. Don't re-tighten it, and don't loosen it for Reconstruct either: a mixed-speed reconstruction coming back as one box instead of one box per run would change how many files its `1+` render writes.
  - **Collapse still needs uniform speed and direction**, unlike a group, because a single clip holds a single `speed` — collapsing a 50% clip onto a 100% one would silently retime half the footage. `canCollapse` checks this itself now; it used to rely on the caller, which stopped checking when mixed merges were allowed.
- **Merge's second selection is deliberately outside the one-selection-per-track model.** Shift-click adds to `App.mergePicks` and does **not** move `selectedId`/`selectedId2` or the playhead; every other tool still reads exactly one selected clip and needed no change. The picks are stored WITH their track (`{track, ids}`) rather than cleared by an effect on `focusedTrack` — shift-clicking a V2 clip while V1 is focused both moves the focus and makes a pick, and an effect watching `focusedTrack` runs after that render and would wipe the pick the click just made. A shift-click also falls through to an ordinary select when there's no primary selection yet or the clip is on the other lane, so Shift can never leave a pick list with nothing to merge it with.

## Security / safety model

- `validate_ffmpeg_command` applies **NO character blocklist deliberately**: subprocess always gets argv lists (never `shell=True`) so `;`, `()`, `$` are inert, and filter_complex legitimately needs them. Safety = first token must be `ffmpeg` (binary path force-replaced), every `-i` path and the output must realpath-resolve inside `input/` or `output/`. Do not "harden" it with character filters.
- `safe_path` rejects absolute paths and traversal via realpath+commonpath; `GET /input/<name>` and `/output/<name>` skip it and rely on `send_from_directory`'s own protection.
- **A range check is not a type check, and NaN passes both directions of one.** `float("nan")` succeeds, and `nan < 0` / `nan > limit` are *both* `False` — so a NaN validated clean through every bound in `app.py` and reached ffmpeg as the literal `nan` (finding #11 measured four routes that started a real encode for one). `bool` is an `int` subclass, so a JSON `true` passed as `1` — `hold_frame time=true` used to hold a frame. Request fields go through **`_str_field` / `_num_field` / `_obj_field` / `_list_field`** in `app.py`'s `# ---------- request fields ----------` section: they take the *value*, not `(data, key)`, so a nested field can be named in full (`_str_field(c.get("input"), f"clip {i}: input")` → `clip 0: input must be a string`), and they raise `ValueError` because that is the shape the routes' existing `except ValueError → 400` blocks already use. `_num_field` rejects `bool` and non-finite values on purpose; ranges are opt-in via `lo`/`hi`, and no *plausibility* bounds were invented for `speed`/`crop`/`overlay x,y` — picking one is a product decision. A string where an object or list belongs is the subtle case these catch: it indexes character-wise, so `{"inputs": "small.mp4"}` used to 404 on a file named `s`.
- **`safe_path` also judges the TYPE of `name`,** because `os.path.isabs`/`join` raise `TypeError` on a non-string and every caller already turns `PathError` into a 400. That's the floor under the routes; the routes still name the offending field themselves.
- **An output name is a filename, not a path — one gate, `check_output_name`, and it must run before the uniqueness loop.** Every export route now reaches it through `fu.unique_output_name` (0.44.0, AUDIT #14): non-empty string, `os.path.basename(name) == name`, not `.`/`..`, extension in `RENDERABLE_EXTENSIONS`. Two mechanisms make a bare-string check insufficient to reason about by eye. `os.path.join(base, absolute)` **discards `base` entirely**, so an absolute name is not "inside" anything; and `stage_output`'s `os.makedirs(stage_dir, exist_ok=True)` builds the whole parent chain, so a name containing `/` silently created a **subdirectory inside the export bin** and the render landed in it — `commit_output` returns `os.path.basename(final)`, so the reply named a file the Bin (which lists one directory, not a tree) could never show. Measured: `8/25 hero cut.mp4` returned 200 and wrote `<export>/8/25 hero cut.mp4`, invisible to the app. The gate refuses instead of sanitizing, because rewriting the name would hand the user a file they did not ask for; spaces, unicode and long names are still fine.
- `input/` is sacrosanct — never modify or delete a file's *contents* there programmatically. `/api/clear_input` and `DELETE /api/files/<name>` (both user-confirmed) are the only sanctioned deletion paths, and `/api/rename_file` with `dir="input"` (the Media Bin's right-click Rename) the only sanctioned write: it renames, so the bytes are still untouched. Everything else reads.

## Environment quirks

- **Binary paths resolve at import time, with Apple Silicon winning.** `ffmpeg_utils._tool()` returns `/opt/homebrew/bin/<name>` when it exists and otherwise `shutil.which(name)`; `CLAUDE_BIN` (app.py) is `shutil.which("claude")` with `~/.toolbox/bin/claude` as fallback. Consequence: on a non-`/opt/homebrew` machine the app inherits the PATH of the shell that launched Flask, so a backend started without `brew shellenv` can fail to find ffmpeg while your own shell finds it fine. Don't reintroduce bare `"ffmpeg"` strings — the explicit brew path is what keeps a stray conda/system build from winning here. `browse_directory`/`reveal_file` are macOS-only (osascript / `open -R`).
- **There are exactly two places an ffmpeg-family binary is spawned, and both must translate `FileNotFoundError`.** `probe()`'s `subprocess.run` and `run_tracked`'s `Popen` (which `run_ffmpeg` wraps) are the only ones; both now raise `RuntimeError(missing_tool_message(...))` instead, because Python's own text — `No such file or directory: '/opt/homebrew/bin/ffprobe'` — reads as a missing *media* file and names nothing to do about it. Measured on a machine with the resolved paths absent: probe, trim, reverse, hold_frame, render_timeline, `/preview` and `/api/execute` all surfaced `internal server error` with the real cause only in `detail`, which the bins and Media Info don't display (finding #12). `fu.missing_tools()` + the `__main__` banner say the same sentence once at startup — it **prints rather than refuses to start**, since the UI, the file lists and saved projects are still worth having, and note the reloader prints it **twice** (parent and reloaded child), which is expected, not a bug. Anything new that spawns ffmpeg goes through `run_tracked`, or it reintroduces the opaque failure. **Both are also bounded now:** `probe()` was the last spawn site in the repo with no `timeout=` (recorded during #7, closed in 0.44.0) and takes `timeout=PROBE_TIMEOUT` (120 s), raising a `RuntimeError` that names the file and the bound. 120 s is far past any real probe — 0.09 s for the test media here — and the point of the number is that one exists at all, so an unreadable file or a disconnected volume can no longer wedge a request indefinitely.
- **`osascript` exits 1 for a user cancel and for a permission denial alike, so the exit status can't tell them apart.** `browse_directory` classifies on AppleScript's own error *number* in stderr — `-128` (`User canceled.`) is the quiet `{"cancelled": true}` path, and anything else, including `-1743` (`Not authorized to send Apple events to System Events.`), is a 500 carrying `_PICKER_ERROR`. Reporting both as cancelled is what made a denied Automation permission a **silent no-op**: Browse pressed, nothing opened, nothing said (finding #12). The number is checked because it is locale-independent; the English text is checked too, only as a fallback. Third face of the same failure, measured in this project's own environment: System Events can simply never answer, so the call hangs to the full 120 s and raises `subprocess.TimeoutExpired` — whose `str()` is *the entire AppleScript source*, which used to land verbatim in the dialog's error line. That branch is handled separately with a plain "did not respond within 120 seconds". Testing this needs a **fake `osascript` earlier on PATH** that reproduces the exit status and stderr (the route sees nothing else); driving the real one blocks the shell for two minutes.
- **Pass a path to `osascript` as an argument, never inside the script text.** `osascript -e '<script>' ARG` runs the script's `on run argv` handler with `ARG` as `item 1 of argv`, i.e. as *data the interpreter never parses*. `browse_directory` interpolated its `initial` value into the source instead, so a folder name containing `"` was compiled as AppleScript and returned **`-2741`** (a syntax error) — the ordinary consequence being that anyone with a quote in a folder name could not open the directory picker at all (AUDIT #14, fixed in 0.44.0). Escaping would work too and is the worse answer: it has to be re-applied correctly at every future call site. Verifying this needs compile-time evidence — the *valid* path opens a picker and blocks for the full timeout in this environment — so check that each payload (`"`, `\`, a newline) compiles rather than that it does the right thing.
- **`.export_settings.json` is untracked and written atomically, and atomic is not the same as safe (0.44.0).** It used to be committed, so every clone inherited the developer's `under50mb_hevc` mode; it is now in `.gitignore` as `.export_settings.json*` (the `*` covers the temp file) and untracked. `_save_export_settings` writes `.export_settings.json.<pid>.tmp` and `os.replace`s it, which is atomic *within a directory*, so a crash mid-write can no longer wipe the export directory, the quality mode and every saved preset — verified by injecting an exception mid-write: previous file intact, all three presets readable, no temp left behind. It does **not** make concurrent saves safe: two savers still race and the loser's update is still lost, the only guarantee being that what remains is a valid earlier state. The temp cleanup catches `Exception`, not `OSError`, because `json.dump` raises `TypeError` on an unserializable value — an `OSError`-only version left the temp file behind.
- **One rule for "where the Export Bin is" — `get_output_dir()`, reached through `resolve_media_dir(which)` on anything that takes a `dir` field** (finding #4, fixed in 0.36.0). Every render route (`render_timeline`, `reformat`, `render_a1`, `trim`, `splice`, `hold_frame`, `reverse`), every read route (`/api/outputs`, `/output/<name>`, `/preview/<which>/<name>`, `/api/probe?dir=output`), the Bin's own rename/delete/reveal/clear, and `unique_output_name` (whose `export_dir` argument is **required**, precisely so a future caller can't silently inherit the default) now all resolve the same way. Before this, five of them hardcoded `fu.OUTPUT_DIR`: with a custom export directory set, the Bin listed one folder while Media Info Out and the preview player read another, and a trim/splice/hold/reverse landed somewhere the Bin could not list, rename, preview, or delete. The remaining `fu.OUTPUT_DIR` references in `app.py` are deliberate: `get_output_dir()`'s own fallback, `browse_directory`'s starting folder, the `default_output_dir` the settings dialog displays, and the **chat/execute subsystem** (`build_file_context`, `_output_arg_info`, `fu._media_path_ok`), which is a sandbox anchored on PROJECT_ROOT-relative `output/` — widening it to a user-chosen directory is a change to where the assistant is permitted to write, not a bug fix. Consequence to know: a file the chat panel produces lands in `output/` and is invisible to a relocated Export Bin.
- **`input/` and `output/` are created on demand, and that can never invent a user's export folder.** `_list_dir` (both bins) and `upload` call `os.makedirs(..., exist_ok=True)` — the same pattern `list_projects` and `PREVIEW_CACHE_DIR` already use — because a clone that skipped the runbook's `mkdir -p` answered `/api/files`, `/api/outputs` and `/api/upload` with a 500 whose only content was `FileNotFoundError: … '/path/input'` (finding #12). The safety argument for doing it inside `_list_dir` is `get_output_dir()`: it returns a custom path **only** `if os.path.isdir(custom)`, so a mistyped or unplugged export directory has already fallen back to `fu.OUTPUT_DIR` before `_list_dir` sees it — the folder that gets created is always the project's own. Don't move the `makedirs` up into `get_output_dir()`, which would reverse that.
- **The preview cache key names the directory as well as the file (0.44.0) — before that, two files with one name shared one transcode.** `.preview_cache` is flat, so while the key was `<basename>.<int mtime>.preview.mp4` two *different* non-browser-playable files sharing a name and a whole-second mtime — one in `input/`, one in the Export Bin — were served the same video. Measured with two ProRes files (`testsrc` vs `testsrc2`) both named `same.mov`, mtimes forced equal: both `/preview/input/same.mov` and `/preview/output/same.mov` returned the identical file (7,335 bytes then; 6,281 in the AUDIT #14 re-measurement), and it reproduced identically before and after 0.36.0 — the key was what was wrong, not the base directory. `preview_cache_key(path, mtime)` now folds ten hex digits of SHA-1 over `os.path.realpath(dirname(path))` into the name, so the same two files get two entries (verified 6,281 and 2,484 bytes, each the right video) and two directories that are one directory through a symlink still share one. A key cannot hold a `/`, so a hash rather than a flattened path; the cost, once: every entry written before 0.44.0 matches no key any request can now produce, so the first sweep deletes all of them and each file still in use is re-transcoded one more time. Browser-playable sources are unaffected (served from their own path, never cached).
- **The preview cache evicts by REACHABILITY, and that criterion is exact rather than a heuristic.** `prune_preview_cache(live_dirs)` deletes every `*.preview.mp4` whose `(basename, whole-second mtime)` key matches no file in the directories the caller offers, because `serve_preview` 404s unless the source exists and then derives the key from that file — so an unmatched entry cannot be *named* by any request, and deleting it costs at most one re-transcode (measured 2.2 s for a 4 s HEVC clip, 11.5 s for a 13 s one, vs 0.06 s to serve a cached copy). Before 0.43.0 nothing evicted at all, in any dimension: measured 602 MB / 334 files with **83% unreachable**, and 92% of those dead bytes were sources that no longer existed (cleared Export Bin renders, renames) rather than the "edited source strands its entry" the audit blamed. Two hooks — `__main__` (the only moment with no request in flight) and a cache **miss** (the only hook a server left running for days reaches, and free next to the encode it just paid for); explicitly *not* on a hit, since one `<video>` issues many range requests and none of them makes garbage. `live_dirs` is passed in from `app.py` because only `get_output_dir()` knows where the Export Bin is. Two invariants to preserve: the sweep must skip anything not ending in `.preview.mp4`, or it deletes the `<key>.<pid>.<tid>.part.mp4` a *concurrent* transcode is still writing and that encode's `os.replace` raises `FileNotFoundError`, which `serve_preview` doesn't catch (it catches `RuntimeError`) — a 500 on an unrelated request; and the size cap (`PREVIEW_CACHE_MAX_BYTES`, 2 GiB) must stay LRU, which works only because a hit does `os.utime(cached)` — that is what puts the file currently being streamed last in the eviction order without a lock. Nothing reads a cache file's own mtime; the key carries the *source's* mtime in its name, so touching it is free. `preview_cache_key()` exists so the writer and the sweeper can't drift.
- **Three extension tuples, and the differences matter.** `RENDERABLE_EXTENSIONS` (0.44.0) is `ALLOWED_EXTENSIONS` minus `.webm` — the set a render may *write*, enforced for all seven export routes by `check_output_name` inside `unique_output_name`. `.webm` stays readable and unrenderable on purpose: every render path encodes through `encode_args`, which emits H.264/HEVC + AAC, and the WebM muxer accepts none of them, so a `.webm` output was always a 500 ("Nothing was written into output file"); teaching `encode_args` VP9/Opus is a feature, not a sharp edge. `_derive_name` also forces `.mp4` when a source's extension isn't renderable. `ALLOWED_EXTENSIONS` is still video-only (.mp4 .mov .mkv .avi .m4v .webm) and gates anywhere a *video* is required (timeline clip, overlay source). `MEDIA_EXTENSIONS = ALLOWED_EXTENSIONS + AUDIO_EXTENSIONS` (+ .wav .mp3 .m4a .aac .flac .aiff) gates the seven file-management sites in `app.py` — `_list_dir` (serving both `/api/files` and `/api/outputs`), `upload`, `clear_input`, `delete_input_file`, `rename_file`, `clear_output`, `delete_output_file` — so an audio bed can be uploaded, listed, and deleted through the normal UI. Image uploads are still rejected. Note `/api/probe` has **no** extension gate at all. **`clear_input` and `delete_input_file` are destructive and now sweep audio files too** — intended (an audio file in `input/` must be deletable the same way), but don't widen either further without saying so out loud.
- **`secure_filename` deletes non-ASCII characters, so an extension check must read the name the BROWSER sent.** It NFKD-normalizes and drops what won't encode, so `видео.mp4` sanitized to `mp4` — a name with no extension at all — and `upload` refused it as `unsupported file type: mp4`, naming a *supported* format as the unsupported one; any filename in a non-Latin script was unuploadable (finding #12). `upload` now takes `raw_ext` from `os.path.splitext(f.filename)`, gates on that (case-folded, against `MEDIA_EXTENSIONS`), then sanitizes **only the stem** and re-attaches the original extension, with `"upload"` standing in for a stem that sanitizes away to nothing — sanitizing the whole name instead would save `видео.mp4` as `mp4`, which every listing route then filters out of sight. Verified byte-identical for every ASCII name (`My Clip 02.mp4`, `café.mp4`, `../evil.mp4`, `a.b.mp4`, `TRAILER.MOV`, `noext`), so the traversal and space handling `secure_filename` was there for is untouched; `os.path.splitext(".mp4")` is `('.mp4', '')`, so a bare-extension name is still refused. **`rename_file` had the same blind spot, and what it actually did was worse than the audit's claim (fixed in 0.44.0, AUDIT #14).** It sanitized the whole `newName`, and because `secure_filename` keeps the ASCII extension, `видео.mp4` became `mp4`, the route re-appended the extension, and the file was silently renamed to **`mp4.mp4`** — not refused as "new name required". It now checks the *stem* separately and returns a 400 saying a name needs at least one Latin letter, digit, dash or underscore before its extension, because the alternatives are storing nonsense or transliterating to something the user never typed. The stem is found by stripping a `MEDIA_EXTENSIONS` suffix, **not** with `os.path.splitext`, which returns `('.mp4', '')` for `.mp4` and let a first attempt keep storing `mp4.mp4`. `café.mp4 → cafe.mp4` is still accepted, knowingly: it matches upload's behaviour and the result is the name the user asked for.
- Version spread: Python 3.9.6 venv (macOS CommandLineTools) vs bleeding-edge Vite 8 / React 19 / Tailwind 4. Lint is oxlint, not eslint.
- **`define` in `vite.config.js` does NOT reach the dev server — it fails in the one mode this app actually runs in.** Verified against the installed vite 8.1.5: `vite:define`'s transform opens with `if (this.environment.config.consumer === "client") return`, and user defines are applied only through `applyToEnvironment`'s bundled branch. So `vite build` inlines the value (greppable in `dist/`) while the dev server serves the identifier *undeclared*, and the browser throws `ReferenceError: <NAME> is not defined` — a compile check cannot catch it, because the compile is the case that works. Cost real time here: the toolbar version readout was written with `define` first, passed `npx vite build` with the literal in the bundle, and crashed `<AppInner>` on load.
  - Use **`import.meta.env`** instead. It works in both modes: in dev Vite prepends a literal `import.meta.env = {…, "VITE_APP_VERSION": "<VERSION's contents>"}` to every served module (confirmed by `curl http://127.0.0.1:5173/src/App.jsx | grep VITE_APP_VERSION`), and a build inlines it. `vite.config.js` populates it by setting `process.env.VITE_APP_VERSION` at module scope — `loadEnv` runs after the config file is evaluated and sweeps in every `VITE_`-prefixed `process.env` key (vite's `loadEnv`, the third of its three merge loops), so no `.env` file is needed. That matters beyond tidiness: a `.env` file would be a second place storing the version.
  - Two follow-on traps. **A failed config reload leaves the old config running**: edit `vite.config.js` badly and Vite logs `server restart failed` and then keeps serving with the *previous* config, so subsequent HMR pushes new source into a server missing the new config — the error you see belongs to a config that is no longer on disk. Restart the process. And **any `vite.config.js` change needs a real restart** to be trusted; `VERSION` is read at config time, so a bump never reaches a running dev server on its own.
  - Anything Vite-injected is invisible to oxlint. `import.meta.env` needs no declaration; a `define` global would have needed a `globals` entry in `.oxlintrc.json` — another reason the env channel is less machinery.
- **Frontend races and wedges are measurable from node over CDP, with no new dependency.** node v26.5.0 has a global `WebSocket` and Chrome (`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`) takes `--remote-debugging-port` with a throwaway `--user-data-dir`; attach with `Target.createTarget` + `Target.attachToTarget {flatten: true}` and drive the page with `Runtime.evaluate`. Three domains do the work that no amount of reading can: **`Fetch.enable` + `Fetch.requestPaused`** to hold one specific response for N ms (`continueRequest` after a timer) or fail one specific request (`failRequest`) — which is how a probe race or a mid-drop upload failure is produced on demand; **`Page.javascriptDialogOpening` + `Page.handleJavaScriptDialog`** to capture *and answer* alerts/confirms (an unanswered dialog blocks the page, so a test that ignores one hangs); and a synthetic `DragEvent` carrying a `DataTransfer` built from real media bytes to exercise the lane drop handlers, which no click can reach. Two traps met in practice: media already in the browser cache is **not intercepted** (a "fetches: []" reading means the request never went out, not that the guard failed), and the A/B that matters is *the same script* against a temporarily reverted copy of the file under test — that is what distinguished #10's fix from the pre-existing 24 fps end-of-file stall (AUDIT #14), which reproduces byte-identically on both.
- **`pgrep -af` prints no argv on macOS, and a grep-based process counter matches its own command line.** `pgrep -af ffmpeg` returns nothing usable here (`-f`/`-x` matching itself works fine, it is the `-a` listing that doesn't), so "which encoder is running, with which flags" needs `ps -Ao pid=,args= | grep bin/ffmpeg` — which is also what makes a two-pass render's pass readable, since libx265 spells it in argv as `-x265-params pass=1:stats=…`. Two traps met while measuring AUDIT #8: a heredoc or `grep` pattern containing `bin/ffmpeg` or the output filename **matches the harness's own shell and grep lines**, which read as a second encoder until `pid ppid args` was printed in full (the real one was ppid = the server); and `ps -M <pid>` needs `-p` (`ps -M -p <pid>`) or it silently lists nothing — it prints a header, the process line, then one line per extra thread, so the thread count is lines-minus-header.
- **Stop the reloader WORKER, never the monitor — signalling the monitor SIGKILLs the worker and nothing cleans up (AUDIT #19, fixed in 0.45.1).** Under `debug=True` both processes listen on 5001, so `lsof -ti :5001 | xargs kill` — the run-app skill's stop command until 0.45.1 — signals both. `run_with_reloader` installs `signal(SIGTERM, lambda *a: sys.exit(0))` in the monitor too (`_reloader.py:446`), and the monitor is blocked in `subprocess.call` (`_reloader.py:275`) whose `except:` clause is `p.kill()`. The worker dies by **SIGKILL**, so no handler and no `atexit` runs: measured, the encoder was orphaned and ran 8.5s to completion and its staged file was left in `output/.partials/` — identical before and after 0.45.0, so it was a coverage limit of 0.39.0, not a regression. The stop command is now `for p in $(lsof -ti :5001); do ps -Eww -p $p | grep -q WERKZEUG_RUN_MAIN=true && kill $p; done` — the worker is the only listener with `WERKZEUG_RUN_MAIN=true` in its environment (do **not** pick it by pid order: macOS pids wrap at 99999, and after a wrap the newer worker has the lower number), and the monitor then exits on its own because `restart_with_reloader` returns on any child exit code other than 3. Two things that look like fixes and are not: worker-then-monitor still orphans (the monitor's `p.kill()` beats the worker's 2.0s ffmpeg grace), and SIGINT to both only works inside `Popen.wait`'s 0.25s `_sigint_wait_secs` window. An operator stop surfaces as HTTP **500** on the in-flight render, not 499 — 0.45.0's disconnect path isn't involved.
- **A Vite proxy passes a client abort through to Flask**, which is why disconnect cancellation works in the real dev topology and not just against curl — verified by aborting a fetch in the browser and watching the Flask side see a closed socket. Standing up a throwaway proxy for this needs care: a `vite.config.js` outside the project cannot `import { defineConfig } from 'vite'` (`ERR_MODULE_NOT_FOUND` — export a plain object instead), and it must be run as `./node_modules/.bin/vite --config <path>` from `frontend/`, because `npx vite` in a directory with no `node_modules` downloads a *second* copy of Vite instead.
- In shell commands, `ffmpeg`/`ffprobe`/`node` are NOT on PATH by default in this environment — run `eval "$(/opt/homebrew/bin/brew shellenv)"` first, and note the working directory resets between some invocations (cd explicitly; `npx vite build` fails with UNRESOLVED_ENTRY if run from the repo root instead of `frontend/`).
- `.export_settings.json` is **global mutable state** — a render's quality mode is whatever it holds at that moment. Parallel test renders can race each other's quality settings (bit-exact hash checks then fail mysteriously); pin it to `lossless` before hash-verification renders. It is also **the user's live configuration**, not scratch space: back it up (`cp` to `/tmp`) before writing test values into it, and restore it when done. `POST /api/export_settings` is a partial update precisely so one writer can't clobber another's keys — keep it that way if you add a field.
