# Domain Glossary

Terms a new engineer needs before touching this codebase.

- **EDL (Edit Decision List)** — the editing model: the timeline is a list of edit *decisions* (source, IN/OUT, holds, reversed, speed), not a working copy of media. Applied only at Render. The EdlTable renders it with SMPTE-style source/record timecodes; exportable as a CMX-style `.edl` file.

- **Clip** — one timeline entry. Full data model (created in `App.jsx handleAddToTimeline`):
  `{ id (UUID), sourceName, sourceDir ('input'|'output'), sourceDurationSec, sourceWidth, sourceHeight, fps, inSec, outSec, headHoldSec, tailHoldSec, roundHoldSec, reversed, speed, crop, dirty, displayName? }`
  `sourceDurationSec` is the **video stream's** duration, not the container's (see gotchas.md).

- **Hold (head/tail)** — freeze-frame extension attached only to the sequence's outer edges: `headHoldSec` freezes the first visual frame before the first clip; `tailHoldSec` freezes the last frame after the last clip. Implemented server-side as a one-frame `trim` + `loop`, with `anullsrc` silence for the audio. Fuchsia segments in the UI; individually selectable/deletable via `selectedPart`. Applying duration 0 in HoldFrameForm is the documented way to remove a hold.

- **Round / Raise** — `RaiseButton` rounds the WHOLE SEQUENCE duration (`sequenceBaseSec`) up to the next whole second by adding `roundHoldSec` to the last clip. Amber ROUND segment. Server-side it just adds to tailHoldSec (freezing an already-frozen frame is a pixel no-op).

- **dirty** — per-clip flag: "this decision hasn't been rendered yet." Amber dashed border + "pending" EDL status; cleared track-wide after a successful render.

- **V1 / V2 tracks** — V1 is the main edit lane and the single source of truth for playhead/ruler/transport timing and undo. V2 is a scratch reference lane (Analyze/Reconstruct results or a raw dropped file), composited "on top" for the preview when visible, NLE-style. V2 shares ONE undo history with V1 and A1 (see the `useUndoableTracks` entry in [key-files.md](key-files.md) — it used to be excluded, which read as "undo only works on V1"), and is otherwise a fully editable clip list — Trim/Hold/Reverse/Speed/Crop/Duplicate/Splice/Raise, drag-to-reorder, and per-hold-segment delete all work on V2 exactly like V1. The shared toolbar row (`App.jsx`) redirects to whichever track is currently focused (`focusedTrack`, lifted from Timeline.jsx into App.jsx) — clicking a clip on either track focuses that track and the toolbar acts on it; clicking the V1/V2 gutter label buttons focuses a track directly. `App.jsx` derives `activeClips`/`setActiveClips`/`activeSelectedClip`/`setActiveSelectedId` from `focusedTrack` and passes those into the toolbar components unchanged — none of the 9 toolbar components know or care which track they're editing.

- **A1 track / audio lane** — a third lane drawn under V1 holding an ORDERED LIST of audio clips (music, voice-over, stings): the lane. "Smart" means it owns no timing of its own — it is **linked to V1**: it starts where V1's *picture* starts (delayed past the first clip's head hold, and it moves whenever that hold changes or is removed) and the render derives its length from V1 on every pass, **padding it with silence if it's shorter and cutting it if it's longer**, so it can never drift out of sync. It **mixes with** V1's own audio rather than replacing it (`amix=...:normalize=0`, an exact unity-gain sum that leaves V1's dialogue level alone, unlike `normalize=1` which would duck it 6 dB), attenuated by the fixed `ffmpeg_utils.BED_GAIN = 0.35` since there is no volume control. The lane's target length is `sum(expected_secs)` — the frame-quantized per-clip truth, not a wall-clock duration, which drift apart by up to 0.076 s under mixed fps + slow-mo. State is `audioBeds` in `App.jsx` — the `a1` slice of `useUndoableTracks`, so add and remove are undoable alongside V1/V2/ANIM edits — an array of `{name, dir, durationSec, startSec, inSec?, outSec?}`, deliberately **not** part of `focusedTrack`/`activeClips`: no clip on it owns editable timing, so of the 9 toolbar components only **Split** acts on it (through its own `selectedBedIndex`, not the focused track) and the Delete key never does. **`startSec` (version 6) makes each clip's position explicit**, in lane seconds from V1's picture start: removing a clip leaves every other clip exactly where it was and opens a HOLE, which renders as digital silence — or as room tone with that toggle on — instead of pulling the rest of the lane earlier. **`inSec`/`outSec` (version 7) are which part of its FILE a clip plays**, both optional and absent meaning all of it — see **A1 split** below. Clips are added end to end and there is no drag-to-reposition, so a lane is contiguous until something is removed or a half of a split clip is moved. The gutter has **no focus button and no mute button** — just the `A1` label and an eye toggle (which hides the bar; it never affects the render). Adding a clip changes **zero video frame hashes** — it touches only the audio branch of the graph. `a1Muted` exists and is honored by the preview player and the bar, silencing A1 in the PREVIEW only, but no UI control sets it. See also [architecture.md](architecture.md) for the render graph and `AudioBedBar` / `AudioBedPlayer`.

- **Analyze** — clones V1's cut structure (same inSec/outSec and hold durations, never reversed, no speed) onto the file dropped on V2 (`analyzeAgainstV1` in `analyzeMath.js`). Overflow past V2's end is clamped and logged. The button is labeled **"V2 Analyzer"** (its counterpart is **"V2 Reconstruct"**); the code still says `onAnalyze`/`analyzeAgainstV1`, so the label and the identifiers differ on purpose.

- **Batch Analyze** — the plain-cut sibling of Analyze (`batchCutAgainstV1` in `analyzeMath.js`; button **"V2 Batch Analyzer"**, beside **"V2 Analyzer"**): splits V2's FIRST clip at every boundary in V1's sequence. The difference from Analyze is the **time base**, and it's the whole reason a second button exists. Analyze clones V1's own `inSec`/`outSec` onto V2, which means something only when V2 is another version of the *same* source. Batch Analyze assumes V2 is V1's **sequence joined into one file** (a V1 Render / V2 Render-on-`1` output that went out to an external tool and came back whole), so the boundaries are **cumulative durations** from the head of V2's own window.
  - **Pieces, not clips.** `sequencePieces(v1Clips)` returns what the sequence renders as, in order: clip 0's head hold, each clip's main body, then the last clip's tail hold and round-up — `{ kind: 'head'|'main'|'tail'|'round', sec }`. A hold is a piece in its own right, not padding on a clip: in the joined file it's a stretch of one frozen frame, so it gets cut out as its own V2 clip. Segments are named **per kind** — `Head01`, `Shot01`…`ShotN`, `Tail01`, `Round01` — so the shot numbering still matches V1's clips however many holds sit among them. Tail and round-up freeze the same frame but stay separate pieces (the timeline draws them separately; Raise owns the round). Mid-sequence holds are excluded, applying the render's own first/last rule so a stale one can't shift every later boundary. Zero-length pieces are never emitted. `sequenceCutOffsets` is the cumulative-boundary view of the same list.
  - Nothing else is copied: holds, reverse and speed are already baked into that footage as real frames, so re-applying them would double them.
  - **Cut points, not durations** — P pieces give P−1 boundaries and the **last segment runs to the end of V2's window**, so no footage is discarded (a cut never throws the tail away); the extra length is reported as `leftoverSec`, and cut points falling past the end of a too-short V2 produce no segment at all and are reported as `overflow`.
  - Cuts snap to **V2's own** fps grid so the segments tile the window exactly; a boundary snapping onto the previous one is dropped rather than emitting an empty segment. Returns `kinds` parallel to the segments so the caller can log "4 shots + 2 holds" without re-deriving it.
  - Further V2 clips (index ≥ 1) are left untouched — same convention as Reconstruct. The no-op guard is `pieces.length < 2`, **not** one V1 clip: a lone clip carrying a head hold or a Raise does have boundaries. It is the return leg of the **1 / 1+ toggle**'s `1` mode, as `1+` is of sending the shots out separately.

- **Reconstruct** — step 2 of a round-trip: after Analyze conforms V2 to V1 and the user takes that V2 footage through an external tool and drops the result back onto V2 (`handleAddToV2` always replaces V2 with a single fresh clip — V2 Render always merges everything into one file first), Reconstruct strips V1's edit artifacts back out of V2's *own* clip — it never touches or copies V1's `sourceName` (`reconstructFromV1`). Holds/round-up are treated as SEQUENCE-level facts about V1 (headHold from V1's first clip, tailHold+roundHold from V1's last — same convention as `sanitizeHoldPlacement`/`RaiseButton`), trimmed off V2's window since they're baked-in duplicate frames; reversed is copied as-is (not toggled) only when every V1 clip agrees on it — a mixed forward/reversed V1 sequence can't be represented by one flat V2 clip, so that case warns and leaves V2's flag untouched; speed resets to 1; crop resets to null (unrecoverable — those pixels don't exist in the round-tripped file). Requires clips on both V1 and V2.

- **Overlay (V2-as-overlay / composite)** — a V2 clip that is a *processed region* of V1 rather than a replacement for it, composited back on top at the crop box's animated position. Serves the round-trip the crop presets exist for: crop a moving region out of V1 → run it through an external tool (an AI video model, a grade, a cleanup pass) → drop the result on V2 → put it back where it came from. This also recovers what Reconstruct can't (see *Reconstruct*: "crop resets to null (unrecoverable)"). Decided entirely by `frontend/src/overlayMatch.js`, whose four rules are deliberate:
  - **Trigger is a resolution difference, nothing else.** V2 ≠ V1 in size → overlay. No flag, no opt-in, no indicator. Equal size → the pre-existing full-frame replacement, untouched.
  - **Size must match the crop box EXACTLY**, or it's refused with a warning in the Actions log (not an alert — the match is derived continuously, so an alert would fire on every keystroke of a resize). Nothing is resampled: a 961×960 file next to a 960×960 box is an upstream mistake, and silently scaling it would bake a soft, misaligned region into an otherwise lossless render.
  - **Pairing is positional** — 1st V2 clip onto 1st V1 clip, 2nd onto 2nd — each inheriting *that* V1 clip's own crop box and `cropKeyframes`.
  - **The crop becomes a placement rect, not a crop.** An overlaid V1 clip is rendered *uncropped* (`clipsToPayload` nulls its `crop`/`cropKeyframes`) — the whole point is the full original frame with the processed region on top. The overlay is composited on the raw input *before* trim/reverse/speed, exactly where `crop` sits, so `t` is source time, one `keyframe_ladder` serves both, and holds/reverse/slow-mo/concat inherit correct behavior for free.

  Live preview is a second `<video>` layer (`OverlayPreview.jsx`). See gotchas.md for the `split=N` and `eof_action` requirements.

- **A / A/B toggle** — the segmented switch right of **V2 Render**, which chooses what that button outputs. **A** (default, mode value `'A'`) renders the V2 track alone to its own file, the original behavior. **A/B** (mode value `'AB'`) composites V2 over V1 and renders the two as one clip. A/B is the only way a composite render is reached, and it's *more* permissive than the always-on overlay derivation in one specific way: it passes `matchOverlays(..., { fullFrameSameSize: true })`, so a V2 clip matching V1's resolution becomes a **full-frame overlay at 0,0** (covering V1 completely) rather than the ordinary track replacement — which is exactly what "put V2 on top of V1" means when the two are the same size. The exception is a *cropped* V1 clip: it renders at its crop box, so a source-sized V2 over it has two possible meanings and is refused with an explanation (`SKIP_AMBIGUOUS_FULL_FRAME`) rather than guessed. Clicking V2 Render in A/B mode with nothing that resolves explains why and points back at A, instead of silently rendering a plain V1.

- **1 / 1+ toggle** — the second segmented switch right of **V2 Render**, deciding how many FILES that click writes, orthogonal to A / A/B (which decides what each shot *contains*). **1** (default, mode value `'1'`) is the original behavior: the whole track joined into one clip, one pass, one file. **1+** (mode value `'1+'`) renders every cut on its own — N passes, N files, `<name>_01`, `_02`… in track order (`renderNames.shotOutputNames`, zero-padded to at least two digits so a series sorts in cut order). The cuts belong to whichever track the render is built from: V2's clips in A, V1's in A/B. Laid end to end a 1+ series **is** the 1 render, verified frame for frame (180/180 framemd5 over a head hold + reverse + slow-down + tail/round hold). What differs is only what a separate file implies: per-shot target resolution/fps instead of the track's max (a 160×120 cropped clip stays 160×120 instead of being padded to a 320×240 neighbour), a separate size budget per file in a capped quality mode, and **no A1** — the lane is timed to the whole V1 sequence, so it's dropped with a log line rather than restarted under each shot. `App.renderShots` runs the passes sequentially (logging + `refresh()` per shot, `v2ShotProgress` counting them off on the button) and stops the series at the first failure, leaving the track dirty. See gotchas.md for the mid-sequence hold rule it has to enforce.

- **Splice** — splits the selected clip at the shared preview's `currentTime` into two clips named via `nextSplitName` (`Video01`, `Video02`, …). Each half needs > 0.1s (`MIN_PART_SEC`).

- **A1 split** — the same **Split** button acting on an A1 clip instead of a video clip: click a bar on the lane (which also moves the playhead to where you clicked, so "click where you want the cut, then Split" is one gesture) and the clip becomes two clips playing adjoining parts of one file — `clipMath.splitBed`, the left half gaining `outSec`, the right half `inSec` plus a `startSec` advanced by the left half's played length, so no hole opens and nothing else on the lane moves. Two things make it a *cut* rather than an edit: the halves are joined by the lane's existing single `concat` with one `atrim` each (see gotchas.md for why `aformat` must precede that `atrim`), and the render is bit-identical to the unsplit one until a half is removed or moved. The split point is the **timeline** playhead, not the preview's `currentTime` — A1 is timeline-locked, so a hold or a slow-down breaks any relation between the two. Deliberately narrow: Split is the *only* toolbar control an A1 selection reaches, the Delete key still acts on the focused video clip, and removal is still the × on the bar. Each half needs > 0.1s, the same `MIN_PART_SEC` the video branch uses.

- **Speed** — slow-motion-only per-clip rate from `PRESET_SPEEDS`, filtered by `allowedSpeeds` so effective fps (source fps × speed) stays ≥ `MIN_EFFECTIVE_FPS = 12`. Pure PTS stretch (`setpts=(1/speed)*PTS`) — no interpolated frames; slowed segments get silent audio.

- **Crop** — per-clip spatial crop to a fixed preset resolution (480p/720p × 6 aspect ratios, `cropMath.js CROP_PRESETS`), stored as `clip.crop = { key, w, h, x, y }` in source-pixel coordinates. `CropForm` picks the preset (box auto-sized to fit the source without upscaling, then centered); `CropOverlay` lets the user drag the box on the live preview (positioned against the `<video>` element's own rendered rect, since it's letterboxed via `object-fit: contain`). Applied server-side as the first filter step per clip (`crop=w:h:x:y`, before trim/reverse/speed) so holds crop identically to the main body; the render's common target resolution is derived from post-crop dimensions.

- **Export quality modes** — `EXPORT_QUALITIES = ("lossless", "match", "high", "under50mb", "under50mb_hevc", "custom")` in `ffmpeg_utils`: lossless = `-qp 0` bit-exact; match = ABR at the source's own video bitrate (1.5× maxrate); high = CRF 18; under50mb = a hard 50MB size cap that outranks quality, via two-pass ABR sized from the render's duration (see `render_size_capped`, `target_bitrate_for_size`) plus a measure-the-real-output-and-retry loop — not produced by `encode_args` since two-pass needs two full ffmpeg invocations, not one args list. under50mb_hevc is the same size-capped mode with `codec="hevc"`: libx265 Main10 profile (`yuv420p10le` intermediate) at preset `medium` instead of libx264 at preset `slow` — better quality per bit, much slower to encode, and not browser-playable (gets transcoded for in-app preview like any other non-`BROWSER_SAFE_VIDEO_CODECS` output). Audio in lossless/match/high: AAC at `max(source bitrate, 192000)`; both under50mb modes use a lower floor (96000) and squeeze it further if the byte budget is tight enough that video would otherwise fall below its own 100kbps floor. Selected globally in `.export_settings.json`.

- **custom (export mode)** — the sixth quality mode, and the only one whose flags the user owns: same two-pass, measure-and-retry, size-capped approach as `under50mb*`, but cap, codec (libx265/libx264), speed preset, profile, pixel format, maxrate/bufsize multipliers and free-text extra args all come from the `custom` block of `.export_settings.json`, edited in the top bar's **gear** dialog (`FfmpegCustomSettings.jsx`) and rendered by `render_custom_two_pass`. Two ways it differs from `under50mb*` beyond configurability: the bitrate formula is `(target_bytes × 8 × safety) ÷ duration ÷ 1000` with the **whole** budget given to video (audio is muxed on top, so `safety` is what has to cover it — a deliberate deviation from `target_bitrate_for_size`, which reserves the audio bitrate first), and `maxrate` defaults *below* the average (0.95×) so VBV holds the file under target — real output lands ≈0.85 of the cap with the default 0.90 headroom. The three modes needing two ffmpeg invocations are `MULTIPASS_QUALITIES`.

- **Export preset** — a *named settings bundle* (`{name, settings}`) for the custom mode, not to be confused with ffmpeg's `-preset` speed knob (which is one field inside it — on the wire the speed presets are `custom_options.encoder_presets`, the bundles are `presets`). Saved in `.export_settings.json`, capped at `MAX_EXPORT_PRESETS = 200`, names unique case-insensitively (macOS filesystem semantics), and carried inside the `.nara` project file so a project travels with its delivery settings. Selecting one in the gear dialog loads *and* activates it; Import/Export move one bundle at a time as a `{kind: "nara-export-settings"}` JSON file.

- **selectedPart** — which piece of the selected clip is active: `'main' | 'head' | 'tail' | 'round'`. Lets a hold segment be deleted (Delete key / hover ×) without deleting its clip.

- **.nara project** — JSON `{ version: 7, clips, track2Clips, audioBeds, selectedId, exportPresets, noiseEnabled, noiseGainDb }`, saved to `projects/` via `/api/projects` or downloaded as a file. Version 2 added `track2Clips`, 3 added a single `audioBed`, 4 added `exportPresets`, 5 turned A1 into the `audioBeds` lane, 6 added the room-tone toggle and its level plus each A1 clip's `startSec`, 7 each A1 clip's optional `inSec`/`outSec` (the A1 split). Nothing reads `version` (it's a marker for humans) and older files load unchanged — a lone `audioBed` is promoted to a one-clip lane, A1 clips with no `startSec` are back-filled from the cumulative sum that used to BE their position (`clipMath.normalizeBeds`), an A1 clip with no `inSec`/`outSec` plays its whole file exactly as it always did (so a version-6 project renders bit-identically), a missing preset list defaults to none, and absent room-tone keys default to off at +12 dB (back-filled by key presence, `== null`, since 0 dB is a legal level that `||` would silently promote). The backend treats it as opaque JSON except validating `clips` is a list.

- **video_duration vs duration** — `get_video_info` returns both: `duration` = container (longest stream, often audio); `video_duration` = video stream only, can be shorter. All frame-freeze sampling and outSec clamping use `video_duration`.

- **Frame budget (`n_norm_frames`)** — `build_timeline_filter` precomputes the exact frame count each normalized clip segment must emit and hard-caps the chain with `trim=start_frame=0:end_frame=N`, padding/cutting audio to the same length. See gotchas.md for why.

- **browser_playable** — probe flag; false means the codec isn't in `BROWSER_SAFE_VIDEO_CODECS` {h264, vp8, vp9, av1}, and the UI swaps the media URL to the `/preview/<dir>/<name>` transcode route (cached in `.preview_cache/`).

- **PPS** — pixels per second (60) for timeline layout math (`clipMainPx` etc. in `clipMath.js`).

- **Media Bin / Exports** — left panel = source files in `input/`; right panel = rendered files in the export dir. Both have localStorage favorites, filter, and sort (`fileList.js`, keys `nara-favorites-<dir>`).
